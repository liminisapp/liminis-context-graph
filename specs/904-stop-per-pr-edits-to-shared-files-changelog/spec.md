# Feature Specification: Stop per-PR edits to shared files: changelog fragments, and generate llms-full.txt at docs publish

**Feature Branch**: `fabrik/issue-904`
**Created**: 2026-11-23
**Status**: Specified
**Input**: User description: "Stop per-PR edits to shared files: changelog fragments, and generate llms-full.txt at docs publish.

Two files are edited by almost every PR. Because of that, concurrent PRs always overlap, so the Fabrik merge train can't batch them and lands members one at a time, with a full ~40 min CI run per landing. Today every 0.19.2 member was deferred at least once for \"overlaps #N on CHANGELOG.md\", and each landing forced the remaining members through another rebase.

1. `CHANGELOG.md`. Every PR adds its entry to the same `## [Unreleased]` block. CONTRIBUTING requires it, and so does the #852 guard (`scripts/assert-contract-changelog.sh`), which fails a PR that changes `contract/` without touching `CHANGELOG.md`.
2. `docs/llms-full.txt`. It is generated by `scripts/generate-docs-llms-full.sh`, committed, and drift-checked by `docs-drift.yml` (\"Verify llms-full.txt is up to date\"). Every docs-touching PR regenerates it, and it overlaps the same way.

The published outputs are still needed: the CHANGELOG feeds the GitHub Release body (cargo-dist's `plan` embeds the version's CHANGELOG section; see `release.yml` and `scripts/assert-plan-output.sh`); the CHANGELOG ships in the release archives (`.github/build-setup.yml`); the CHANGELOG is the documented channel for behaviour changes that affect raw-socket clients (CONTRIBUTING, \"CHANGELOG rules for raw-socket clients\"); `llms-full.txt` is published on the docs site (ADR-0295). Only the per-PR editing of one shared file has to go.

Change — 1. Changelog fragments: one file per PR (`changelog.d/<issue>-<slug>.md`) using the existing Keep a Changelog section headings inside the fragment, in a format a small dependency-free script can assemble. A script (e.g. `scripts/assemble-changelog.sh`) merges every fragment into `CHANGELOG.md`'s `## [Unreleased]` section in the release PR, before the version rename, grouping entries by section in a stable order, then deleting the fragments; added to CONTRIBUTING's release runbook before \"Update `CHANGELOG.md`\"; idempotent; fails clearly on a malformed fragment or unknown section. CI check: every fragment in a PR must parse and name a known section; the script gets a self-test like the other `scripts/test-*.sh`. #852 guard: `assert-contract-changelog.sh` and its self-test pass when the PR adds or edits a `changelog.d/` fragment; editing `CHANGELOG.md` directly still passes during the transition. Transition (must hold): entries already under `## [Unreleased]` stay where they are; PRs in flight (#859, #861, #862, #900, #903) still edit `CHANGELOG.md` directly and that must keep working, and the assembled release section must contain both kinds of entry. Instructions: CONTRIBUTING and the repo's agent instructions (`CLAUDE.md` / anything that tells workers to \"update CHANGELOG.md\") now say to write a fragment, keeping the raw-socket-client rules, which apply to the fragment text. Classifier: `.github/actions/classify-changes` must treat `changelog.d/` like `CHANGELOG.md` does today, with a pattern test.

2. Stop committing `docs/llms-full.txt`: generate it at publish time by running `scripts/generate-docs-llms-full.sh` in the docs publishing workflow (`docs-publish.yml` / `scripts/docs-publish-build*`), so the published site still serves `llms-full.txt` at the same URL. Remove the file from git, add it to `.gitignore`, and replace the `docs-drift.yml` drift check with a check that the generator runs cleanly on the PR (still catching the constructs it rejects today). Update CONTRIBUTING (line ~242) and ADR-0295 to match, with a short ADR note or amendment explaining why. Check nothing else needs the committed copy (links to the raw file on GitHub, the release workflow, tests); if something does, say what and how it is handled.

Out of scope: changing what goes into a changelog entry, the Keep a Changelog format of the published file, or how release notes are written; any change to the Fabrik merge train.

Acceptance: a PR that adds only a fragment, with no `CHANGELOG.md` edit, passes CI (including one that touches `contract/`); running the assemble script on a tree with fragments plus existing `[Unreleased]` entries gives a correct, grouped `[Unreleased]` section and removes the fragments, and a second run is a no-op; the release-notes path still works (`dist plan` or the `scripts/assert-plan-output.sh` self-test sees the assembled section); `docs/llms-full.txt` is no longer tracked, the docs build produces it, and the published site serves it at the same path; this PR itself uses a fragment for its own entry.

Sequencing: in 0.19.2 at the maintainer's request. It must not force the in-flight 0.19.2 PRs (#859, #861, #862) through extra rework: they keep editing `CHANGELOG.md` directly, and the transition rule covers them. Removing `docs/llms-full.txt` will conflict with any in-flight PR that regenerated it; the merge train resolves that by regenerating or dropping the file on rebase, so make the generator easy to run and the removal obvious in the diff."

## Background

Two files are touched by nearly every PR: the `## [Unreleased]` block of `CHANGELOG.md`, and the committed, generated `docs/llms-full.txt`. Because concurrent PRs always edit the same lines, the Fabrik merge train sees them as overlapping, cannot batch them, and lands them one at a time with a full ~40 minute CI run per landing. During 0.19.2 every member was deferred at least once for "overlaps #N on CHANGELOG.md", and each landing forced the remaining members through another rebase.

The published outputs of both files are still required and must not change:

- The **CHANGELOG** feeds the GitHub Release body (cargo-dist `plan` embeds the version's section; `release.yml`, `scripts/assert-plan-output.sh`), ships in the release archives, and is the documented channel for behaviour changes affecting raw-socket clients.
- **`llms-full.txt`** is published on the docs site at a stable URL (ADR-0295).

Only the per-PR editing of a single shared file has to go. The fix is to move each PR's changelog entry into its own file (assembled into `CHANGELOG.md` at release time) and to stop committing the generated `llms-full.txt` (building it at docs publish time instead).

Observations from the repo that shape the requirements:

- `scripts/assert-contract-changelog.sh` (#852) and its self-test currently require `CHANGELOG.md` to be touched when `contract/` changes.
- `.github/actions/classify-changes` classifies `CHANGELOG.md` as a docs-only path (with a pattern test in `test-patterns.sh`); `changelog.d/` must be classified the same way, or fragment-only PRs would trigger the full Rust CI.
- `.gitignore` already ignores `site/public/llms-full.txt` (the site-side copy); `docs/llms-full.txt` is a separate, tracked file.
- `docs/index.md` links to `llms-full.txt` relatively, so removing the tracked copy must not leave a broken link in the docs link check.
- `CONTRIBUTING.md` (~line 242) instructs contributors to regenerate `docs/llms-full.txt`; its release runbook (~line 257) has the "Update `CHANGELOG.md`" step; line ~321 tells contributors to record contract changes in `CHANGELOG.md`.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Contributor adds a changelog entry without touching `CHANGELOG.md` (Priority: P1)

A contributor (human or Fabrik worker) whose PR has a user-visible change writes one new file, `changelog.d/<issue>-<slug>.md`, containing Keep a Changelog section headings and entries. They do not edit `CHANGELOG.md`. Two such PRs open at once no longer overlap on any file.

**Why this priority**: This removes the dominant source of merge-train serialization and is the core of the issue.

**Independent Test**: Open a PR that only adds a valid fragment (and, in a variant, also changes `contract/`). CI must pass, including the #852 guard, and the PR must be classified as docs-only.

**Acceptance Scenarios**:

1. **Given** a PR that adds only a valid `changelog.d/` fragment, **When** CI runs, **Then** all required checks pass and no `CHANGELOG.md` edit is demanded.
2. **Given** a PR that changes `contract/` and adds a fragment but does not edit `CHANGELOG.md`, **When** the #852 guard runs, **Then** it passes.
3. **Given** a PR that changes `contract/` and edits neither a fragment nor `CHANGELOG.md`, **When** the guard runs, **Then** it still fails with a message that mentions fragments.
4. **Given** a PR that edits `CHANGELOG.md` directly (as #859, #861, #862, #900, #903 do), **When** CI runs, **Then** it still passes during the transition.
5. **Given** a PR that touches only `changelog.d/` files, **When** the change classifier runs, **Then** it is classified as docs-only, exactly as a `CHANGELOG.md`-only PR is today.

---

### User Story 2 - Fragment validation catches mistakes in the PR (Priority: P1)

A contributor writes a fragment with a typo in a section heading or an empty or malformed file. CI fails on that PR, with a message that names the file and the problem, rather than the mistake surfacing at release time.

**Why this priority**: Fragments are assembled unattended in the release PR; errors must be caught where they are introduced.

**Independent Test**: Run the validation against fragments with an unknown section, no section, entries before any heading, and an empty body; each must fail clearly. A valid fragment must pass.

**Acceptance Scenarios**:

1. **Given** a fragment whose heading is not a known Keep a Changelog section, **When** the check runs, **Then** it fails and names the file and the unknown section.
2. **Given** a fragment with no section heading or no entries, **When** the check runs, **Then** it fails and names the file.
3. **Given** a fragment that is valid, **When** the check runs, **Then** it passes.
4. **Given** the repository's script self-tests, **When** they run in CI, **Then** the assemble script's self-test runs and passes alongside the other `scripts/test-*.sh`.

---

### User Story 3 - Release manager assembles the changelog at release time (Priority: P1)

In the release PR, the release manager runs the assemble script before renaming `## [Unreleased]` to the version. The script merges all fragments, together with any entries already under `## [Unreleased]`, into one grouped section in a stable section order, and deletes the fragments. The existing runbook step then renames the section as before, and the GitHub Release body and release archives carry the same content as today.

**Why this priority**: Without assembly the fragments never reach the published CHANGELOG, so the change would break release notes.

**Independent Test**: On a tree that has several fragments plus pre-existing `[Unreleased]` entries, run the script once and inspect `CHANGELOG.md`; run it a second time and confirm no change; run the `assert-plan-output.sh` self-test (or `dist plan`) and confirm the section is seen.

**Acceptance Scenarios**:

1. **Given** fragments under several sections and existing `[Unreleased]` entries, **When** the script runs, **Then** `## [Unreleased]` contains every entry from both sources, grouped under each section heading in a fixed, documented order, and the fragment files are deleted.
2. **Given** the script has already run, **When** it runs again with no fragments present, **Then** it makes no change and exits successfully.
3. **Given** a malformed fragment or unknown section, **When** the script runs, **Then** it exits non-zero with a clear message naming the file, and does not modify `CHANGELOG.md` or delete any fragment.
4. **Given** an assembled `## [Unreleased]`, **When** the existing rename step and cargo-dist `plan` run, **Then** the version's section is embedded in the release notes as before.
5. **Given** the release runbook in CONTRIBUTING, **When** a release manager follows it, **Then** assembly is a step that comes before "Update `CHANGELOG.md`".

---

### User Story 4 - Docs publish generates `llms-full.txt`; PRs no longer commit it (Priority: P2)

A contributor who edits docs no longer regenerates or commits `docs/llms-full.txt`. The docs publish workflow generates it as part of the build, and the published site serves it at the same URL as today. The docs-drift workflow still rejects a PR whose docs would make the generator fail.

**Why this priority**: It removes the second shared file. It is lower than the changelog because the changelog is touched by every PR while `llms-full.txt` only by docs-touching ones.

**Independent Test**: Run the docs publish build and confirm `llms-full.txt` is in the output at the same path; confirm `docs/llms-full.txt` is untracked and ignored; confirm the PR-time check fails on a docs page containing a construct the generator rejects today.

**Acceptance Scenarios**:

1. **Given** the docs publish workflow runs, **When** the build finishes, **Then** the published site serves `llms-full.txt` at the same URL as before, with content produced by the generator.
2. **Given** a checkout of the repo, **When** a contributor runs `git ls-files docs/llms-full.txt`, **Then** nothing is listed, and running the generator locally creates a file that `git status` ignores.
3. **Given** a PR whose docs contain a construct the generator rejects today, **When** the docs-drift workflow runs, **Then** the check fails with the generator's message.
4. **Given** a PR that does not touch docs, **When** CI runs, **Then** nothing about `llms-full.txt` is required of it.
5. **Given** the docs link check, **When** it runs after the file is untracked, **Then** the `llms-full.txt` link in `docs/index.md` does not fail the check (and still resolves on the published site).

---

### User Story 5 - Instructions and decision record match the new workflow (Priority: P2)

A new contributor or agent reading CONTRIBUTING, `CLAUDE.md` or the ADRs is told to write a fragment (not edit `CHANGELOG.md`) and not to commit `llms-full.txt`, and can see why.

**Why this priority**: Without this, workers keep following the old instructions and re-create the overlap.

**Independent Test**: Search CONTRIBUTING, `CLAUDE.md` and other agent/worker instructions for "update CHANGELOG.md"-style guidance and for the `llms-full.txt` regeneration step; none should remain that contradicts the new workflow.

**Acceptance Scenarios**:

1. **Given** CONTRIBUTING's changelog guidance, **When** read, **Then** it says to add a `changelog.d/<issue>-<slug>.md` fragment, describes the format and allowed sections, and still carries the "CHANGELOG rules for raw-socket clients" applying to the fragment text.
2. **Given** the contract-change guidance (~line 321), **When** read, **Then** it points to a fragment and the guard's updated behaviour.
3. **Given** CONTRIBUTING (~line 242) and ADR-0295, **When** read, **Then** they state that `llms-full.txt` is generated at publish time and not committed, with an ADR note or amendment explaining why (named by issue number per repository convention).
4. **Given** this PR, **When** its diff is read, **Then** its own changelog entry is a fragment, not an edit to `CHANGELOG.md`.

## Edge Cases

- **Mixed sources**: the same section heading appears both in existing `[Unreleased]` text and in fragments; the assembled output has one heading per section with all entries beneath it.
- **Transition**: direct `CHANGELOG.md` edits by in-flight PRs land after this PR merges; the next assembly must still place them correctly and not duplicate or drop them.
- **No fragments, no `[Unreleased]` changes**: the script is a no-op and succeeds.
- **Fragment with several sections**, or only a subset of sections: only the sections present appear in the output; empty sections are not emitted.
- **Multi-line and nested-bullet entries**: preserved intact, including indentation and entries that contain the text of a heading-like line within code spans.
- **Non-fragment files in `changelog.d/`** (for example a README describing the format): ignored by assembly and validation, and not deleted.
- **Partial failure**: if any fragment is invalid, no fragment is deleted and `CHANGELOG.md` is left unchanged.
- **Release-note path**: an `[Unreleased]` section that is empty after assembly (no fragments, no entries) should behave as today at the release step.
- **In-flight PRs that regenerated `docs/llms-full.txt`**: removal conflicts on rebase; the removal must be obvious in the diff, and the generator easy to run, so the merge train can resolve by dropping or regenerating.
- **Generator failure at publish time** must fail the docs publish run rather than publish a site with a missing or stale `llms-full.txt`.
- **Versioned docs publishing** (ADR-0477 publishes docs per tag): `llms-full.txt` is produced for each published version from that version's docs.
- **Consumers of the committed copy**: any link to the raw file on GitHub, release workflow step, or test that reads `docs/llms-full.txt` is identified and either updated or documented as handled.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The repository MUST support one changelog fragment file per PR under `changelog.d/`, named `<issue>-<slug>.md`, whose content uses the existing Keep a Changelog section headings (`### Added`, `### Changed`, `### Fixed`, and the other sections the repo's CHANGELOG uses).
- **FR-002**: The fragment format MUST be simple enough to be parsed and assembled by a small shell-level script with no new dependencies, and MUST be documented (format, allowed sections, naming) in CONTRIBUTING and in a note in `changelog.d/` that is itself ignored by assembly.
- **FR-003**: An assemble script (for example `scripts/assemble-changelog.sh`) MUST merge every fragment, plus any entries already under `## [Unreleased]`, into `CHANGELOG.md`'s `## [Unreleased]` section, grouped by section heading in a stable, documented order, and delete the fragments it consumed.
- **FR-004**: The assemble script MUST be idempotent: a second run with no fragments present makes no change and exits successfully.
- **FR-005**: The assemble script MUST exit non-zero with a message naming the offending file and the problem for a malformed fragment (no section, entries outside a section, empty body) or an unknown section, and MUST leave `CHANGELOG.md` and all fragments untouched when it fails.
- **FR-006**: Entries already under `## [Unreleased]` MUST remain in place, and the assembled section MUST contain both these and fragment entries (transition rule); this PR MUST NOT move or rewrite existing `[Unreleased]` entries.
- **FR-007**: CI MUST validate every fragment added or changed in a PR (parses, names only known sections) and MUST fail the PR with a clear message when one is invalid.
- **FR-008**: The assemble tooling MUST have a self-test in the style of the other `scripts/test-*.sh`, run by CI, covering at least: grouping and ordering, mixed fragment plus existing entries, idempotence, malformed fragment, unknown section, and non-fragment files being ignored.
- **FR-009**: `scripts/assert-contract-changelog.sh` MUST pass when the PR adds or edits a `changelog.d/` fragment, and MUST still pass when it edits `CHANGELOG.md` directly; it MUST still fail when `contract/` changes with neither. Its self-test MUST cover all three cases, and its failure message MUST describe the fragment route.
- **FR-010**: `.github/actions/classify-changes` MUST classify `changelog.d/` paths as docs-only exactly as it does `CHANGELOG.md`, with a case added to its pattern test (`test-patterns.sh`).
- **FR-011**: CONTRIBUTING's release runbook MUST include running the assemble script as a step before "Update `CHANGELOG.md`" (the version rename), and the runbook's remaining steps MUST work unchanged on the assembled output.
- **FR-012**: The assembled `CHANGELOG.md` MUST remain compatible with the release-notes path: cargo-dist `plan` embedding of the version's section, `release.yml`, `scripts/assert-plan-output.sh` and its self-test, and the archive staging in `.github/build-setup.yml` MUST work without behavioural change.
- **FR-013**: CONTRIBUTING, `CLAUDE.md`, and any other instruction that tells contributors or workers to add or update a `CHANGELOG.md` entry MUST be changed to say to write a fragment. The "CHANGELOG rules for raw-socket clients" (including naming raw-socket clients and the **BREAKING** convention for contract changes) MUST be retained and stated as applying to the fragment text.
- **FR-014**: `docs/llms-full.txt` MUST be removed from version control and added to `.gitignore`.
- **FR-015**: The docs publishing workflow MUST run `scripts/generate-docs-llms-full.sh` as part of the build, so the published site serves `llms-full.txt` at the same URL as before, for every published docs version; a generator failure MUST fail the publish.
- **FR-016**: The `docs-drift.yml` check "Verify llms-full.txt is up to date" MUST be replaced by a check that the generator runs cleanly on the PR; it MUST still fail on every construct the generator rejects today, and MUST NOT require a committed output file.
- **FR-017**: CONTRIBUTING (the `llms-full.txt` regeneration step, ~line 242) MUST be updated to say the file is generated at publish time and not committed, and ADR-0295 MUST be amended or accompanied by a short ADR note explaining why, following the repo's ADR naming rule (`docs/adr/<issue_number>-<slug>.md`, with the index updated).
- **FR-018**: All other references to the committed `docs/llms-full.txt` (the `docs/index.md` link and the docs link checker, links to the raw file on GitHub, release workflow, tests, other docs and ADR-0477's mentions) MUST be audited; each that depends on the committed copy MUST be updated, and the PR description MUST state what was found and how each was handled.
- **FR-019**: The generator MUST remain simple to run locally with one command, and the removal of `docs/llms-full.txt` MUST be a plain, visible deletion in the diff, so the merge train can resolve conflicts with in-flight PRs by dropping or regenerating the file.
- **FR-020**: This PR MUST record its own changelog entry as a `changelog.d/` fragment and MUST NOT edit `CHANGELOG.md`.
- **FR-021**: Fragment and assembly behaviour MUST NOT require changes to the Fabrik merge train, and MUST NOT change the content rules of changelog entries or the published Keep a Changelog format.

### Key Entities

- **Changelog fragment**: a single `changelog.d/<issue>-<slug>.md` file holding one PR's entries under one or more known section headings.
- **Known section**: one of the Keep a Changelog headings the repo's CHANGELOG already uses; the assemble order is stable and documented.
- **Assembled `[Unreleased]` section**: the union of pre-existing `[Unreleased]` entries and all fragment entries, grouped by section.
- **`llms-full.txt`**: a generated bundle of the docs content, produced at docs publish time and served at a stable URL; no longer a tracked file.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Two concurrent PRs that each add a changelog entry (as fragments) share no changed file, so the merge train no longer reports an overlap on `CHANGELOG.md` between them.
- **SC-002**: Two concurrent docs-touching PRs no longer both change `docs/llms-full.txt`, so no overlap is reported on that file.
- **SC-003**: A PR that adds only a valid fragment, including one that touches `contract/`, passes all required CI checks and is classified docs-only.
- **SC-004**: Running the assemble script on a fixture with fragments plus existing `[Unreleased]` entries yields one grouped, correctly ordered section containing 100% of the entries from both sources, with fragments removed; a second run produces zero diff.
- **SC-005**: Every malformed-fragment and unknown-section case in the self-test fails with a non-zero exit and a message naming the file, leaving the working tree unchanged.
- **SC-006**: After assembly and the version rename, the `assert-plan-output.sh` self-test (or `dist plan`) finds the version's section and the release body matches what would previously have been produced from the same entries.
- **SC-007**: `git ls-files docs/llms-full.txt` returns nothing, and the docs publish build output contains `llms-full.txt` at the same published path as before.
- **SC-008**: The PR-time docs check fails for a docs change containing a generator-rejected construct and passes for a clean tree, without any committed `llms-full.txt`.
- **SC-009**: No instruction file in the repo tells a contributor to edit `CHANGELOG.md` for a per-PR entry or to commit `docs/llms-full.txt`, other than documented transition wording.
- **SC-010**: The in-flight 0.19.2 PRs (#859, #861, #862) land without any extra changes required of them beyond what a normal rebase does.

## Assumptions

- The exact fragment layout is a design choice for the plan: a fragment is a Markdown file made of `### <Section>` headings followed by bullet entries, matching the CHANGELOG's own style, which keeps it parseable by a small shell script. The spec only requires that it use the existing section headings.
- The "known sections" list is the set of Keep a Changelog headings already used in `CHANGELOG.md` (Added, Changed, Deprecated, Removed, Fixed, Security, and any other heading the file already uses); the research stage will confirm the actual list and the stable order.
- Assembly is run manually by the release manager in the release PR, as a runbook step; it is not run automatically on every merge.
- The fragment-validation CI check may be part of an existing workflow or script-test job; where it runs is a plan-stage decision as long as it runs on PRs that touch `changelog.d/`.
- Fragment files are named by issue number, or by PR number when there is no motivating issue, consistent with the `specs/` and ADR numbering conventions.
- A `changelog.d/` note or README documenting the format is acceptable and is ignored by the script.
- The transition wording for "editing `CHANGELOG.md` directly still passes" is temporary, and removing it later is a separate follow-up.
- This repo's docs site build already has a place where the generator output can be added to the published artifact (the existing `site/public/llms-full.txt` ignore entry suggests this).

## Out of Scope *(optional)*

- Changing what goes into a changelog entry, the Keep a Changelog format of the published `CHANGELOG.md`, or how release notes are written.
- Any change to the Fabrik merge train.
- Migrating existing `[Unreleased]` entries into fragments.
- Removing the "edit `CHANGELOG.md` directly" allowance (a later follow-up once in-flight PRs have landed).
- Changing the content or generator logic of `llms-full.txt` beyond what is needed to run it at publish time.
