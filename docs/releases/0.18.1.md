# 0.18.1 — 2026-11-13 (full release notes)

A patch release, prompted by the Orac project's reports. It adds two operator controls and fixes
one bug:

- bound lbug's memory and threads for memory-limited containers (#737);
- restrict which groups clients may write to, enforced in the daemon (#742, for #740);
- fix cross-group edges that went missing depending on the order groups were rebuilt (#741, for
  #739).

## Upgrading

Nothing to do. There's no schema or storage change: the storage version stays 47, lbug stays
0.21.2, and there is no one-time rebuild on first start. Every new setting is opt-in. With none
set, behaviour matches 0.18.0 except for the cross-group fix below.

## Added

### Memory and thread limits for lbug (#737, ADR-0737)

By default lbug takes about 80% of system memory for its buffer pool. In a memory-limited
container that led to OOM-kill loops during the startup WAL rebuild, with the service stuck at
`busy (rebuilding)`.

| Variable | Accepts | Unset |
|---|---|---|
| `LCG_BUFFER_POOL_BYTES` | a positive byte count, or an integer with a `KiB`/`MiB`/`GiB` suffix (case-insensitive) | lbug's default |
| `LCG_MAX_THREADS` | a positive integer | lbug's default |

- The effective values are logged at startup.
- **Invalid values are fatal at startup** and the error names the variable and the value. That
  covers zero, empty, fractional, decimal or unknown suffixes, overflow and non-numeric values.
  There is no silent fallback to the default.
- See `docs/operations.md` for sizing guidance and `docs/configuration.md` for the reference rows.

### Per-group write allow-list (#742, implements #740, ADR-0742)

`--scope` decides which tools a connection can see. It doesn't say which groups a write-capable
connection may change. `--writable-groups=<g1,g2,…>` (or `LCG_WRITABLE_GROUPS`) does.

- **Where it's enforced:** in the daemon's core request path, so IPC, standalone `--mcp-stdio`
  and attached `--mcp-stdio --connect` are all covered. Passing `--writable-groups` with
  `--connect` is a CLI error, because the daemon enforces the list. An inherited
  `LCG_WRITABLE_GROUPS` there logs a warning.
- **Parsing:** strict. The flag wins over the env var. An empty value, an empty entry (`a,,b`) or an
  entry containing whitespace fails startup. The effective list is logged. Unset leaves every
  group writable.
- **Refusal:** JSON-RPC `-32004`, with `data {reason, group_ids, setting, env, writable_groups}`.
  The check runs before any handler work, so a refused call does no embedding or extraction and
  writes no database row or WAL event.
- **Which group is checked:**
  - an omitted `group_id` is checked against the default group, which must be listed to stay
    writable;
  - `knowledge_add_cross_group_edge` is checked against the edge's own `group_id`, because the
    foreign endpoints are read-only pointers;
  - multi-group writes need every written group listed;
  - `knowledge_delete_by_group` and `knowledge_rebuild_from_wal` also need every group that owns a
    cross-group pointer into the target, and `knowledge_rebind_pointers` needs the pointer owners
    (ADR-0385);
  - `knowledge_delete_episode` is checked against the episode's own group;
  - `knowledge_clear_all`, `knowledge_apply_corrections` and, on a healthy database,
    `knowledge_recover` need every present group listed.
- **Raw Cypher:** `knowledge_query_cypher` is refused outright while a list is set, reads included.
  Cypher can't be scoped by group.
- **Exempt:** `knowledge_recover_full`, `knowledge_recover` on a degraded database (a degraded
  database must stay recoverable, ADR-0009), and the WAL, checkpoint, index and process-only admin
  tools.
- **Fails closed:** every dispatched method has a write classification, and a test keeps the table
  and the dispatcher in step. A method without one is refused while a list is set.

Things to know when adopting it:

- purging or rebuilding a listed group is refused while an unlisted group holds a pointer into it,
  so list the owner too;
- `dry_run` gets no exception;
- reads of unlisted groups are unaffected.

## Fixed

### Cross-group edges and rebuild order (#741, fixes #739, ADR-0741)

Rebuilding the group that owns a cross-group edge before the group its pointer targets left the
edge missing. `knowledge_status` still reported the pointer as `bound`, and nothing repaired it:
`knowledge_rebuild_from_wal` only re-bound pointers after a detected WAL reset, and the
staleness gate (ADR-0392) skips a `bound` pointer.

After every successful non-dry-run `knowledge_rebuild_from_wal` (full or incremental, streaming or
background job), lcg now runs two steps:

1. pointers on edges the rebuilt group owns that claim `bound` but have no edge behind them are
   demoted to `unbound`, so `knowledge_status` reports them honestly;
2. the staleness-gated rebind of pointers *into* the rebuilt group runs, and each rebind write is
   flushed to the WAL of the group that owns the row.

The final graph no longer depends on the order groups are rebuilt in.

Behaviour changes:

- `cross_group_rebind` in the rebuild result is non-null on every successful non-dry-run rebuild.
  It stays `null` on `dry_run`, or if the repair fails (logged).
- **An ordinary rebuild can now append rebind writes to another group's WAL stream.** Before, only
  a WAL reset did that. If you replicate WAL streams to a read-only receiver, expect these writes.
- A `force_clear` rebuild of a pointer's target group now re-binds pointers in groups that are
  already built.

## Changed

- **macOS release builds run on `macos-15`** (#735). GitHub retired the `macos-14` runner image on
  2026-11-02. Binaries still target macOS 11.0 and link OpenSSL through the same Homebrew prefix.
- **Dependencies:**
  - `rmcp` 3.7.0 → 3.8.0 (#726);
  - `swift-transformers` 1.3.5 → 1.4.0 in the local inference sidecar (#730);
  - Astro and Starlight patch updates for the docs site (#729).

## Known issues

- **Windows: lbug's CHECKPOINT can silently corrupt some STRING and INT8/UINT8 data** (#719,
  LadybugDB/ladybug#1447). Unchanged from 0.18.0.
  - **Cause:** MSVC's vectorized `std::minmax_element` can return a wrong min/max for some byte
    arrays. A column chunk is then stored as a constant, and the checkpoint keeps one byte.
  - **Scope:** Windows x64 builds that link upstream's prebuilt lbug 0.21.2. It's now reproduced
    through lcg itself on Windows x64. macOS and Linux aren't affected.
  - **Recovery:** lcg's own WAL isn't affected, so `knowledge_rebuild_from_wal` restores a corrupted
    graph.
  - **Fix:** needs an upstream lbug release; #719 tracks it.

## What was verified

Checks ran against `main` at `dd19f3b1` (after #744), using the **CI-built macOS release artifact**
from `main`'s post-merge `Release` run, which is the code that ships. That binary still reports
0.18.0, because the version bump is in the release PR.

- **MCP:** `tools/list` returns 50 tools, the same as 0.18.0.
- **#737:**
  - `LCG_BUFFER_POOL_BYTES=0`, `=1.5GiB` and `LCG_MAX_THREADS=abc` each fail startup with a `FATAL`
    error that names the variable and the value;
  - `256MiB` with 2 threads starts healthy and logs
    `lbug buffer pool: 256.0 MiB (268435456 bytes) …; max threads: 2`.
- **#742:**
  - `LCG_WRITABLE_GROUPS=a,,b` fails startup;
  - with `--writable-groups=a`, the effective list is logged;
  - a write to `a` succeeds;
  - writes to `b`, and to the default group via an omitted `group_id`, are refused with `-32004`;
  - `knowledge_query_cypher` is refused even for `RETURN 1`;
  - a read of `b` succeeds.
- **#741:** covered by CI. Eight new end-to-end tests replay #739's reproduction through real
  dispatch: both rebuild orders, the streaming and background-job paths, incremental and
  `force_clear` rebuilds, and an operator rebind.
- **macOS linkage:**
  - OpenSSL 3 is linked through the stable Homebrew prefix (`/opt/homebrew/opt/openssl@3/lib`);
  - `minos` is 11.0 on the `macos-15` runner;
  - `LC_RPATH` is unchanged from 0.18.0.
- **Extensions:** the pins (`.cargo/config.toml`) are unchanged since v0.18.0.
- **CI:** `main`'s post-merge run built release artifacts for all four targets. The full Rust suite,
  the real-corpus end-to-end jobs and Windows CI passed on every merged change.
