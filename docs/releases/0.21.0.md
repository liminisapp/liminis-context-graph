# 0.21.0 — 2026-11-25 (full release notes)

A minor release, because of one breaking change: requests now have a size limit (#293). It also
finishes the ingest-supervision work that integrators asked for in #836: a per-request deadline and
a join for duplicate in-flight resubmits (#914). There is no storage migration. lbug stays 0.21.2,
`PROTOCOL_VERSION` stays 1, and the MCP registry stays at 60 tools.

The complete list is in [`CHANGELOG.md`](../../CHANGELOG.md#0210---2026-11-25).

## Upgrading

- **Request lines over 16 MiB and `chunk_text` over 512 KiB are refused (#293). BREAKING for
  raw-socket clients that sent larger ones.**
  - The socket read loop used to buffer a request line without any bound. It now stops at
    `LCG_REQUEST_MAX_BYTES` (default 16 MiB) and answers with JSON-RPC error `-32005`, `id: null`,
    `error.data.reason: "request_too_large"`. The line is refused before it is parsed, and the same
    connection keeps serving. A line that runs past four times the limit closes the connection.
  - `knowledge_process_chunk` refuses a `chunk_text` over `LCG_CHUNK_TEXT_MAX_BYTES` (default
    512 KiB, in UTF-8 bytes) with `chunk_text_too_large`, before any extraction or write. Send long
    texts to `knowledge_process_document`, which has its own cap (`LCG_DOCUMENT_MAX_BYTES`, 2 MiB by
    default).
- **Check your settings if you raised `LCG_DOCUMENT_MAX_BYTES`.** The default line limit carries a
  maximal 2 MiB document after worst-case JSON escaping. Startup now refuses a configuration where it
  can't: `LCG_REQUEST_MAX_BYTES` must be at least `6 x LCG_DOCUMENT_MAX_BYTES + 64 KiB`, so a
  document cap above about 2.7 MiB needs a larger line limit too. The error names both settings and
  the minimum. As with `LCG_DOCUMENT_MAX_BYTES`, an empty or invalid value of either new setting
  stops startup.
- **Two new error codes:** `-32005` (`request_too_large`) and `-32006` (`deadline_exceeded`). A
  client that doesn't know them can treat them as ordinary errors.

## Highlights

### Request size limits (#293)

Until now one oversized request could hold unbounded memory while the service read it. Both limits
are checked before any work starts, and both are advertised by the `request_size_limits` feature
string. [ADR-0293](../adr/0293-request-line-limit-and-chunk-cap.md) records the decisions, including
why the line limit sits well above the document cap.

### Ingest deadlines and duplicate-resubmit join (#914, part 2 of #836)

- **`deadline_ms`** on `knowledge_process_chunk` and `knowledge_process_document`: an optional
  positive integer, counted from when the service starts the request.
  - A request that can't reach commit in time stops at its next cancellation point and returns
    `-32006` with `error.data = {"reason": "deadline_exceeded", "phase": …, "committed": false}`.
  - Nothing is written for a chunk. A document adds `"partial": true`: sections already committed
    stay, and nothing is retired.
  - A deadline that passes once the commit has started never interrupts it. The success result then
    carries `"deadline_exceeded": true`.
  - Feature string: `process_deadline`.
- **Join.** An identical `knowledge_process_chunk` for a chunk that is already being ingested waits
  for the first request and returns its result, with `"joined": true`, instead of extracting again.
  - Identical means the same text, attributes, origin, `source_file`, `doc_id` and `reference_time`.
  - If the first request is cancelled by a disconnect or its deadline, the joined ones carry on: one
    of them restarts the ingest and the rest join it. Any other failure of the first request is
    shared, with its error code.
  - A request only joins when the first is the only one in flight for that chunk, so commit order is
    unchanged.
  - Feature string: `chunk_join_inflight`.
- Together these make timeout-and-retry safe. A client can give up on a slow request, retry it on a
  new connection, and pay for one extraction.
- **Pipelining several requests on one connection was declined.**
  [ADR-0914](../adr/0914-declined-pipelining-on-one-connection.md) gives the reasons: replies are
  in order today, progress frames carry no request id, and disconnect detection assumes one request
  in flight. Keep one connection per concurrent request.
- The design is in [ADR-0914](../adr/0914-process-deadline-and-inflight-join.md). The
  `knowledge_process_chunk` response schema gains the optional `joined` and `deadline_exceeded`
  keys.

## Known issues

- **Windows (#719):** unchanged from 0.18.x. lbug's CHECKPOINT can silently corrupt some STRING and
  INT8/UINT8 data. The fix is merged upstream (LadybugDB/ladybug#1593) but isn't in an lbug release
  yet; it will arrive with the lbug upgrade (#718). `knowledge_rebuild_from_wal` restores a graph.
- **#778** stays open, as in 0.20.1: an identity removal made while both a group's stamp and its WAL
  ontology sidecar's `identity_types` are missing is not detected.

## What was verified

- **CI** on both PRs (#926, #927) and on the release PR. The full workspace suite also ran in the
  release profile on macOS arm64 on the release branch: 3,672 passed, 0 failed, 27 ignored.
- **Upgrade from the published 0.20.1 binary, over the IPC socket.** 0.20.1 wrote a group with chunks,
  an episode and a document. 0.21.0 then opened it:
  - episodes read back identically, before and after a restart. `knowledge_capabilities` reports
    0.21.0, protocol 1 and the three new feature strings, and the MCP registry reports 60 tools;
  - a 600 KiB `chunk_text` was refused with `chunk_text_too_large`, with no extraction call and no
    episode. A 100 KiB one was accepted;
  - a 17 MiB request line got `-32005` with `id: null`, and the same connection then answered a
    `health_check`;
  - a document just under 2 MiB, full of quotes and backslashes (a 2.4 MiB request line), was accepted;
  - invalid `deadline_ms` values (0, -5, 1.5, "abc") were rejected. A 500 ms deadline on a 3 s
    extraction got `-32006` (phase `extract`, `committed: false`) and wrote nothing, and a met deadline
    carried no `deadline_exceeded` key;
  - two identical slow chunks sent 0.5 s apart on separate connections both succeeded with the same
    `episode_uuid`, exactly one marked `joined`. They made one extraction's worth of calls and wrote
    one episode, and a third resubmission was the unchanged no-op;
  - startup refused an empty `LCG_REQUEST_MAX_BYTES`, an invalid `LCG_CHUNK_TEXT_MAX_BYTES`, and a
    4 MiB `LCG_DOCUMENT_MAX_BYTES` with the default line limit. Each error named the settings.
- **Sidecar-gated replay tests** (runbook step 1), run serially against a live BGE-base sidecar,
  with no `[SKIP]`:

  | | 0.21.0 | 0.20.0 |
  |---|---|---|
  | cold cache | 137.3 s, 194 batch calls | 140.3 s, 194 batch calls |
  | warm cache | 53.1 s, 0 real calls | 62.8 s, 0 real calls |
  | no-recompute baseline | 48.9 s, 255.2 mutations/s | 57.8 s, 215.9 mutations/s |
  | recompute drift, min cosine (name / fact / content) | 0.999950 / 0.999989 / 0.996619 | identical |

  The drift is identical to 0.20.0's, against the same freshly converted sidecar model (see the
  0.20.0 notes for why it is below 1.0).
