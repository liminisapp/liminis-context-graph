# 0.16.0 — 2026-09-29 (full release notes)

Entities gain a **kind**. Same-named entities of different kinds (`Person "Aurora"` and
`Technology "Aurora"`) now coexist instead of merging, and an ontology can mark which entity types
carry identity. Underneath, the graph engine moves from lbug 0.20.3 to **0.21.0**. This is the
first release where lbug's core and its vector/full-text extensions are built for the same version.

**This is a minor release because first start migrates entities and downgrade is unsupported.
Read Upgrading first.** There is **no storage migration**: databases stay at storage version 47.

## Upgrading

1. **First start migrates entities (#615).** The migration is automatic and runs once:
   - `Entity` gains a `kind` column.
   - `lookup_key` becomes `group_id ␟ kind ␟ lower(name)`.
   - Every existing entity is backfilled to kind `Entity`.
   - `labels` is normalized so `Entity` comes first (for example `[Object, Entity]` →
     `[Entity, Object]`). The label set itself is unchanged.

   On a real 0.14.x notebook (198 entities) this added about 3 seconds to the first start. Later
   starts were back to normal. Nothing is logged while it runs.
2. **Downgrade is unsupported.** A pre-0.16.0 binary cannot replay a WAL written by 0.16.0,
   because `lookup_key` is no longer written to the WAL. **If you may need to roll back, copy your
   workspace's `.lcg/` directory before the first start.** Rolling back means restoring that copy.
3. **No storage migration.** lbug 0.21.0 keeps storage version 47, the same as 0.15.x:
   - A 0.15.x database opens unchanged.
   - A 0.14.x database (storage 42) is migrated to 47 on first checkpoint, exactly as 0.15.0 did.
4. **API changes** (all additive, except where noted):
   - `knowledge_assert_entity` takes `kind`. Omitting it means the default kind `Entity` only.
   - `knowledge_assert_relationship` takes `source_kind` and `target_kind`.
   - There is a new read tool, `knowledge_resolve_entity`.
   - A **name-only resolution that matches several kinds now fails** with JSON-RPC `-32002` and a
     candidate list, instead of picking one.

## Added

- **Kind-scoped entity identity** ([ADR-0615](../adr/0615-kind-scoped-entity-identity.md), #615):
  - `kind` filters on `knowledge_find_entities` and `knowledge_list_entities`.
  - `kind` on `knowledge_merge_entities`. Merges never cross kinds.
  - Kind-aware endpoints on `knowledge_add_cross_group_edge`.
- **Ontology-driven kind assignment** ([ADR-0616](../adr/0616-ontology-driven-kind-assignment.md),
  #616):
  - An entity type marked `identity: true` becomes the `kind` of entities extracted as that type.
  - Unflagged types, and every existing ontology, merge by name exactly as before.
  - A change to a group's identity-bearing set that would reinterpret existing entities is refused
    for that group, with `-32003` on `knowledge_add_episode` and `group_identity_refusals` on
    `knowledge_status`.

## Changed

- **lbug 0.20.3 → 0.21.0** (#619).
  - **Why now.** On 2026-09-29 upstream republished every extension on its `v0.20.0` path. The
    Windows files became 0.20.4-era builds, and against a 0.20.3 core they crash full-text index
    creation (4 of 5 runs, `0xC0000409`). The 0.20.2-era bytes that 0.15.0 was verified against are
    no longer served, so 0.20.3 had no safe Windows pairing left.
  - **What changes.** 0.21.0's extensions are published under their own `v0.21.0` path and built
    for the 0.21.0 core.
  - **API impact.** The Rust binding changes are additive only, and the database config defaults
    are identical.
- **Release builds verify extension bytes** (#593, [ADR-0593](../adr/0593-pin-lbug-extension-bytes.md)).
  - The vector and full-text extension binaries staged into each release archive are checked
    against pinned sha256 hashes in `LBUG_EXTENSION_HASHES`. A mismatch fails the build rather
    than shipping.
  - This check caught the upstream republish above on its first encounter with one.
- **Windows CI now creates and queries vector and full-text indexes** (#587). It no longer only
  checks that the extensions load. This closes the gap that let a broken extension pairing pass CI.

  not just socket presence). No skips.

- Tested both directly (0.14.x → 0.16.0) and in two hops (0.14.x → 0.15.0 → 0.16.0).

- Every node and relationship count matches.

## Caveats

- **Recompute is no longer bit-exact on the release machine.** Minimum cosine is 0.999950, where
  0.15.0's release run recorded 1.000000.
  - This is **not caused by this release.** The same test at the shipped **v0.15.0** tag, on the
    same machine and against the same sidecar, gives identical figures to six decimal places.
  - Between the two runs, the sidecar was rebuilt from current source, and the machine is now on
    macOS 27.0, so the embedding stack changed.
  - A cosine of 0.99995 has no practical effect on search. But recompute-from-WAL is how vectors
    are restored since #526, so the drift is recorded here rather than rounded away.
- **No release-candidate soak.** This release was cut without the usual few days of hands-on use
  of a candidate build.
- **Summary-embedding search had weak coverage in the real-data test.** The notebook's summary
  embeddings were still pending backfill, so every distance tied. The results matched, but that
  proves little.
