# 0.19.1 — 2026-11-16 (full release notes)

A patch release with one fix, from an Orac project report (#775): a group rebuilt from its WAL
into a fresh workspace root was locked by the identity-set guard the first time it extracted,
although its ontology hadn't changed.

## Upgrading

Nothing to do.
- No schema, storage or lbug change: storage stays 47, lbug stays 0.21.2, and the MCP registry
  stays at 52 tools.
- **Downgrade works:** 0.19.0 opens a database 0.19.1 has written, and ignores the new sidecar field.
- A group that 0.19.0 refused this way is accepted on its next start or
  `knowledge_reload_ontology`, provided its data is consistent with its ontology.

## Fixed

### Rebuild into a fresh workspace no longer locks a group (#775, #776, ADR-0776)

An ontology can mark entity types `identity: true`, so extraction assigns them as the entity's
`kind`. The D1 guard (#616, ADR-0616) refuses a change to a group's identity-bearing set that would
reinterpret existing entities. The set in force is recorded in a per-group stamp,
`.lcg/identity-set/<group>.json`, under the workspace root.

**What went wrong.** Hosts that keep only the WAL (ephemeral containers, fresh clones of a
git-hosted WAL) have no stamp, so the recorded set read as empty. The replayed entities already
had their identity kinds, but the guard counted every entity whose labels mentioned the type. It
therefore saw a flag being *added* over existing entities and refused. Every later `add_episode`
for the group failed with `-32003`, and `knowledge_reload_ontology` returned the same refusal.

**What changed.**
- **The guard checks `kind`.** An entity counts as reinterpreted only if its `kind` would differ
  under the new set:
  - adding identity to T counts entities whose own type is T and whose `kind` isn't T (NULL and
    empty included);
  - removing identity from T counts entities whose `kind` is T.
  So a group whose data matches its ontology is accepted with or without a stamp, and the stamp is
  written. A genuine flip on an established group is still refused.
- **Ancestor types.** Kind is never inherited, so an entity of a subtype no longer blocks a flag
  change on its ancestor. This supersedes the corresponding consequence in ADR-0616.
- **The stamp is restored on rebuild.** The WAL ontology sidecar (`.wal-ontology.json`) now
  records the group's identity types. `knowledge_rebuild_from_wal` restores a missing stamp from
  it and never overwrites an existing one. Sidecars written before 0.19.1 don't have the field and
  restore nothing; the kind-aware check covers that case.

## Known issues

- **Removing an identity flag while the stamp is missing isn't caught (#778).** If a group's stamp
  is lost and identity is removed from a type before any rebuild, the change is accepted. 0.19.0
  behaves the same. A rebuild from a WAL written by 0.19.1 restores the stamp and closes the gap.
- **Windows (#719):** unchanged from 0.18.x. lbug's CHECKPOINT can silently corrupt some STRING
  and INT8/UINT8 data. The fix is merged upstream (LadybugDB/ladybug#1593) but isn't in an lbug
  release yet. `knowledge_rebuild_from_wal` restores a graph.

## What was verified

- **CI:** the full suite on #777, including the new `identity_set_hydrate` tests for the three
  orderings in #775, the stamp restore, and the subtype cases.
- **#775 end to end, release build against the published 0.19.0 binary.** A Person entity
  (`identity: true`) was ingested; then only the WAL was copied to an empty workspace, the
  ontology installed, the group rebuilt and `add_episode` called:

  | Wrote WAL | Rebuilt with | Result |
  |---|---|---|
  | 0.19.0 | 0.19.0 | refused with `-32003` (the bug, reproduced) |
  | 0.19.0 | 0.19.1 | accepted; stamp written; reload clean |
  | 0.19.1 | 0.19.1 | stamp restored by the rebuild; accepted; reload clean |

- **A genuine flip is still refused:** removing identity from Person on the hydrated group, with
  the stamp present.
- **Upgrade and downgrade:** 0.19.0 → 0.19.1 reads back identically; 0.19.0 reopens the workspace
  and rebuilds from 0.19.1's WAL.
