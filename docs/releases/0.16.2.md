# 0.16.2 — 2026-09-30 (full release notes)

This release adds one community-requested ontology feature: **assert-only types**. It's
**additive**: there's no storage migration, no schema change, and nothing to do when upgrading
from 0.16.x. An ontology that doesn't use the new flag behaves exactly as before.

## Upgrading

- **From 0.16.0 or 0.16.1:** drop-in, with no migration.
- **From 0.15.x or earlier:** read the 0.16.0 notes first. That release migrates entities on first
  start and does not support downgrade.

## Added

- **`extract: false` on ontology entity and relation types**
  ([ADR-0637](../adr/0637-extract-false-assert-only-types.md), #637, requested in #636).
  - **The problem it solves:** hosts often add a small base ontology of structural types they
    assert themselves from metadata, such as a provenance `Source` with `DERIVED_FROM`. Declaring
    those types also offered them to the LLM extractor, which then created them from prose. With
    `identity: true` (0.16.0), those fuzzy extractions landed in an identity-bearing kind and
    collided with the host's own keyed assertions.
  - **What it does:** a type marked `extract: false` is:
    - **left out** of the entity and edge extraction prompts;
    - **never accepted from the extractor.** A stray extracted label is reclassified to
      `Unclassified` for entities or `UNCLASSIFIED` for relations, with the original label kept,
      in both strict and open mode. It **never** gets the type's identity `kind`.
    - **Otherwise fully declared.** It still counts for `knowledge_assert_entity` /
      `knowledge_assert_relationship` typing and `kind`, the identity set and its `-32003` guard,
      `parent` ancestry and label stamping, and drift.
    - **Never a retyping target.** `knowledge_reprocess_entity_types` and relation
      canonicalization never retype extracted data into an `extract: false` type, and never remap
      asserted edges of one.
  - **Default and compatibility:** the flag defaults to `true`. An ontology without it renders
    identical extraction prompts and has an identical content hash, so upgrading causes no drift.
    Flipping the flag on a type changes the hash and shows as drift. It doesn't change the identity
    set, so `knowledge_reload_ontology` (0.16.1) accepts the change instead of refusing it.
  - **An edge case handled:** a strict ontology whose every type is `extract: false` falls back to
    the default extraction vocabulary and no longer reclassifies ordinary labels. The eval harness
    handles the same case without reporting false vocabulary violations.
  - See [docs/ontology.md](../ontology.md#assert-only-types-extract-false).

## What was verified

**macOS (Apple Silicon)**: the sidecar-gated battery at `bb4958c6`, run serially against a live
`bge-base-en-v1.5` sidecar (probed with a real embedding). No skips.

| | 0.16.2 | 0.16.1 |
|---|---|---|
| cold cache | 136.654s, 194 batch calls | 144.865s |
| warm cache | 48.312s, 0 real calls | 50.684s |
| no-recompute baseline | 47.485s, 262.9 mutations/s | 49.897s |
| recompute drift, min cosine | 0.999950 / 0.999989 / 0.999990 | identical |

The drift is the same environmental figure recorded since 0.16.0. It isn't caused by lcg.

**CI** on the merged PR: the full Rust suite and the real-corpus end-to-end jobs on
Linux, the Windows named-pipe end-to-end job with index creation and queries, and release-artifact
builds for all four targets with the pinned extension-hash check.

**Acceptance** is covered by a dedicated `extract_false` suite:
- both prompts omit `extract: false` types;
- a canned extraction that emits `Source` doesn't produce a `Source`-kind entity;
- asserting `Source` and `DERIVED_FROM` still works and is identity-scoped;
- reprocess and canonicalize never retype into those types;
- ontologies without the flag produce byte-identical prompts and hashes;
- flipping the flag is reported as drift and a reload accepts it.
