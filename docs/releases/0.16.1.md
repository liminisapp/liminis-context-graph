# 0.16.1 — 2026-09-30 (full release notes)

Three community-requested operational improvements for hosts that run lcg as a long-lived,
multi-tenant daemon. All are **additive**: there is no storage migration, no schema change, and
nothing to do on upgrade from 0.16.0.

## Upgrading

- **From 0.16.0:** drop-in, with no migration.
- **From 0.15.x or earlier:** read the 0.16.0 notes first. That release migrates entities on first
  start and does not support downgrade.
- **One behaviour change for supervisors:** during a long write (for example a WAL rebuild),
  `knowledge_health_check` now answers `ok: true, healthy: false, state: "busy"` instead of not
  answering at all. A caller that treats any `ok: true` as "ready" should gate on `healthy`.

## Added

- **`knowledge_reload_ontology { group_id }`** ([ADR-0627](../adr/0627-per-group-ontology-reload.md),
  #627, requested in #611). This is an admin-scope method and MCP tool.
  - **What it does:** reloads one group's ontology without restarting the service, so one team can
    change its vocabulary while every other group keeps serving. Afterwards
    `knowledge_canonicalize_relations` and `knowledge_reprocess_entity_types` run against the new
    ontology instead of failing with `-32000` or using the stale cached one.
  - **Identity guard:** a reload that would reinterpret existing entities (adding or removing
    `identity: true` on a type the group already holds, as in ADR-0616) is refused. The refusal is
    reported in the response and enforced as `-32003` on writes, exactly as a restart would enforce
    it. Restoring the previous file and reloading again clears it.
  - **Response and no-op:** it returns `{group_id, previous_hash, new_hash, changed, drift,
    identity_refusal}`. Reloading an unchanged file does nothing.
- **Relevance evidence and a similarity floor for `knowledge_find_entities` and
  `knowledge_find_relationships`** ([ADR-0629](../adr/0629-find-search-evidence-and-similarity-floor.md),
  #629, requested in #613).
  - **Why:** both tools used to return a full top-k with no scores, so a nonsense query filled every
    slot.
  - **Evidence:** each result now carries a `search` object with `rrf_score`, `text_match`,
    `bm25_score`, and the cosine similarity for each vector path (`name_similarity` and
    `summary_similarity` for entities, `fact_similarity` for relationships). A path that didn't
    retrieve the item reports `null`.
  - **Floor:** the optional `min_similarity` (0–1, clamped, no default) removes distant vector
    candidates before fusion. Full-text hits stay eligible regardless of the floor. It works with
    the `kind` filter from 0.16.0.
  - **Default behaviour is unchanged:** without `min_similarity`, results and ordering are identical
    to 0.16.0, and regression tests check this.

## Fixed

- **`knowledge_health_check` no longer blocks behind the write lock**
  ([ADR-0628](../adr/0628-health-check-busy-state.md), #628, reported in #612).
  - **The problem:** a health check issued during a WAL rebuild used to queue until the rebuild
    finished. Supervisors with short timeouts therefore saw a busy daemon as dead and restarted it
    mid-rebuild, and the rebuild could then never complete.
  - **Now:** it answers immediately with `state: "busy"`, without touching the database, and
    includes an `activity`:
    - `rebuilding`, with the job's `job_id` and `progress`;
    - or `writing`.
  - **Readiness:** `healthy` is `false` while busy, because the daemon is alive but not ready. This
    departs from the example in #612 on purpose: existing readiness checks gate on `healthy`, and
    the Liminis app's startup wait already retries on `healthy: false`.
- **Episode straddling a reload:** an episode whose extraction was in flight when its group's
  ontology was reloaded no longer overwrites the reloaded ontology's drift record. That episode's
  own entities stay typed by the ontology they were extracted under.
- **Docs site:** it now republishes automatically when a release is published (#626). Releases
  created with the workflow's `GITHUB_TOKEN` never triggered the `release: published` event, so
  0.14.0 through 0.15.0 were never published to the site, and 0.16.0 was published by hand.
  `release.yml` now dispatches the docs workflow itself.

## What was verified

**macOS (Apple Silicon)**: the sidecar-gated battery at `8bf285cc`, run serially against a live
`bge-base-en-v1.5` sidecar (probed with a real embedding). No skips.

| | 0.16.1 | 0.16.0 |
|---|---|---|
| cold cache | 144.865s, 194 batch calls | 143.068s |
| warm cache | 50.684s, 0 real calls | 49.133s |
| no-recompute baseline | 49.897s, 250.2 mutations/s | 48.3–55.5s |
| recompute drift, min cosine | 0.999950 / 0.999989 / 0.999990 | identical |

The recompute drift is the same environmental figure recorded in the 0.16.0 notes: identical at
the v0.15.0 tag on the same machine and sidecar, so it is not caused by lcg.

**CI**, on every merged PR:
- the full Rust suite on Linux, including all real-corpus end-to-end jobs;
- the Windows named-pipe end-to-end job, which also creates and queries vector and full-text
  indexes;
- release-artifact builds for all four targets, with the pinned extension-hash check.

Each change's acceptance criteria were covered by dedicated tests:
- 12 reload scenarios, including the identity refusal and an episode straddling a reload;
- the busy, rebuilding, writing, contended and poisoned health-check paths;
- 10 search-evidence tests, including unchanged ordering with no floor and the `kind` path.
