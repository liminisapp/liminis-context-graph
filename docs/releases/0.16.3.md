# 0.16.3 — 2026-10-01 (full release notes)

A fix for a **0.15 → 0.16 upgrade regression**: on a database built by lcg 0.15.x or earlier,
deleting or updating any row containing a non-ASCII character failed, and non-ASCII full-text
search silently returned nothing. There is no storage migration and no data change; only derived
full-text (FTS) indexes are rebuilt.

## Upgrading

- **From 0.15.x or earlier:** nothing to do. **The first start of 0.16.3 rebuilds the three FTS
  indexes once.** It is logged on stderr, runs before the service handles any request, and its time
  is proportional to corpus size, so on a large notebook the first start is slower than usual.
  Later starts don't rebuild, and neither do databases created by 0.16.3.
- **From 0.16.0, 0.16.1 or 0.16.2:** the same one-time rebuild happens on first start of 0.16.3
  if the database was last built by 0.15.x or earlier.
- **Staying pinned to 0.16.0–0.16.2:** you don't get the automatic fix. Repair by hand:
  1. Drop **all three** indexes. Dropping only the index named in the error just moves the failure
     to the next one.
     ```cypher
     CALL DROP_FTS_INDEX('Entity', 'node_name_and_summary')
     CALL DROP_FTS_INDEX('RelatesToNode_', 'edge_name_and_fact')
     CALL DROP_FTS_INDEX('Episodic', 'episode_content')
     ```
     (via `knowledge_query_cypher`, or the `cypher` MCP scope).
  2. Call `knowledge_build_indices` to recreate them.

  After that, replays complete and non-ASCII searches return results again.

## Fixed

- **Non-ASCII FTS terms undeletable and unsearchable on 0.15-built databases**
  ([ADR-0649](../adr/0649-fts-index-rebuild-on-lbug-version-change.md), #649, fixes #646).
  - **Cause:** lbug 0.20 → 0.21 stores non-ASCII FTS terms differently without bumping the storage
    version (47 for both), so nothing detected the stale indexes. Reported upstream as
    LadybugDB/ladybug#1092.
  - **Symptoms:** `knowledge_delete_episode`, re-asserting an entity, edge `SET name/fact` and
    `knowledge_rebuild_from_wal {from_seq: 0, force_clear: true}` failed with
    `FTS index '<idx>' is inconsistent: term '<t>' is missing during delete`; `QUERY_FTS_INDEX` for
    `→`, `Zürich` or `東京` returned zero rows with no error. ASCII was unaffected.
  - **Fix:**
    - The service records the lbug version that built the FTS indexes (`SchemaState` key
      `fts_built_by_lbug`) and rebuilds all three when it is missing or differs. This also means
      any future lbug bump rebuilds once.
    - If a write still hits `FTS index … is inconsistent`, all three indexes are rebuilt and that
      statement retried once. The count and time of such repairs are in `knowledge_status`
      (`fts_repair_count`, `fts_last_repair_unix_ms`; `null` while degraded). The retry does not
      happen inside an explicit transaction.
    - `knowledge_rebuild_from_wal` with `force_clear` drops the FTS indexes before purging, so a
      full replay never deletes through a live index.
