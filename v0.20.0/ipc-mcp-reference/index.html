IPC & MCP Reference

liminis-context-graph serves the same graph over two transport surfaces, both routed through the same core dispatch in crates/core/src/handlers.rs — no graph logic is duplicated between them:

  • JSON-RPC 2.0 over a local socket (default). Newline-delimited requests/responses over .lcg/service.sock — a Unix domain socket on macOS/Linux, a named pipe on Windows (see Windows: named pipe).
  • Model Context Protocol over stdin/stdout (--mcp-stdio). Any MCP client — Claude Code, Claude Desktop, other agents — can query and mutate the graph directly.

Windows: named pipe

Section titled “Windows: named pipe”

On Windows the service serves the identical protocol over a named pipe, because AF_UNIX is not usable from Rust’s tokio, Node or CPython there (issue #581). LCG_SOCKET_PATH keeps its meaning — it still names the workspace’s endpoint — and maps to a pipe:

  • Discovery. At bind the service writes the pipe name to .lcg/service.endpoint (the socket path with its extension replaced). Clients should read that file.
  • Name. \\.\pipe\lcg-<16 hex digits>: FNV-1a 64-bit over the UTF-8 bytes of the absolute socket path, lower-cased, with / replaced by \. Stable per workspace, so a client that cannot read the file can compute it. A LCG_SOCKET_PATH (or --connect) that is already a \\.\pipe\… name is used as-is.
  • Access. Only the user the service runs as (and SYSTEM) can connect; remote clients are refused, and a second process cannot bind the same pipe name.
  • Signals. Closing the console, logoff/shutdown, Ctrl+Break and Ctrl+C all trigger the same graceful shutdown SIGTERM/SIGINT do on Unix.

A pipe opens like a file, so a client needs no socket library:

In Node, net.createConnection(endpoint) accepts the pipe name directly.

Connections, concurrency and timeouts (issue #861)

Section titled “Connections, concurrency and timeouts (issue #861)”

One request at a time per connection. The service handles the requests on a single connection strictly in order: it reads one line, runs it to completion, writes the response, then reads the next. Pipelined requests wait unserved until the current one finishes (while a knowledge_process_chunk or knowledge_process_document is running, the service watches the socket and holds up to 8 pipelined lines in memory; it stops reading beyond that). So a knowledge_find_entities sent on the same connection as a slow knowledge_process_chunk waits behind the ingest; a read is only fast on a connection that is not busy ingesting. Connections do not block one another (reads never take the write lock, and each connection has its own task), so:

  • Open several connections to run ingest in parallel, or to keep reads responsive while an ingest is running: one connection per concurrent request, or a small pool. Requests that write still serialise on the per-group write lock inside the service; parallelism pays off in the embed/extract phase, which is the slow one.
  • Correlate by connection, not by id: _progress_token frames (below) do not echo the token, which is safe because a connection never has two requests in flight.

Disconnect cancels an in-flight ingest (feature cancel_on_disconnect). While a knowledge_process_chunk or knowledge_process_document request is running, the service watches its connection. If the client disconnects (the socket closes, errors, or a progress write fails), the request is cancelled at its next cancellation point before commit and the service logs client disconnected; cancelling in-flight <method> (cause=client_disconnect). A cancelled knowledge_process_chunk writes no episode, entity, edge or WAL record; a cancelled knowledge_process_document leaves the units it had already committed in place (see below). Either way the request releases its locks and leaves the service healthy. Once the commit has started it finishes, whether or not the client is still there: the commit is never interrupted. This applies to streaming (_progress_token) and plain requests alike, and to requests queued behind another on the same connection (they do not start). Other methods are not cancelled on disconnect and run to completion as before.

  • An in-flight LLM call is abandoned at the next cancellation point, not aborted instantly; a provider may still bill for a request it had already received.
  • knowledge_process_document commits per extraction unit’s episode as it goes; units that were already written stay written, and the revision itself is only committed in its final step, so a cancelled document ingest retires nothing. Resubmit the document to finish it.
  • A half-close is supported. A client that sends its request and then half-closes its write side (shutdown(SHUT_WR), socat, nc -N, printf '{...}\n' | nc -U ...) can still receive, so its process_chunk / process_document request runs to completion and is answered, and the connection then closes. The service cancels only when the peer has fully closed (it can no longer receive: Python’s socket.close() after a timeout is the case this exists for), and it keeps checking while the request runs, so a client that half-closes and later closes fully is cancelled then. On a Windows named pipe there is no half-close: EOF means the client closed. A socket read error while the request runs is treated as a disconnect. (A pipelined line that is not valid UTF-8 is not: the in-flight request finishes and is answered, then the connection closes.)
  • Keep reading while a request runs. Progress and heartbeat frames are written while the request executes, and a frame that cannot be written within 5 s (a client that has stopped reading and let its socket buffer fill) is treated as a disconnect, so the request is cancelled before commit. A commit that has already started still finishes.

Choosing a timeout and retrying. Ingest latency is dominated by the embedder and the LLM, so set the client timeout to the slowest chunk you expect (or stream with _progress_token and treat silence between frames as the timeout). When a call times out, close the connection and retry on a new one:

  • If the timeout fired during embed or extract, the disconnect cancelled the original, so the retry extracts the chunk once, not twice.
  • If it fired during commit, the original finishes anyway and may have succeeded. “During commit” starts when the commit frame is sent (the group write lock is held). A request that is still waiting for the lock behind another writer has not committed and is cancelled like one in embed or extract. The retry is still safe: an identical resubmission is a no-op (unchanged_noop, issue #858) that returns the existing episode, and a changed one supersedes it as usual.

knowledge_status episode breakdown (issue #884, ADR-0884). knowledge_status accepts an optional boolean include_episode_breakdown (default false; only a literal true enables it). The feature is advertised as status_episode_breakdown by knowledge_capabilities. It is opt-in because it scans every episode, MENTIONS edge and edge while holding the read lock, which blocks writers for its duration; a call without it runs no extra query and is unchanged. With it, the response gains:

  • live / superseded / pending partition a group’s episodes. Liveness is the belief/search predicate (EpisodeSupersession::live_at) evaluated at as_of_us; pending is an uncommitted document revision (ADR-0785), never counted as live or superseded. Unattributed episodes are never superseded, so they are live. A future-dated supersession counts as live until its instant.
  • only_superseded_entities: entities with at least one MENTIONS from a superseded episode and none from a live one (pending mentions are neutral). only_superseded_edges: edges whose belief state is superseded (every surviving producing episode superseded), counted by producer and not by fact text. Each is attributed to the entity’s / edge’s own group_id and counted once.
  • Every field is present even at 0; groups are sorted by group_id; the superseded : live ratio is superseded / live, computed by the client.
  • When the database is not open, not queryable or the scan fails, episode_breakdown is null and episode_breakdown_unavailable is a reason string; the rest of the status response is unaffected.
  • A workspace rebuilt from knowledge_dump_wal has no native MENTIONS (ADR-0828 finding F1), so only_superseded_entities reads 0 there.

Every long-running method above (the six WAL/recovery/reclassification operations most likely to run for a while) accepts a _progress_token and streams {"type":"progress",...} frames before the terminal result — see Progress notifications below.

Readiness

Section titled “Readiness”

A successful connection to .lcg/service.sock is not evidence the service is ready. The socket is bound before the database opens — deliberately, so health_check and recovery IPC stay reachable during degraded-mode recovery (ADR-0009) — and issue #378’s WAL-root migration also runs in that same pre-open window, after the bind. (Legacy .graphiti/→.lcg/ workspace migration runs earlier still, before the socket is even bound.) The process’s own accept loop only starts once startup work has fully resolved, so a request sent immediately after connect() queues in the kernel rather than racing the migration with stale state — the real risk is a client that treats connect() succeeding as readiness by itself and acts on that assumption (e.g. inspecting on-disk state) without waiting for a health_check round-trip.

The correct readiness signal is a health_check round-trip reporting "healthy": handle_health_check only returns healthy once Db::open() has succeeded, which is after migration has completed. Poll health_check until it reports healthy (or knowledge_status until connected and queryable are both true and initializing is false — knowledge_status has no healthy field of its own) before sending real work; see Operations: Self-healing and degraded mode for the full rationale. A degraded response after startup has otherwise settled is a legitimate outcome (e.g. unrecovered corruption) — not something to retry indefinitely.

A busy response (see Health check contract) is not a write readiness signal: it means the service is alive but a write is holding or waiting for the write lock — most importantly a long knowledge_rebuild_from_wal. Pollers that need to send writes keep waiting on busy (gate on result.healthy == true) and must not treat it as failure. A client that only reads gates on result.ready_for_reads == true instead, which stays true while busy.

Section titled “Capabilities”

knowledge_capabilities (read scope; IPC and MCP; ADR-0854, #854) lets a client ask the running service what it is and what it supports. It takes no parameters (unknown ones are ignored), reads no database and takes no lock, so it answers in degraded mode, during a rebuild and under any --writable-groups policy.

Health check contract

Section titled “Health check contract”

health_check never waits on the write lock, so it answers promptly even during a long WAL rebuild (ADR-0628, #628). The response’s state is one of:

The three fields carry three different facts (ADR-0855):

  • ok — liveness: the process is alive and answered. Gate on it for restart decisions.
  • healthy — idle and ready for writes: DB loaded and no write pending or in progress. Gate on it before sending writes, or to wait for a rebuild to finish. It is not a liveness signal.
  • ready_for_reads — reads are served now: the database is loaded. true while busy, false only when degraded. Gate on it before sending reads. It means “loaded”, not “every read will succeed”: indexes may still be rebuilding, and a read racing a mid-clear rebuild can fail.

Since ADR-0628 (0.16 era) healthy stopped meaning liveness. Raw-socket clients written before then should use ok for liveness and ready_for_reads for read availability.

busy carries an activity field. While a knowledge_rebuild_from_wal job is running:

progress uses the same values as knowledge_rebuild_status. For any other writer the response is {"ok": true, "healthy": false, "state": "busy", "ready_for_reads": true, "activity": "writing"} with no job_id or progress. The busy path never connects to or queries the database.

Every health_check response, in every state, also carries server_version and protocol_version (issue #854), with the same values as knowledge_capabilities. They are additive; no existing field changed.

Notes:

  • busy means “a write is pending or in progress”: a writer queued behind readers also makes the lock unavailable, so an otherwise idle service can briefly report busy.
  • Batched passes (ADR-0030) release the lock between batches, so during one the state alternates between busy and healthy.
  • A streaming rebuild (_progress_token) is not registered as a job: it reports activity: "writing" without progress.
  • Startup work (legacy and WAL-root migration, startup recovery) runs before the accept loop, so a probe sent then queues in the kernel and gets no answer until startup finishes.
  • healthy can be reported in the short window after a rebuild job is registered but before it takes the write lock.
  • busy has healthy: false on purpose: existing pollers that gate on healthy keep waiting. A liveness probe that only needs “is the process alive” should accept ok: true, and a read-only client should gate on ready_for_reads: true.

Response contract (JSON Schemas, issue #852)

Section titled “Response contract (JSON Schemas, issue #852)”

Method names are discoverable from the dispatch table; method result shapes used to be known only from the code that built them, so consumers guessed key names. One such guess shipped a bug: a notebook-health view read knowledge_lint details by the wrong keys (details.derived_document, the causes map and finding.reason were each missed). lcg now publishes a JSON Schema (draft-07) for the result of each of these methods, and its own test suite fails when a real response stops validating:

health_check, knowledge_status (including wal and wal_groups), knowledge_search_passages, knowledge_find_entities, knowledge_find_relationships, knowledge_process_chunk and knowledge_lint (with a per-category details shape, discriminated by category, and by reason where one category has two shapes).

The schemas live in contract/ as <method>.schema.json and are attached to every GitHub release, next to the binaries, together with a contract-manifest.json that names the lcg version they belong to:

Fetch them at the version you pin, exactly as you fetch the binary:

Validate a recorded response offline with any draft-07 validator (no engine, no source checkout). The schemas are self-contained: the only $refs are internal (#/definitions/...).

Generate types from them with a stock generator, for example npx json-schema-to-typescript knowledge_lint.schema.json > knowledge-lint.d.ts or quicktype -s schema knowledge_lint.schema.json -o knowledge_lint.rs.

What the schemas say, and do not say:

  • They describe a method’s successful result only: not JSON-RPC error objects, _progress_token progress lines, or the MCP envelope (the MCP tools return the same result inside their own wrapper).
  • A field that is always present is required. A field that is sometimes omitted is optional (index_created_at on an empty graph, source_files without include_episodes, belief without believed_only / as_of, warning on a normal process_chunk, wal.scope without a WAL root). A field that is always present but may be null is required and nullable (derived_document, valid_at, embedding_cosine, next_cursor).
  • Alternatives are modelled as oneOf / anyOf: health_check by state, knowledge_status as degraded / queryable / not queryable, knowledge_lint findings by category.
  • Free-form members stay loose on purpose (attributes is a JSON string, rerank / expansion are objects, causes is a map from cause to count), so they can grow without a breaking change.
  • Additional properties are allowed. Validate with a stock validator and an unknown extra field still passes; do not turn on “additional properties: false” yourself unless you want every additive release to break you.

Compatibility policy. The schemas describe what lcg emits, so “breaking” is judged from the reader’s side. Removing or renaming a field, widening a type (string to string|null, integer to number), making an always-present field optional, or adding an alternative to a oneOf / anyOf is a breaking change to a published schema and is announced in the release notes as such: a consumer that reads the old shape can crash or mis-parse the new one. Adding an optional field, narrowing a type (string|null to string) or making an optional field always present is not breaking: every response that validated against the new schema still validates for readers of the old one. Every release that changes a schema lists the change in the CHANGELOG. Contributors: see CONTRIBUTING.md.

MCP-over-stdio transport

Section titled “MCP-over-stdio transport”

liminis-context-graph --mcp-stdio starts a native Model Context Protocol server over stdin/stdout, using the official Rust SDK (rmcp). Any MCP client (Claude Code, Claude Desktop, other agents) can query and mutate the knowledge graph directly — no Electron app, no Node, no custom JSON-RPC client required. DB-access modes

Section titled “DB-access modes”
  • Standalone (default, no --connect): the MCP process opens the .lcg database directly, reusing the same startup and self-recovery path as the socket service (ADR 0009). Zero-dependency — works with no other process running.
  • Attached (--connect <socket-path>): the MCP process never opens the database; it forwards each call over the given socket to a service that already has it open. Use this to add MCP access to a workspace where another socket-service instance is already running, without contending for lbug’s single-writer lock.
    • Lazy connect by default (issue #575). The socket is not dialled during startup — initialize and tools/list succeed immediately, serving the tool set from the compiled-in registry, regardless of whether the daemon at --connect’s path is up. The first tools/call triggers a dial; if it fails, that call returns a tool result with isError: true naming the socket path and suggesting you start the daemon, but the MCP process itself stays up and the client’s session is unaffected — no protocol error, no exit. This avoids two failure modes a client can otherwise get stuck in for the client’s own cached-failure window: registering a native MCP server before its daemon has started (first install, post-reboot), and the client caching a failed attach for several minutes even after the daemon comes up. Pass --connect-eager to restore the pre-#575 behavior of dialling at startup and exiting immediately (before initialize) if the socket is unreachable — useful if you rely on that fail-fast behavior as an external health check (e.g. a supervisor that restarts the front until the daemon is ready).
    • Idle timeout. LCG_ATTACHED_CALL_TIMEOUT_MS (default 30s) is a per-read-line idle timeout, not a whole-call timeout: it resets on every line read off the socket, including {"type":"progress"} lines. A call that keeps emitting progress is never bounded by it, no matter how long the call runs in total — only genuine silence (no output at all for the full timeout window) trips it. If the remote stops responding mid-call (e.g. it crashes), the attached client fails that call with a clean timeout error rather than blocking forever. Keep it comfortably above 10 s: for knowledge_process_chunk and knowledge_process_document the attached client asks the remote for progress frames, and the remote’s only sign of life during a long silent stretch (e.g. LLM extraction) is a fixed 10 s heartbeat frame. A shorter timeout drops the connection mid-ingest, and the remote then cancels that ingest before commit (cancel-on-disconnect, ADR-0861) instead of finishing it in the background as it did before.
    • Reconnect and retry. If the connection to the remote breaks, the client transparently re-dials the same socket path rather than staying wedged. If the break is detected while writing the outgoing request — treated as safe to retry, since the write failing is the client’s best available signal that the request didn’t get through — the client automatically retries that request exactly once over the freshly-dialed connection. If the break is detected only after the request was fully written — while waiting for or reading the response — the call is not retried automatically, since the remote’s execution status is unknown and blind retry could double-apply a non-idempotent write (e.g. knowledge_add_episode); that call fails with a clear “connection lost mid-call” error, but the connection is marked dead so the next call reconnects fresh. If a reconnect attempt itself fails (no listener at that path), the call fails with a clear, descriptive error — never a hang — and a later call will try reconnecting again. See ADR-0040 for the full rationale.

Per-group write allow-list

Section titled “Per-group write allow-list”

--scope decides which tools a connection sees; it does not limit which groups a write-capable connection may change. When one daemon holds groups with different owners — say layer groups hydrated from streams other parties publish, beside the group the local user authors — start it with --writable-groups=<g1,g2,…> (or LCG_WRITABLE_GROUPS; see Configuration). The list is enforced inside the daemon, at the one point every request reaches, so it holds for the IPC socket (which has no scopes at all), standalone --mcp-stdio and attached --mcp-stdio --connect alike. It is one list per daemon: there is no per-client identity, and per-group read restriction is out of scope. Unset, nothing changes.

The check is made against the groups a call actually changes, not every group it mentions:

  • An omitted (or null/non-string) group_id resolves to the default group, liminis — the default group must be listed to stay writable. group_id: "" is a distinct group that can never be listed, so it is always refused. A write that falls back to the default group also carries an implicit default-group warning.
  • knowledge_add_cross_group_edge is checked against the edge’s own group_id. The source_group_id of a foreign endpoint is a read-only pointer and is not checked: with --writable-groups=a, {group_id: "a", target: {source_group_id: "b", …}} succeeds and {group_id: "b", …} is refused.
  • A call that changes several groups needs every one listed, otherwise it is refused whole and nothing is written.
  • The check runs before any handler work, so a refused call does no embedding or extraction and writes no database row and no WAL event. Reads of any group, and read-only tools, are never affected. dry_run gets no special case: a dry run on a non-listed group is refused too.
  • Daemon-internal work — startup WAL replay, auto-heal index builds, degraded-mode recovery — is not a client request and is not blocked.

Error shape. A refused call fails with JSON-RPC code -32004 and structured data; over MCP the same object arrives as the tool error’s data:

knowledge_close in attached mode is a footgun without --allow-remote-close. In attached mode, calling it would shut down the running remote service. Recovery and export live under admin. knowledge_rebuild_from_wal (rebuild one group’s data from its own WAL directory — group_id, default "liminis"), knowledge_dump_wal (snapshot/export the graph into a fresh compacted WAL directory), knowledge_strip_wal_embeddings (rewrite existing WAL files in place to remove the embedding-vector params fields a pre-0.14 WAL still carries — see Operations), knowledge_wal_mark_create / _list / _delete (name a retained WAL position within one group’s stream, without a full snapshot — each also takes group_id, default "liminis", and _list reports only that one group’s marks, never an aggregate across groups), and knowledge_recover / knowledge_recover_full are all admin-scope tools — an attached client only sees them when launched with --scope=admin (or all). If a mutation goes wrong, this is the recovery path. See Operations for the recovery model in full. Note the WAL replays forward-only, so take periodic knowledge_dump_wal snapshots, or a lighter-weight knowledge_wal_mark_create named position, if you want restore points before large or destructive operations — a mark does not survive knowledge_dump_wal, since dump_wal renumbers sequence numbers and a copied mark’s seq would be meaningless against the new numbering.

knowledge_rebuild_from_wal refuses to run against a non-empty group, unless you ask it not to. Since issue #378, one instance holds an independent WAL directory and applied position per group_id; knowledge_rebuild_from_wal {group_id, ...} targets exactly one of them and never disturbs another group’s data or position. A from_seq: 0 (default) full rebuild against a group that already contains data fails fast with an explicit error rather than silently emitting a duplicate-primary-key failure for every existing Entity/Episodic/RelatesToNode_ row in that group — the native write path uses CREATE, not MERGE, for those labels. Pass force_clear: true to have the call clear that group’s data automatically before replaying (the same group-scoped purge knowledge_delete_by_group uses — this does not delete or reopen the database file, unlike the pre-378 whole-database force_clear behavior), or clear it yourself first with knowledge_delete_by_group {group_ids: [group_id]}. dry_run: true always fails fast on a non-empty group regardless of force_clear, since a dry run must never mutate the database — this lets a preview surface the problem before you commit to a real rebuild. None of this applies to an incremental from_seq > 0 resume, which intentionally targets a group that already has state.

Rebuild order across groups does not matter, and every rebuild reports cross_group_rebind (issue #741). A cross-group edge lives in the WAL of the group that owns it (say layer) but points at an entity in another group (say up). Rebuilding layer before up used to leave that edge permanently missing: its hop writes found no endpoint and did nothing, yet the pointer kept the bound state cached in its WAL attributes. Now, after every successful rebuild — full or incremental, reset-triggered or not, foreground or background job — the service (1) demotes any bound pointer on an edge owned by the rebuilt group whose hop was not actually created to unbound (local derived state, not written to any WAL), so knowledge_status.cross_group_pointers reports the gap instead of claiming bound, and (2) runs the staleness-gated rebind_pointers for pointers pointing into the rebuilt group, flushing each resulting mutation to the group that owns the edge. Rebuilding layer then up therefore ends in the same graph as up then layer, with no manual knowledge_rebind_pointers call. The result’s cross_group_rebind carries the same counts knowledge_rebind_pointers reports (zeros when nothing needed attention); it is null only on a dry_run, or if the repair itself errored (logged, and the rebuild still succeeds).

to_seq bounds replay from the other end: from_seq <= seq <= to_seq. Pass an inclusive upper bound to exclude a mutation (and everything after it) from a rebuild — e.g. a WAL-recorded mutation that corrupted the graph. Omit to_seq for today’s unbounded behavior (replay to the end of the WAL); it must not be less than from_seq, or the call is rejected before any WAL line is read or the database is touched. A bounded rebuild is not durable: WAL entries past to_seq stay on disk, unapplied, not truncated or archived — a later unbounded rebuild, or a from_seq resume that covers the excluded range, reapplies them, including a previously-excluded bad mutation. to_seq bounds an endpoint; it does not add reverse/undo semantics to the forward-only replay noted above.

Search evidence and the similarity floor (find_entities, find_relationships)

Section titled “Search evidence and the similarity floor (find_entities, find_relationships)”

Hybrid search fuses its candidate lists with Reciprocal Rank Fusion, which is rank-only: the top hit of a gibberish query scores almost the same as the top hit of a perfect one, and every query fills its top-k. To let a caller tell a real match from filler, each result of knowledge_find_entities and knowledge_find_relationships carries an additive search object (issue #629):

FieldOnMeaning

fact_similarityrelationshipscosine similarity (1 - distance) on the fact-vector path, or null

A field is null when that retrieval path did not return the item (text_match is then false). Values are raw and unnormalised; cosine similarity can be negative.

Both tools also accept an optional min_similarity (number). Vector candidates whose cosine similarity is below it are dropped before fusion, independently per vector path, so they never affect the ranking and are not reported for an item they did not qualify for. Full-text matches always stay eligible, so an exact-name query still returns its match while a gibberish query returns nothing. With the kind filter the floor applies on top of the kind path’s bounded nearest-neighbour probe.

How it differs from knowledge_search_passages’ min_score: the value is clamped to 0–1 the same way (a non-number is an invalid-params error), but min_similarity has no default — omitted or null means no floor and results are identical to before, apart from the added search object — and it acts before fusion and per path rather than as a post-filter on a single list.

Caps differ on purpose. knowledge_walk include_provenance returns at most 20 episodes per edge, in the edge’s recorded order, and always emits episodes_truncated (false when nothing was cut). find_entities returns at most 50 per entity, newest first, and emits episodes_truncated only when true. The units (edge vs. entity) and orderings differ, and an entity is typically mentioned by far more episodes than an edge has producers, so a single value would change shipped behaviour for one of them. Neither cap is request-tunable.

support and corroboration are unchanged by the flag and always count every live document (live in the same sense as above, so a pending revision does not count), not just the capped list; because support counts distinct documents and the list counts episodes, the two need not agree. get_entity_neighbors and get_entities_by_source do not filter superseded episodes (unchanged), so a find_entities hit’s episode_uuids equals the live subset of what get_entity_neighbors reports for the same entity.

Demoted passages are never dropped, and a demoted passage’s score is lowered to just below the passage it ranks under, so score can differ as well as the order. The workspace switch LCG_PASSAGE_BELIEF_AWARE (off, 0 or false disable; on, 1 or true enable; case-insensitive; anything else warns once on stderr and is ignored) sets the default for requests that omit belief_aware; an explicit request value always wins. With the switch off, hybrid gives weighted RRF without the rules, which is not the pre-#806 hybrid default (rules on). A non-boolean value is an invalid-params error. The removed top_rank_bonus parameter is ignored.
  • legs and lexical_score (issue #871, additive, hybrid mode only): each hybrid passage carries legs, which retrievers found it: dense (vector only), lexical (BM25 only) or both (at any rank in each list). dense and both hold exactly when similarity is present, so legs: "lexical" is the documented form of the older “similarity is absent” convention. In single-query hybrid lexical_score is the raw BM25 value when the lexical leg matched, and is omitted otherwise. With queries (variants), legs is the union over every query that retrieved the passage (dense through one query plus lexical through another is both); the vector side counts only candidates at or above min_score. lexical_score is not set with queries, because BM25 values from different queries are not comparable. If the full-text index is unavailable, hybrid falls back to vector-only and every hit is dense. Both fields are omitted in vector mode, so a vector-mode response is unchanged. A passage that reached the result only through an expand HyDE variant (a vector-only search) carries no legs; a passage keeps the legs of the first stage list that returned it. legs does not change ranking, scores or membership.
  • min_score (default LCG_SEARCH_MIN_SCORE, else 0.5; clamped 0–1) floors the vector retriever’s cosine similarity before fusion, as min_similarity does for entity search. A passage found only by the lexical retriever is not excluded by it, so hybrid mode can still return hits for an off-topic query (E15: 25 of 34 off-topic queries, against 13 in vector mode); use similarity and legs to tell them apart. This is a deliberate change in meaning from vector mode, where min_score filters the single list. When a request omits min_score (or sends null or a non-number), the operator-configured default applies; an explicit number, including 0.0, always wins. The effective default is reported by knowledge_status as search_min_score_default (additive, top-level, present in every status response shape). LCG_SEARCH_MIN_SCORE is validated once at startup: an empty, non-numeric, NaN or infinite value fails startup, and a finite out-of-range value is clamped to 0–1.
  • Fallbacks. A query with no lexical tokens (punctuation or stop words only), or no lexical match, returns the vector ranking. If the episode full-text index is missing or inconsistent (for example right after an lbug upgrade, before the index is rebuilt) hybrid search silently falls back to vector-only, and the service logs one line on stderr per process. Query text is reduced to alphanumeric tokens before it reaches the index, so no query can cause a parse error.
  • Filters. group_ids and origins (ADR-0752) are applied inside both the lexical and the vector query, so a passage excluded by either cannot enter through the other path.
  • Superseded episodes are still returned in both modes; belief_aware only moves them below their successor.

The full-text index also covers an episode’s source and source_description, so a query term in a file name or description can match. Which mode is better is measured per category on the retrieval eval (lcg-passages is the shipped default; lcg-passages-raw, lcg-passages-belief, lcg-passages-hybrid and lcg-passages-hybrid-belief are opt-in; see retrieval-quality-evaluation.md and ADR-0789).

knowledge_search_passages accepts three optional parameters. Omit them all and the call behaves exactly as before (same results, order, response shape and latency).

group_ids semantics: omitted vs. empty

Section titled “group_ids semantics: omitted vs. empty”

Every read tool that accepts group_ids treats an omitted or null group_ids uniformly as “all groups” (issue #413) — this holds across all 10 read tools: knowledge_find_entities, knowledge_find_relationships, knowledge_search_passages, knowledge_list_entities, knowledge_list_relationships, knowledge_get_entity_neighbors, knowledge_get_entities_by_source, knowledge_get_nodes_by_group, knowledge_get_edges_by_group, knowledge_get_episodes.

  • On knowledge_find_entities, knowledge_find_relationships, knowledge_get_nodes_by_group, and knowledge_get_edges_by_group, an explicit group_ids: [] is preserved as “exactly these groups” — i.e. zero rows, a filter matching nothing.

Time: event time vs ingest time (reference_time, ingested_at)

Section titled “Time: event time vs ingest time (reference_time, ingested_at)”

The graph keeps two separately stored clocks, so a record can be both old in the world and new to the graph — a months-old conversation ingested today, or a document chunk dated by its content rather than its file mtime.

ClockKeySet byMeaning

Upgrading an existing graph. Records written before this feature have no stored ingest time, so on the first start of an upgraded service each one is backfilled once, from the best available signal, in this order:

  1. the ts of the WAL entry that created the record (the first native CREATE line for its uuid under the group WAL directories) — a true ingest time;
  2. otherwise the record’s own created_at.

Belief time: corrections supersede, they do not delete (issue #705)

Section titled “Belief time: corrections supersede, they do not delete (issue #705)”

Alongside event time and ingest time (above) the graph records when it stopped believing something. Belief is transaction time; it is deliberately separate from validity (valid_at / invalid_at, the world’s clock). When a document is corrected, the removed fact was never true, so no supersession path ever writes valid_at or invalid_at: correction ends belief and leaves validity alone. See ADR-0705.

Corrections. Resubmitting a chunk_id with changed content to knowledge_process_chunk supersedes that chunk’s earlier live episodes in the same group_id, at the new episode’s ingest time, and only once the new ingest has fully succeeded. (A resubmission identical to the chunk’s live episode is a no-op instead; see Unchanged resubmission below.) A failed re-ingest leaves the old episode live. The result gains superseded_episode_uuids. Nothing is deleted. The same chunk_id in another group is never touched. knowledge_add_episode never supersedes (its name is free-form).

A revision supersedes only episodes knowledge_process_chunk can attribute to itself (issue #292, ADR-0292). Every episode records which write path produced it (Episodic.write_path: chunk for knowledge_process_chunk, episode for knowledge_add_episode and every other path; not returned by episode reads). A live same-named episode written by another path — for example a knowledge_add_episode whose name equals a chunk_id and whose source_description mirrors "{source_file}:{chunk_id}" — is left alone: it stays live, the call still succeeds as a normal ingest, a WARN naming its UUID and source_description is logged, and the result gains left_alone_episode_uuids (present only when non-empty). Legacy exposure: episodes written before the marker existed (NULL write_path) are still treated as the chunk’s own, so a pre-upgrade knowledge_add_episode row whose name equals a chunk_id can still be superseded; so can rows written by raw Cypher or other writers that leave the column NULL. The explicit by-name operations (knowledge_mark_chunk_removed, knowledge_delete_chunk_episode) are unchanged and still act on every same-named episode.

Unchanged resubmission (issue #858, unchanged_noop). Before any embedding or LLM call, knowledge_process_chunk looks up the live episode for (group_id, chunk_id). If it is identical to the request, the call writes nothing (no episode, entity, edge, supersession or WAL record), makes no embedder or extractor call, and returns {"success": true, "status": "unchanged", "chunk_id", "source_file", "episode_uuid": <existing>}. The ingest counters (nodes_extracted, superseded_episode_uuids, …) and any oversize warning are absent. Clients therefore no longer need their own content-hash ledgers for chunk re-syncs; a resubmission of everything on each sync costs nothing for the chunks that did not change. “Identical” means all of: chunk_text byte-for-byte (no trimming or line-ending folding, as in document mode); attributes equal as JSON (key order is irrelevant; missing means {}); origin (a legacy NULL is primary); source_file; doc_id (omitted means none); and reference_time, compared as an instant only when you pass one, so an omitted reference_time is never a difference. knowledge_process_chunk has no title parameter; source_file is its analogue. Any difference takes the supersede path above, unchanged. The shortcut does not apply when: supersede is false or same_revision_episode_uuids is given (a multi-unit revision); more than one live episode exists for the chunk_id; a live same-named episode was written by another path (knowledge_add_episode, document mode); the live episode has a pending (future-effective) document supersession; another knowledge_process_chunk or knowledge_mark_chunk_removed call for the same (group_id, chunk_id) is in flight (the ordinary path then orders the two, so a revert is never lost to an earlier edit still extracting); or no live episode exists (never ingested, superseded, or removed with knowledge_mark_chunk_removed). With a doc_id, the “one document has one origin” refusal applies to a no-op as to an ingest. A malformed request is rejected as always, never reported as unchanged. A change of extractor, model or ontology does not by itself re-extract an identical chunk: change the chunk or use the reprocess operations. Discover support with the unchanged_noop entry in knowledge_capabilities features. See ADR-0858.

To submit one chunk as several calls under one chunk_id, send supersede: false on every unit but the last, and pass the earlier units’ episode_uuids as same_revision_episode_uuids on the last: they stay live, the older episodes are superseded. Record a chunk as ingested only after the call succeeds — a client that records it first will never resend a failed correction.

Removal. knowledge_mark_chunk_removed {chunk_id, group_ids} records that a chunk no longer exists in its document: its live episodes are superseded with reason chunk_removed, and nothing is deleted. group_ids is required and non-empty, as for the delete. It returns {superseded_count, superseded_uuids, superseded_at} and is idempotent (a repeat reports 0). knowledge_delete_chunk_episode is unchanged and still destroys the episodes — use it only for explicit deletion. After a heading rename, ingest the renamed chunks first, then report the old ids removed; no fact present in both revisions is unbelieved at any instant.

Episode fields. Episodes gain superseded_at (null while live), superseded_by (the superseding episode, absent for chunk_removed), superseded_by_kind (episode) and supersession_reason (revision, chunk_removed). They appear on knowledge_get_episodes only when set and are accepted in its fields projection. get_episodes and search_passages still return superseded episodes by default.

Edge provenance. Each extracted edge records the episode that produced it. That is producing_episode_uuids in the belief object below — not the episode_uuids field on edge reads, which remains the either-endpoint inference (episodes mentioning the source or target) and is not evidence for that specific relationship. Edges with no producing episode carry a warrant (assertion for knowledge_assert_relationship, cross_group for knowledge_add_cross_group_edge) and are believed until retracted. An extracted edge’s valid_at_source is text when the extractor read the date from the text and reference_time when it defaulted. A direct assertion never overwrites an extracted edge’s fact; it creates a separate edge.

Reading belief. knowledge_find_relationships, knowledge_list_relationships, knowledge_get_entity_neighbors, knowledge_get_edges_by_group and knowledge_get_edges_by_uuids accept two optional parameters:

An edge is believed at t iff it was ingested at or before t and either carries a warrant or has at least one producing episode not superseded at or before t; a fact is therefore believed on [T1, T2) when ingested at T1 and superseded at T2, and stays believed while any one live source still states it. Capped reads (find_relationships, list_relationships, get_entity_neighbors) over-fetch and filter afterwards, so a filtered read can return fewer than num_results. They cannot be soundly backfilled (endpoint co-occurrence is not provenance, #404), so re-ingest legacy graphs. Separately, an edge whose producing episodes were all hard-deleted (knowledge_delete_episode, delete_by_source, delete_chunk_episode) is support_deleted and unbelieved at every time.

Document supersession: a new document replaces an old one (issue #707)

Section titled “Document supersession: a new document replaces an old one (issue #707)”

A document is sometimes replaced rather than edited — last year’s decision record superseded by a new one. That is a relation between two documents, and it differs from a correction in one way: the old decision was true until it was replaced. So the old facts stop being believed when the supersession is recorded, but are reported as in force until the date the new document took effect. The two axes stay separate. See ADR-0707.

Document identity. knowledge_process_chunk and knowledge_add_episode accept an optional doc_id: the stable identity of the logical document an episode came from, unique within its group_id (path-valued today). It is stored on the episode and returned by knowledge_get_episodes when set. It is never defaulted from source_file; an episode without one cannot take part in supersession, and omitting it changes nothing for existing callers. Graphs written before this release have none — re-ingest them.

Recording a supersession. knowledge_supersede_document {group_id, superseding_doc_id, superseded_doc_id, effective_at} (write scope) records “A supersedes B, effective effective_at” within one group. effective_at is an RFC 3339 timestamp with a timezone offset; it may be in the past (the retroactive case) or the future. Supersession is always explicit — the graph never infers it from topic similarity. The call:

  • writes one durable record per superseded document (a document has at most one superseding document; express successive replacement as a chain), and
  • supersedes B’s live episodes in that group with superseded_by_kind document, reason document_superseded, superseded_by A’s doc_id, at the service-clock recording instant — or at effective_at when that is later, so a decision with a future effective date stays believed and in force until then. A correction to B’s chunk before that date still ends belief at the correction.

It returns {success, already_recorded, group_id, superseding_doc_id, superseded_doc_id, effective_at, recorded_at, superseded_count, superseded_uuids}. Episodes of B ingested after the recording are not marked. Facts A also asserts stay believed through A’s own episode. A recorded supersession is not undone by later corrections to A.

It is rejected with no side effects (nothing written, WAL untouched) when A and B are the same document, when either is unknown in the group (no episode carries that doc_id), when the relation would form a cycle, when effective_at has no timezone, or when B is already superseded by a different document or effective date. Recording the identical relation again is a no-op (already_recorded: true). valid_at / invalid_at are never written. The record is in the WAL, is carried by dump compaction and checkpoint restore, and is removed by knowledge_delete_by_group.

Retiring a whole document (issue #859). knowledge_retire_document {group_id, doc_id, effective_at?, origin?} (write scope) says “this document no longer exists and nothing replaces it”. It supersedes every live episode of doc_id in group_id with reason document_removed (no superseding document, no durable record beyond the episodes). Nothing is deleted: the episodes and the edges they produced stay readable as history, knowledge_get_episodes lists them as superseded with reason document_removed, valid_at / invalid_at are never written, and belief-filtered reads stop returning facts supported only by them. A fact another live document also asserts stays believed through that document’s episode. effective_at is an RFC 3339 timestamp with a timezone offset and, as for knowledge_supersede_document, a future value keeps the facts believed and in force until then. Belief ends at max(recorded, effective_at), so a past effective_at behaves as “removed now” — without a record there is no retroactive “in force until” date. origin follows knowledge_mark_chunk_removed: a derived or answer retirement of a primary / external document is refused (origin_conflict:).

It returns {success, group_id, doc_id, superseded_count, superseded_uuids, superseded_at, effective_at, existing_retirement_at} (superseded_at is null when nothing was retired; effective_at echoes the request, or null). It is idempotent: a document with no live episode (already retired, or already superseded by another document) reports superseded_count: 0, changes nothing and writes nothing to the WAL; an earlier reason (chunk_removed, document_superseded) is never overwritten. On such a no-op existing_retirement_at carries the instant the document’s retirement is, or was scheduled to be, in effect (null otherwise), so a caller can see why nothing changed. A pending (future-dated) retirement can be moved earlier by retiring again with an earlier or omitted effective_at (belief then ends at the earlier instant); a later or equal one is a no-op, and nothing is ever moved later. A pending retirement does not shield the document from correction: re-ingesting a chunk or the document with new content supersedes the old episodes at the correction, exactly as for a pending document supersession, so the old and the corrected fact are never both believed. While a retire waits for the write lock it registers each of the document’s chunks as in flight (ADR-0858), so a concurrent identical knowledge_process_chunk cannot return unchanged and then have its episode retired underneath it. An unknown doc_id, an omitted group_id or an effective_at with no timezone is rejected with no side effects. Episodes ingested under the same doc_id after retirement are live as usual; there is no un-retire. The statement is uuid-keyed and fixed-valued, so WAL replay, dump compaction and checkpoint restore reproduce the retired state. See ADR-0859.

Reading it. On opted-in relationship reads (believed_only / as_of, above) the belief object gains:

FieldMeaning
in_forceWhether the fact was in force at the evaluated time, independently of believed. false once the superseding document’s effective date has been reached; true otherwise; null for a fact that was corrected (it was never true, so it makes no validity claim). An edge is in force while any producing episode is.
supersessionPresent once the fact’s producing episodes are all superseded; not time-dependent, so it classifies the fact from any read. cause is corrected (revision or chunk removal), document_superseded or document_removed. document_superseded also carries superseded_by_document, in_force_until (the effective date) and recorded_at; document_removed carries in_force_until (equal to superseded_at). superseded_at is when belief ended.

So between the effective date and the recording date an as-of read shows the old fact believed with in_force: false — the graph had not yet learned otherwise. Believed-only filtering is unchanged: it filters on belief, not on being in force, and there is no in-force-only filter yet.

Document mode: send the whole document, the server does the diff (issue #785)

Section titled “Document mode: send the whole document, the server does the diff (issue #785)”

knowledge_process_chunk makes you chunk a document yourself and tell the server what changed. A section you stop sending stays believed for ever, a heading rename orphans the chunk ids under it, every chunk you resend is re-extracted, and the extractor never sees the document’s title or the chunk’s heading path. knowledge_process_document removes all four costs: you send the whole document every time, and each call is a completeness claim — “this is document doc_id, in full”. See ADR-0785.

What the server does. It chunks the document by section (a heading plus its body up to the next heading of any level; text before the first heading is the preamble), splitting a section over LCG_DOCUMENT_CHUNK_MAX_CHARS into units. It then matches each section against the previous revision by the hash of its exact text: unchanged sections are skipped without extraction, so re-sending an identical document with the same metadata makes zero extraction calls and writes nothing (status: "unchanged"). A failed or cancelled call retires nothing: the previous revision stays fully believed, and its pending episodes are never believed (they read not_yet_ingested on belief reads). Retry with the same content and the diff runs against the last committed revision. The first document-mode ingest of a doc_id also supersedes that document’s live chunk-mode episodes. Concurrent calls for one document are serialized.

A client never needs its own chunker.

Episode origin: derived pages never corroborate themselves (issue #752)

Section titled “Episode origin: derived pages never corroborate themselves (issue #752)”

Systems that keep an “LLM wiki” write agent-authored summary, topic and synthesis pages back into the same notebook that holds the human’s notes. Indexed like any other note, such a page returns a fact the agent derived from note A as a second, apparently independent episode supporting it: support counts inflate, retrieval re-reads the agent’s own pages as evidence, and an error in a page propagates. Origin is the field that lets a client say which is which. See ADR-0752.

Vocabulary. knowledge_process_chunk and knowledge_add_episode accept an optional origin:

OriginMeaningCounts as corroboration
primarya human-written note (the default)yes
externalclipped or imported third-party materialyes
derivedan agent-written page or a consolidationno
answera filed Q&A responseno

The set is closed: any other value is rejected before anything is written (no episode, no WAL entry), with an error naming the allowed values. An episode with no origin is primary, so a client that never sends the field sees no change. The value is stored on the episode, written to the WAL, carried by dump compaction, and restored by knowledge_rebuild_from_wal. A WAL written before this feature replays with every episode primary. knowledge_get_episodes reports the origin of an episode that has one, and knowledge_search_passages reports it on every passage (primary when none was recorded).

Origin is a claim, not an authenticated attribute. LCG records and enforces what the caller declares; it does not detect a misdeclared origin.

Support, not a head count. Relationship and entity reads (knowledge_find_relationships, knowledge_find_entities) carry two additive fields:

support counts distinct source documents per origin: a doc_id is one document, however many chunks it was split into, and an episode with no doc_id counts as its own document. corroboration is primary + external; a derived or answer episode is a citation (it stays linked for provenance) and never adds to it. Counts are over episodes that are live now (the belief/search predicate: not superseded and not part of an uncommitted document revision), so a corrected episode stops contributing and a pending document revision does not count until it commits. On knowledge_find_relationships, when a belief query (as_of) is given, liveness (for both support and the origins filter) is evaluated at that as_of instant instead, so it agrees with the belief block. For a relationship, support is derived from the edge’s producing episodes and those of its same-fact siblings — edges with the same endpoints and relation name. (Ingest does not deduplicate edges, ADR-0705, so a page that restates a fact produces a second edge; the grouping happens at read time.) It never comes from the either-endpoint episode_uuids inference. Supply a doc_id for notes split into chunks: without one, each chunk counts as a separate document.

Filtering. knowledge_find_relationships, knowledge_find_entities and knowledge_search_passages accept origins, a non-empty array drawn from the vocabulary; an empty list or unknown value is rejected. A relationship matches if one of its own live producing episodes has a listed origin, an entity if one of its live mentioning episodes does, a passage if its episode does. Asserted facts, entities with no episode at all, and pre-#705 edges count as primary. Omitted, nothing changes. origins: ["primary", "external"] is what an agent should send while refreshing its own page. The filter runs after retrieval (relationships and entities over-fetch ×3; passages oversample the nearest-neighbour probe; in hybrid mode the filter also runs inside the full-text query), so a selective filter can return fewer than num_results.

Derived content never overrides primary content. A derived or answer submission:

  • never rewrites the summary of, or merges by embedding or LLM verdict into, an entity that has a live primary or external mention. An exact or identical-normalized name match still links the episode to the entity (provenance) but leaves its summary alone; an embedding or judged match keeps the extracted entity separate. An entity with no mentioning episode (knowledge_assert_entity) is not protected. The guard is best-effort against a concurrent primary ingest (the ADR-0029 trade-off).
  • never invalidates a fact: ingest does not do that for any origin, so a derived page saying “X uses MySQL” is stored as its own derived-only fact beside the primary “X uses Postgres”, which stays valid and believed. The conflict is visible: the new fact has corroboration: 0 and is excluded by origins: ["primary", "external"].
  • is refused — error message prefixed origin_conflict:, code -32000, nothing written, no WAL entry — when it would end belief in a primary or external episode: a knowledge_process_chunk whose chunk_id has a live primary or external episode (whatever supersede says); a knowledge_mark_chunk_removed with origin: "derived" or "answer" on such a chunk (the removal path takes an optional origin; omitted means primary); or a knowledge_supersede_document whose superseding document is derived and whose superseded document is primary or external. Primary content may supersede derived content freely by chunk_id revision (no doc_id involved) or by knowledge_supersede_document.
  • is refused when its doc_id already carries a different origin: one document has one origin. This applies in both directions, so a primary submission cannot take over a derived doc_id by reusing it. To replace an agent-written document with a human-written one, use a new doc_id and knowledge_supersede_document, or re-stamp the old document with knowledge_stamp_origin.

A rebuild cannot re-open a protected fact: these decisions are baked into the statements the WAL records.

knowledge_stamp_origin (admin scope) stamps origin onto existing episodes, for a graph that predates the field and so reads entirely primary. It re-extracts nothing and calls no LLM or embedder.

Rules are evaluated in order and the first match wins; each needs at least one selector, and selectors within a rule are ANDed. source_path_prefix matches the start of the episode’s source_description (<source_file>:<chunk_id>); attributes_kind matches attributes.kind exactly. An episode with a doc_id pulls in the rest of its document, and rules that would give one document two origins are refused. The reply is {success, dry_run, group_id, matched, changed, unchanged, changes: [{uuid, doc_id, from, to}], truncated} (changes is capped at 200; the counts are exact). dry_run: true writes nothing. A repeat run changes nothing and writes no WAL entry. The stamp is fixed-valued per episode, so it survives rebuild and overlapping tail replay. It is not retroactive: supersessions and invalidations already made are not revisited. Episodes with attributes.kind = "knowledge" are not treated as derived until you stamp them.

Operating an LLM wiki. Send origin: "derived" (and a doc_id) for every page the agent writes and "external" for clipped material; leave notes unmarked. Search with origins: ["primary", "external"] while the agent refreshes a page. To adopt this on an existing notebook, run knowledge_stamp_origin as a dry run, check changes, then run it for real.

Moving a document: knowledge_move_document (issue #903)

Section titled “Moving a document: knowledge_move_document (issue #903)”

A rename or a folder move changes a document’s path, not its words. Removing the document and ingesting it again under the new path would extract every fact a second time at full LLM cost. knowledge_move_document (write scope; feature string move_document; ADR-0903) instead re-keys the document’s existing episodes: no extractor, LLM or embedder call, and entities, relationships, embeddings and belief history stay exactly as they are.

ParameterMeaning
group_idRequired. A missing one is an error (see the omitted-group table).
movesRequired, non-empty array. One item is a single move; many are one batch.
moves[].from / to{doc_id?, source_path?}. Name a doc_id, a source path, or both, and the same kinds on both sides. A document with no doc_id is moved by source path alone. With both kinds, an episode must match both. Only the named identities are rewritten, so a consumer whose doc_id and path differ passes both.
moves[].chunk_id_prefixOptional {from, to}. Chunk ids (episode name / chunk_id) that start with from are rewritten; without it chunk ids are left as they are. What changes. On every episode of the document: doc_id, the stored source file (source_file), source_description (recomposed as <source_file>:<chunk_id>), and with a prefix the chunk id. The document’s DocRevision rows (so the next knowledge_process_document at the new doc_id finds its baseline and does not re-extract) and its document-supersession records, on both sides, are re-keyed too. A document is identified by its live episodes, but its superseded revisions are history that belongs to it and move with it, so knowledge_delete_by_source on the old path finds nothing and knowledge_lint citations of earlier revisions name the new identity. Search, the find methods, knowledge_status, knowledge_lint (stale_derived_page) and citations read the stored fields, so they report the new path at once, with no rebuild.

What does not change. Origin: a move never re-evaluates it. If the new location implies a different origin, call knowledge_stamp_origin afterwards. Other documents’ attributes.links entries that point at the moved doc_id are not rewritten; re-send the pages that link to it.

Refusals. Everything is validated against the state before the batch, under the per-document locks and the write lock, before the first write. If any move is refused, nothing is applied and nothing is written to the WAL; the error (message prefixed move_refused:, code -32000) names each offending move by index with one of these codes, and carries them as structured data: error.data is {"reason": "move_refused", "refusals": [{"index": 1, "code": "unknown_source", "message": "…"}, …]} (over MCP it is the same data on the tool error).

The destination must be empty. A move’s destination has to have no episodes and no document state of any kind in the group: no episode of any liveness (live, superseded or retired) at the new doc_id, at the new source path, or under the rewritten chunk-id prefix; no DocRevision row and no DocSupersession record for the new doc_id, on either side; and no episode whose superseded_by names it. The moving document’s own rows do not count. A doc_id-only move of a document whose source file is its doc_id (document mode with no source_path) also stores the new doc_id as its source file, so that string counts as a destination path too. Anything live in the way is occupied_destination; anything else is destination_has_history. “Live” is the same test knowledge_delete_by_source uses, so a document between knowledge_retire_document(effective_at: <future>) and that date is still live. The check is the same whether the move names a doc_id, a path or both, and a failure to read the database is an error, never a refusal. Clearing a destination: knowledge_delete_by_source removes the episodes at a source path, which clears an occupied_destination / path-level destination_has_history; it does not remove a doc_id’s DocRevision rows or DocSupersession records (a hard delete keeps them). A doc_id that has any of that cannot be used as a move destination: pick a different doc_id.

Reply. {success, dry_run, group_id, moved, episodes_rekeyed, moves: [{from, to, episodes, chunk_ids_rewritten}]}. episodes counts episodes; chunk_ids_rewritten counts distinct chunk ids (the units of one split chunk are several episodes that share one chunk id). There is no per-episode list, because a folder rename covers hundreds of documents.

Durability and atomicity. Each episode is one fixed-valued, uuid-keyed SET, flushed as one WAL chunk, so a rebuild from the WAL, a dump and an overlapping tail replay give the same graph (the same approach as knowledge_stamp_origin). A batch is applied after full validation in one database transaction: if anything fails part-way, the transaction is rolled back and nothing is logged, so neither the graph nor the WAL has a trace of the move, and re-sending the same batch simply works. (A graph whose full-text index is stale fails the whole move with an index error rather than half-applying it; rebuild the indexes and retry.)

Concurrent ingest. A move takes the per-document locks that knowledge_process_document holds, so it waits for an ingest of the same doc_id (source or destination) and the two never interleave. knowledge_process_chunk takes no document lock, so the move instead waits, for up to 30 seconds, for any in-flight chunk call of the moving chunks to finish; if one is still running it fails with nothing changed and the caller retries. The moving chunks are registered as in flight for the whole call, so an identical resubmission that arrives meanwhile is not answered unchanged and then moved away. A chunk ingest into the destination that is still extracting when the move runs cannot be detected in chunk mode (its chunk id is not known yet): send moves while the affected notes are not being ingested. The same gap exists for a move that names only a destination path (no doc_id): the doc_id a document ingest will use at that path is not known, so no document lock covers it, and a knowledge_process_document that is still extracting into that path when the move commits is not detected. Both documents then share the source path, and knowledge_delete_by_source on it deletes both. A move that names the destination doc_id is covered by the lock.

Query variants: knowledge_search_passages queries (issue #802)

Section titled “Query variants: knowledge_search_passages queries (issue #802)”

knowledge_search_passages takes one required query. A question that describes a thing instead of naming it shares few words with the note that answers it, so a direct search can come back thin. The caller, usually an LLM agent, can write rewrites of its own question and pass them as the optional queries array. LCG adds no model call of its own: the variants are the caller’s.

Good variants are keywords the note itself would use, a likely name for the thing described, and a one-sentence hypothetical answer. Use them when a direct search came back thin or the question describes something rather than naming it.

Guidance for callers.

  • Keep the named entities. Every variant must keep the question’s named entities (people, projects, policies, suppliers) and rephrase only the rest. A variant that drops the entity (“supplier uptime guarantee percentage” for a question about Lumen Core’s supplier) matches every company’s note for that attribute equally and pulls the right note down.
  • No placeholders. Do not send template answers such as [supplier name], [Name] or X%; they add a noise token that matches no note.
  • Use variants where they help. They help most for described-not-named lookups and for exact passage lookups. Do not send them for multi-part questions whose entities are already explicit: on the v2 eval these lose to the plain search (see below).

Known regression. On the v2 retrieval eval, with the committed fixture, variants lower multi-hop nDCG@10 by 0.062 [-0.107, -0.026] (vector) and 0.059 [-0.097, -0.027] (hybrid) against the same config without variants, while raising passage-lookup nDCG@10 by about 0.11 and, in hybrid mode, paraphrase by 0.082 [+0.017, +0.153]. Overall the difference is within noise. queries is opt-in, so callers that do not send it are unaffected. The cause and the planned mitigation are in ADR-0802.

Validation (an error naming the broken rule; nothing is silently truncated):

RuleValue
Shapean array of strings; absent, null and [] all mean “no variants”
Countat most 5
Each entrynon-empty after trimming whitespace
Total lengthat most 2000 Unicode scalar values (chars()) across the trimmed entries

Variants are trimmed; query is not. A trimmed variant equal (case-sensitive) to query as sent or to an earlier variant is dropped before searching, so repeating a phrase never boosts a result. query is compared verbatim: if it carries surrounding whitespace, a variant equal to its trimmed text is not dropped and is searched as a near-identical second query, so send query without stray whitespace.

Execution. [query, ...queries] are embedded in one batched query-role call. Each query then runs the request’s whole retrieval pipeline, concurrently and each on its own connection: the same mode (vector, or hybrid with BM25 + vector fused per query, so a variant’s keywords reach BM25), group_ids, origins, probe size and min_score. group_ids and origins therefore bind every query: a variant can never surface a passage from a group or origin that would be excluded for query. The min_score cosine floor binds each query’s vector list only; in hybrid mode a variant’s BM25 hits are not subject to it (as in single-query hybrid), so a variant keyword can add a lexical-only passage whose cosine is below min_score. The per-query rankings are then fused with weighted Reciprocal Rank Fusion (weight / (rank + 60), UUID tie-break): query weighs 2 (PRIMARY_QUERY_WEIGHT, the qmd choice) and the variants share a total weight of 1 (VARIANT_BUDGET_WEIGHT, split equally: 1 each for one variant, 0.2 each for five). However many variants there are, query keeps at least 2/3 of the weight, so variants widen the candidate set but together can never outvote the primary query. Belief-aware ranking (belief_aware; on by default in both modes since #806; belief_aware: false opts out) runs once, on the fused candidates, never per variant. The first num_results of the result are returned.

Response. With queries, every passage also carries matched_queries: ascending indices into the caller’s [query, ...queries] of the queries that retrieved it (0 is query; a dropped duplicate’s index is simply absent). score is the fused rank score (rank-ordered, so it stays monotone through belief demotion), and similarity is the best cosine across the vector legs that matched the passage (absent for a lexical-only hit), exactly as in hybrid mode. min_score floors each query’s vector list before fusion. In hybrid mode each passage also carries legs, the union of the legs over every query that retrieved it (see Hybrid passage search); lexical_score is not set with queries. Without queries (or with [] / null) the response is byte-for-byte what it was before: no matched_queries key.

Why a fixed variant budget: with one weight per variant, five variants outweighed query 5 : 2, and on the v2 retrieval eval that cost 0.046 overall nDCG@10 (ADR-0802). Rerank-on-fused-candidates and knowledge_graph_search queries are follow-ups (ADR-0802).

Notebook health: knowledge_lint (issue #755)

Section titled “Notebook health: knowledge_lint (issue #755)”

Wiki-style notebooks need a health pass — contradictions, stale agent-written pages, thinly supported facts, orphans, missing links. Doing it by having an LLM re-read the notes is slow, nondeterministic and grows with the notebook. LCG already holds the structure (belief time, document supersession, episode origin), so knowledge_lint answers the same questions as graph queries: no LLM call, no embedding-model call, read-only, deterministic. It reports; it never merges, edits, deletes or suggests a fix — that stays with the caller. read scope, ReadOnly for --writable-groups.

Contradictions are deliberately narrow. LCG stores no contradiction signal (ingest never invalidates one fact because of another), and without an LLM the only non-noisy deterministic rule is the single-valued-relation one. “X is in Berlin” against “X moved to Paris” under different relations is out of reach.

The page/link convention (unlinked_mention). LCG does not model notebook pages or links, so the category reads a convention in episode attributes (ADR-0528), parsed only when the category is selected and never by text matching:

  • {"page_for": "<entity uuid or name>"} on any live episode makes that episode’s document the entity’s page (a uuid is exact; a name must match one entity in the group, case-insensitively). The episode must carry a doc_id: links entries are doc_ids, so a doc-less page could never be linked to and its declaration is ignored.
  • {"links": ["<doc_id>", …]} on any live episode opts its document into link tracking (an empty array counts); the union over its live episodes is its outgoing link set.

The category is unavailable — reason no_page_data or no_link_data — until the scope carries both keys somewhere. Whether the notes app writes this convention is for the app to agree.

Cost model. Because counts are exact on every call, each call is a full pass over the selected categories: chunked, uuid-keyed scans (no content, no embeddings) into memory, then pure analysis; the cursor only selects which slice of the ordered result is returned, and only that page is hydrated with entity names. Time grows near-linearly with group size (benches/lint.rs measures 1k/10k/50k episodes; run it with cargo bench --bench lint). The read lock is held only while the snapshot loads, so writers do not queue behind the analysis; the page may reflect a slightly newer graph than the summary. Near-duplicate candidates come from a deterministic blocking scheme (shared long token or shared 3-character prefix of the sorted-token name) so work stays bounded; a block of more than 200 entities is skipped and counted in summary…skipped_blocks, and a near-duplicate sharing no block with its twin is not found. Likewise a (source, relation) with more than 50 distinct believed targets is skipped for contradiction (it would yield one finding per pair) and counted in summary…skipped_subjects. Findings depend on the evaluated instant (a future-dated document supersession takes effect when its time arrives), so determinism holds for an unchanged graph at the same instant.

Origin is a claim. Lint reads origin exactly as ADR-0752 does: the caller’s label, never authenticated. Derived and answer content never counts as corroboration in any category. A group in degraded mode fails like every other read. Start with the Episode origin and Belief time sections; design in ADR-0755.

Deletion (delete_chunk_episode, delete_by_source)

Section titled “Deletion (delete_chunk_episode, delete_by_source)”

To stop believing a whole document without destroying it, use knowledge_retire_document. For a chunk that merely disappeared from its document, prefer knowledge_mark_chunk_removed (see “Belief time” above), which ends belief without destroying the evidence. knowledge_delete_chunk_episode keeps its explicit-deletion contract unchanged.

Breaking change in 0.13.2 (issue #406): group_ids is required and non-empty on both knowledge_delete_chunk_episode and knowledge_delete_by_source. A call that previously omitted group_ids deleted matching episodes across every group in the workspace; that was cross-group-unsafe, so as of 0.13.2 an omitted, null, or empty group_ids is rejected outright with an error, before any delete runs. There is no default to fall back to — a caller upgrading from a pre-0.13.2 client that relied on omission must start passing its own group(s) explicitly:

This is a different contract from the read-tool one above — omitting group_ids here never means “all groups”; it means “reject the call.” A group_ids naming a group with no matching rows still succeeds, returning deleted_count: 0.

knowledge_delete_by_source matches the source exactly (issue #853). It deletes the episodes whose stored source_file equals the request byte for byte, superseded episodes included. It no longer prefix-matches the composed source_description, so deleting https://a.com leaves every episode of https://a.com:8443/x alone, and deleting notes/a leaves notes/ab alone. Episodes written before #853 are matched by the safe legacy rule described under Source identity. An episode that rule cannot attribute is never deleted by source; remove it with knowledge_delete_chunk_episode by its chunk ID.

Behaviour change. A client that wrote source_description = "file:section" through knowledge_add_episode and relied on delete_by_source("file") prefix-matching it will now get deleted_count: 0 for those rows. A raw episode matches only its exact source_description.

Orphaned entities are reported, and pruned only on request (issue #859). Both delete methods delete episodes only. Source identity: source_file and chunk_id (issue #853)

Section titled “Source identity: source_file and chunk_id (issue #853)”

Every episode written by knowledge_process_chunk or knowledge_process_document stores its source file and chunk ID as two separate values, alongside the unchanged display value source_description = "<source_file>:<chunk_id>". A URL contains colons, so the display value cannot be split back reliably. Read the two fields instead of parsing it.

  • Where they appear. source_file and chunk_id are additive fields on knowledge_get_episodes items (projectable with fields), knowledge_search_passages passages and knowledge_get_affected_work candidates. For a chunk ingest they are the request’s source_file and chunk_id. For a document ingest they are the source_path (or the doc_id when no path was given) and the minted chunk name ({doc_id}::{hex}).
  • Legacy episodes carry neither field, and the keys are omitted from the response. Those are episodes written before #853, replayed from a pre-#853 WAL, or created by knowledge_add_episode (which takes no structured source). There is no backfill.

Two operations match a source on this identity, byte for byte, with no URL normalisation (case, trailing slash and default port all count):

  • knowledge_delete_by_source: see Deletion.
  • knowledge_get_entities_by_source returns the entities mentioned by the live episodes of the source. A live episode is one that is not superseded, or whose document supersession is not yet effective, and that does not belong to an uncommitted document revision. An entity is returned when at least one live episode of the source mentions it. https://a.com/p no longer returns entities that only https://a.com/page, https://a.com/p?x=1 or https://a.com/p/sub support. The optional group_ids filter applies to the entity’s group, as before.

The legacy rule. For an episode without a stored source_file, the source is derived from its own name, never by splitting on a colon. Each episode maps to at most one source, so it can never match two different requests.

Direct assertion (assert_entity, assert_relationship)

Section titled “Direct assertion (assert_entity, assert_relationship)”

knowledge_assert_entity and knowledge_assert_relationship (issue #379) are a direct write path: the caller already knows a fact and records it as a single entity or edge, without a prose round-trip through knowledge_process_chunk’s LLM-driven extraction. Use process_chunk when you have unstructured text and want the graph populated by extraction; use the assert tools when you already know exactly which entity or edge you want to write.

knowledge_assert_entity accepts name (required), entity_uuid (optional), kind (optional, see Entity kinds), labels, summary, attributes, and group_id (default liminis).

  • Upsert identity is (group_id, kind, name) (kind defaults to Entity), unless entity_uuid is supplied. entity_uuid, when given, is a strict, group-scoped lookup — the call fails if no entity with that UUID exists in group_id; there is no create-under-this-UUID fallback (ADR-0379 Decision 3). A caller cannot mint an entity at a UUID of its own choosing.
  • On an update, omitting summary or attributes clears the previously stored value rather than leaving it untouched — both fields are always overwritten with whatever the call supplies: summary defaults to "" if omitted, attributes defaults to "{}" (an empty JSON object, not an empty string) if omitted or non-object, matching how labels/name are handled.
  • Only name is embedded for semantic search (name_embedding). summary is stored and is full-text searchable (it’s part of Entity’s [name, summary] FTS index), but is not semantically searchable — a knowledge_find_entities vector query will not match on summary content until issue #470 lands. attributes is not indexed at all — full-text or semantic — and is retrievable only via direct UUID lookup or knowledge_query_cypher.
  • An update never re-embeds name_embedding — only a create does (ADR-0379 Decision 6, forced by a lbug constraint: the embedded column sits under an HNSW index once indexes are built, and lbug rejects a plain SET on an indexed column). Re-asserting an existing entity with a changed name updates the stored name, but name_embedding keeps reflecting the old name until the entity is deleted and recreated. There is currently no supported way to refresh it in place.

knowledge_assert_relationship accepts source_name, target_name, predicate (all required), source_kind / target_kind (optional, see Entity kinds), fact (optional — auto-derived as "{source_name} {predicate} {target_name}" if omitted), attributes, relation_type, valid_at, and group_id (default liminis).

  • Upsert identity is (source_node_uuid, predicate, target_node_uuid, group_id), resolved via find_active_relates_to_uuid (an invalidated edge is skipped, so re-asserting after an invalidation creates a fresh edge rather than resurrecting the old one).

  • Endpoint resolution is strictly scoped to the call’s own group_id — it never falls back to a cross-group search. If source_name or target_name doesn’t resolve to an entity already in that group, the call fails with an error naming knowledge_add_cross_group_edge as the tool to use for connecting entities across groups.

  • fact is the field embedded for semantic search (fact_embedding) — not name/predicate, the opposite of knowledge_assert_entity. fact is also part of RelatesToNode_’s [name, fact] FTS index, so it’s both full-text and semantically searchable; attributes is indexed neither way, same as on the entity side.

  • Same never-re-embed-on-update caveat as knowledge_assert_entity (ADR-0379 Decision 6): a re-assert that changes fact updates the stored fact text but leaves fact_embedding reflecting the prior text until the edge is deleted and recreated.

  • Both tools stamp ingested_at with the service clock at the moment a record is created, regardless of any valid_at supplied; see Time: event time vs ingest time.

See ADR-0379 for the full rationale behind these upsert and embedding decisions.

Algorithm (E13’s v5, generic — no relation names are hard-coded). Per hop:

  1. Candidates are edges incident to the frontier (either direction) whose far end is not a start entity or an entity reached on an earlier hop (walks never cycle back). The current frontier is not excluded: an edge between two frontier entities (for example a project and its supplier, both reached on the previous hop) is a candidate in both orientations, each with its own direction_matched, and ranking keeps only the better one, so the edge takes one beam slot and its fact is reported once. Hop 1 excludes the start entities. Live edges only, except in history mode. On the last hop, when answer_type is "value" or absent, the frontier entities’ own self-loops are candidates too. These are the literal-valued facts (a budget, a price, a date) an ontology extraction stores on the entity they describe (ADR-0823). A self-loop is filtered and ranked like any other edge. It matches either direction, so direction_matched is null, but it gets the soft bonus and is always kept by the hard filter. The hard filter decides between matching and falling back by looking at moving edges only, so a self-loop never hides that fallback. It never becomes frontier. Self-loops are never candidates on an earlier hop, where they would take beam slots meant for moving on, nor in the completion hop.
  2. Relation filter: keep edges whose relation_type is in relation_types; if none match, keep all and record a fallback.
  3. Answer-type filter (last hop only, answer_type an entity type, mode not history): keep edges whose far end has that type (a supertype counts); if none do, keep all and record it.
  4. Direction: out means the frontier entity is the edge’s source as its type reads, in that it is the target. soft adds a fixed 0.05 cosine bonus to matching edges; hard keeps only matching edges, falling back to all (recorded) if none match. Sideways edges (both ends in the frontier) never decide that match-or-fall-back question while forward edges exist, because one orientation of a sideways edge always matches. any applies neither.
  5. Rank by cosine(embedding of phrase with the query-side instruction, the edge’s fact embedding) plus the bonus. On equal score a forward edge (one that reaches a new entity) ranks before a sideways edge (both ends in the frontier), then ties break by edge uuid. Edges with no usable fact embedding rank after every embedded edge (score 0.0). Each edge is kept in one orientation only. While forward edges are candidates, sideways edges are limited to the slots the forward edges do not need (and never below half of the beam, rounded up), so a tightly connected frontier cannot crowd out the walk’s next entities. The top B are kept; their far ends are the next frontier, and a kept sideways edge carries both of its ends into it (both were already reached, and which orientation was kept is only a tie-break).

If the hops end on no entity of an entity-type answer_type and query is given (and mode is not history), one completion hop runs: edges from the final frontier to entities of that type, ranked by cosine(query, fact embedding), no direction logic. It is an edge hop (not a node ranking), appears as an extra entry with completion: true, and sets completion_hop_ran. A hop with no candidates ends the walk early (dead_end_at). A self-loop is not a move: a last hop whose only candidates are self-loops is also reported as dead_end_at, and that hop is still returned with their facts. In facts_text a self-loop renders once, as (X [Type] -> X [Type]).

Response:

  • found: false (with message, empty hops) when start resolves to nothing — never a silent empty walk. Hop numbers in fallbacks and dead_end_at are 1-based.
  • direction_matched is null for any hops. type is the entity’s primary type, empty when it has none.
  • signature_mismatch uses the flag persisted on the edge when present (attributes), otherwise recomputes whether the endpoint types violate the relation’s declared source_type / target_type; false with no ontology, no declared signature or an untyped endpoint. With several group_ids, each edge is checked against the ontology of its own group_id.
  • An edge whose fact embedding is unusable — a zero vector, or a different dimension from the query embedding (the embedder changed since the edge was written) — cannot be scored: it gets score: 0.0, no direction bonus, and ranks after every scorable candidate.
  • facts_text is the typed reader format, deduplicated by edge uuid, in hop then rank order: - <fact> (<source> [<Type>] -> <target> [<Type>]) [from <date> until <date>]. An untyped endpoint drops its [Type]; the validity suffix is omitted when both dates are absent and shows only the side that is present otherwise. Showing the reader each endpoint’s type was E13’s largest single gain.
  • An embedder failure is an explicit error, never a walk over zero vectors.
Provenance (include_provenance)
Section titled “Provenance (include_provenance)”

With include_provenance: true, every edge in every hop (completion-hop and self-loop edges included) gains three keys, appended after signature_mismatch and always present (empty list / false, never omitted):

  • episodes: the UUIDs of the edge’s producing episodes (the RelatesToNode_.episodes column, ADR-0705) that are live: they still exist, are not superseded and are not a pending document revision (the predicate belief and search use). Superseded or deleted episodes are never listed, in any mode including history. Recorded order, at most 20. episodes_truncated is true only when more than 20 live producers exist.
  • source_files: the distinct sources of all live producers (not only the 20 shown), in first-seen order: each episode’s source_file (Source identity, #853), or, for a legacy episode without one, its stored source_description unsplit (the composed value cannot be reliably split).
  • An edge whose producers are all superseded or gone is still returned, with empty episodes and source_files (no fallback to stale descriptions); provenance never filters, ranks or reorders edges.
  • An edge with no recorded producing episodes (a legacy row, a direct assertion, a cross-group edge) has empty episodes and falls back for source_files: first the edge’s own source_descriptions, otherwise, for an edge without a warrant, the sources of live episodes in the edge’s group that mention both endpoints (at most 20 distinct sources, ordered by episode UUID; episodes_truncated is true when more were dropped). This is a heuristic for legacy rows only; those episodes are not reported as producers. The mention query itself is unbounded (every episode mentioning either endpoint is read), so a hub entity mentioned by thousands of episodes costs proportionally even though at most 20 sources are returned; only the liveness lookup is restricted to episodes mentioning both endpoints.
  • Without the flag (absent or false) the response is byte-identical to before, facts_text is unchanged either way, and no extra lookups run. Episodes are looked up in the edge’s own group. The walk stays read-only. Fetch passages for a citation with the existing episode tools.

Known limit: each hop loads every incident edge (with its fact embedding) of the frontier, so a hub entity with thousands of edges costs proportionally; the beam keeps later frontiers small. There is deliberately no cap, since a cap would silently drop candidates; each hop reports its candidate_count (the unfiltered candidates after the start/earlier-hop exclusion and before orientation dedup, so an edge between two frontier entities counts once per orientation) so a caller can see how wide a hop was.

Ontology reload (knowledge_reload_ontology)

Section titled “Ontology reload (knowledge_reload_ontology)”

knowledge_reload_ontology {group_id} (admin scope) discards one group’s cached ontology resolution and re-resolves it, so an edited per-group ontology file takes effect without a service restart. It returns {group_id, previous_hash, new_hash, changed, drift, identity_refusal}; an identity-bearing-set change on a group that already holds entities of that type is reported in identity_refusal (and enforced as -32003 on knowledge_add_episode) rather than installed silently. Other groups are untouched and stored data is never modified. See Ontology → Reloading a group’s ontology.

Relation typing (canonicalize_relations, backfill_relation_types, reprocess_relation_types)

Section titled “Relation typing (canonicalize_relations, backfill_relation_types, reprocess_relation_types)”

Three tools populate an edge’s relation_type, with different tradeoffs:

knowledge_canonicalize_relations maps each edge’s existing raw predicate onto your ontology’s declared relation_types. Its behavior has four caveats worth knowing before you rely on it:

  • group_id is required (issue #447) — candidate selection and the resulting WAL mutations are both restricted to that one group; no other group’s edges or WAL stream are ever touched. An omitted, null, or empty group_id is rejected before any candidate selection or write, rather than falling back to a database-wide rewrite or the default group — there is no supported way to canonicalize every group in one call.
  • The primary pass is lexical, over the predicate — not the fact. It matches the edge’s predicate / current relation_type against ontology type names, aliases, and keywords. It does not read the edge’s fact sentence, so an edge whose relation_type was cleared cannot be re-mapped from its fact by this pass.
  • embedding_threshold tunes only the fallback promoter (default 0.7). The fallback embeds each residual edge’s fact against the ontology types’ descriptions and force-assigns the single nearest type at or above the threshold. Lowering it types more edges, but by nearest-neighbor force-fit with no abstention — an idiosyncratic fact (e.g. “X is affiliated with Y”) can land on a wrong type (e.g. HOLDS).
  • Re-runs are only partly idempotent, and clearing relation_type can’t be undone by canonicalize. A re-run skips an edge only when it’s already at its target — a Mapped edge already equal to the canonical type, or a residual edge already UNCLASSIFIED; an edge whose classification changes is overwritten (including a previously-assigned type), while arrow-named “noise” edges keep any existing predicate. Critically, canonicalize’s only input is the edge’s existing predicate / relation_type — if you null that field to “start clean,” canonicalize has nothing to map from and cannot rebuild it. Snapshot with knowledge_dump_wal before such an operation.

Edge direction repair (#816). When the ontology declares a relation signature (source_type/target_type) or inverse_aliases, knowledge_canonicalize_relations also applies the ingest-time direction rules to the stored graph, with no re-extraction (Ontology → Edge direction, ADR-0816):

  • An edge whose endpoint entity types fit its relation’s signature only when reversed is swapped (source and target exchanged; the stored name is rewritten only if it has the ingest form "A → B"). An edge retyped through an inverse alias (or an inverse keyword hit) is retyped and swapped in the same pass. An edge that fits neither way is never dropped: it is marked "signature_mismatch": true in its attributes (existing keys such as original_relation_type are preserved). A stale mark is cleared once the edge fits. Symmetric relations, relations with no signature, and edges with an untyped endpoint are skipped.
  • dry_run: true computes and reports everything and writes nothing.
  • The response gains swapped_count, signature_mismatch_count and by_type: {<RELATION>: {checked, swapped, mismatched}} (checked = edges that could be evaluated). by_type is {} and the counts are 0 for an ontology with no signature and no inverse alias, which is processed exactly as before.
  • It is idempotent: a second run on a repaired graph reports swapped_count: 0. Edges missing either endpoint hop (e.g. unbound cross-group pointers) are not checked.
  • A swap rewrites the edge’s three stored structures (shadow node, direct relationship, two hops) as several statements; a crash mid-swap can leave one edge half-wired. Take a snapshot (knowledge_dump_wal) and preview with dry_run before running it on a large graph.

knowledge_backfill_relation_types (DEPRECATED) does not classify at all — it mints uppercased fact-prefix pseudo-types (e.g. THE_SPECIFICATION_DOCUMENT_DEFINES) for edges with no relation_type, rather than matching against the ontology. Avoid it for building a typed taxonomy; prefer knowledge_reprocess_relation_types below, which supersedes it for that purpose. Like knowledge_canonicalize_relations, group_id is required (issue #447): candidate selection and WAL attribution are both restricted to that one group, and an omitted, null, or empty group_id is rejected rather than running database-wide or against the default group.

knowledge_reprocess_relation_types is the relation-side twin of knowledge_reprocess_entity_types: for each in-scope edge, it sends the edge’s fact and the ontology’s declared relation types (name + description) to the configured extraction LLM and asks it to pick exactly one type, or honestly abstain. This is the tool to reach for when you want genuine fact-based classification instead of lexical matching or pseudo-typing:

  • Always reads the fact, never the predicate. Unlike canonicalize_relations, classification is grounded in the edge’s natural-language fact sentence against the ontology’s declared menu — not lexical/alias/keyword matching on the existing predicate string.
  • A declared ontology relation-type menu is always required. Unlike knowledge_reprocess_entity_types (whose untyped scope works with no ontology via open-ended classification), every scope value (untyped, off_ontology, all) fails with a structured {success: false, error: ...} if the ontology declares no relation types — there is no open-ended fallback (see ADR-0037).
  • Abstention is an honest, real write of UNCLASSIFIED. If the LLM cannot map a fact to any declared type, the edge’s relation_type is set to the literal string UNCLASSIFIED — never a force-assigned nearest match. This differs from knowledge_reprocess_entity_types, where an unclassifiable entity is simply left unchanged (see ADR-0037).
  • scope controls candidates: "untyped" (default) — relation_type NULL/empty, the same predicate backfill_relation_types uses; "off_ontology" — untyped edges plus edges whose relation_type isn’t a declared type (this naturally covers prior UNCLASSIFIED sentinels and backfill_relation_types’s fact-prefix pseudo-types with no special-casing); "all" — every edge in the group.
  • Idempotent. An edge whose computed verdict already matches its current relation_type (including an edge already correctly UNCLASSIFIED) is left unchanged — no write, no WAL entry.
  • dry_run: true returns would_reclassify_count, a plan array of per-edge {edge_id, fact, old_type, new_type} entries, and a breakdown object counting edges per assigned new_type (including an UNCLASSIFIED count) — without mutating the graph.
  • dry_run: false (apply) returns reclassified_count, unchanged_count, and — since issue #332 — the same breakdown object as the dry-run path, so callers can see the per-type classification distribution (including how many candidates abstained to UNCLASSIFIED) without a separate dry-run call. plan and would_reclassify_count remain dry-run-only, since they describe a proposed mutation rather than one that already happened; breakdown is always present on a successful apply response, as {} when there were zero in-scope candidates.

Semantic search maintenance (backfill_summary_embeddings)

Section titled “Semantic search maintenance (backfill_summary_embeddings)”

knowledge_backfill_summary_embeddings (issue #470) computes summary_embedding for every entity in group_id that has a non-empty summary, so entities created before this capability existed become semantically retrievable by summary paraphrase — not just by name-vector or full-text match. knowledge_find_entities already fuses a summary-vector match into its hybrid retrieval for entities embedded going forward (both knowledge_assert_entity and the extraction path embed summary on creation); this tool is what makes that retrieval available for entities that predate the capability.

  • Every candidate is unconditionally re-embedded on each call. There is no cheap way to tell “already has a real embedding” apart from “still carries the schema migration’s zero-vector placeholder” from a stored FLOAT[] value alone, so re-running this backfills the same rows again. This is safe (idempotent in effect) but not free (an embedder round-trip per candidate, same as knowledge_backfill_relation_types and subject to the same no-batching caveat, #445) — use dry_run: true first to see the candidate count.
  • Holds an exclusive lock for the whole run, blocking all other reads and writes. Unlike most admin operations, the summary-vector HNSW index is dropped for the run’s duration and rebuilt at the end — this is the only way an indexed embedding column can be refreshed for existing rows at all (a plain SET on an HNSW-indexed column is rejected once the index exists). Prefer running this at a low-traffic time, especially for a large group.
  • group_id is required (matching knowledge_backfill_relation_types’s convention): candidate selection and WAL attribution are both restricted to that one group; an omitted, null, or empty group_id is rejected rather than running database-wide or against the default group.
  • A partially-completed backfill is not an error. Entities not yet processed simply retrieve via existing name/lexical behavior, exactly as before this issue — running the tool again covers more of the group each time.
  • A knowledge_assert_entity re-assert does not refresh summary_embedding. A re-assert that changes an entity’s summary leaves its summary_embedding as it was — the vector reflects whichever summary was embedded last (at creation, at an extraction merge, or at the most recent backfill run), not necessarily the current summary text. Re-run this tool to bring a changed summary’s vector back in sync. (Extraction merges do refresh it: when extraction folds a new description into an existing entity the merged summary is consolidated into one bounded description of at most 600 characters and re-embedded in the same write — ADR-0651.)

Repairing zero-vector rows (reembed_missing)

Section titled “Repairing zero-vector rows (reembed_missing)”

knowledge_reembed_missing (issue #809, ADR-0809) re-embeds exactly the rows that were stored with a fallback zero vector because the embedder failed during WAL replay. Such a row is invisible to vector search until repaired. Replay records each one durably as (group, kind, uuid); knowledge_status reports the per-group count as wal_groups.<gid>.zero_vector_rows (#808), and this tool acts on that record. Unlike knowledge_backfill_summary_embeddings it does not touch rows that are fine, and unlike a full knowledge_rebuild_from_wal it takes time proportional to the number of recorded rows plus one index rebuild per affected kind.

Parameters:

ParamTypeNotes
group_idstring, requiredThe group whose recorded rows are repaired. Subject to --writable-groups: an unlisted group is refused before any embedder call, dry_run included.
kindsarray, optionalAny non-empty subset of name (entity name), summary (entity summary), fact (relationship fact), content (episode content). Default: all four. An invalid value is rejected, naming the valid ones.
dry_runbool, default falseReport per-kind candidates only: no embedder call, no write, no record change, no index change.

Result:

All four kinds are always present. candidates is the number of recorded rows of the kind, so reembedded + failed + skipped_no_source = candidates and a dry_run reports what a real run would attempt. The envelope can also carry cancelled: true, index_rebuild_errors (see below) and write_error.

  • What is repaired and how. Each recorded row is re-embedded from the source text stored on the same row, through the embedder’s document role and instruction profile, using the same bounded retry, backoff and failure-splitting policy as replay (LCG_REPLAY_EMBED_RETRIES, LCG_REPLAY_EMBED_BACKOFF_MS, LCG_REPLAY_EMBED_BACKOFF_MAX_MS — the names say “replay” but they apply here too). A text the embedder cannot process fails only its own row.
  • failed — the embedder failed for the row, returned a vector of the wrong dimension, with a non-finite value or all zeros (never written), the write failed, or the row’s text changed after it was read (a vector from stale text is never written). It stays recorded; run the tool again.
  • skipped_no_source — the recorded row no longer exists (its stale record entry is removed), or it exists but has empty/whitespace text or belongs to another group (it stays recorded).
  • The record. A repaired row is removed from the record, so zero_vector_rows in knowledge_status drops by that amount; after a full repair it is 0. Rows not in the record are never modified.
  • Index cost: read this before running it. All four embedding columns carry a database-wide vector index, and a plain write to an indexed column is rejected. The tool therefore finishes all embedding first, with no lock held and no index touched, and only then takes the exclusive write lock, drops only the indexes of kinds that have something to write, writes, and rebuilds them. Because those indexes span all groups, repairing one group blocks writes everywhere, and vector search for every group waits for the rebuild, while the index is down. With nothing to write — no candidates, or every embed failed — no index is dropped and no repair write lock is held (removing stale record entries takes the write lock only briefly). Run dry_run: true first and prefer a low-traffic time for a large database.
  • If an index rebuild fails the result still carries the counters (the rows are already written) plus index_rebuild_errors: [{"kind", "error"}], the service’s “indexes built” state is left false, and the next search rebuilds all indexes automatically. That search pays for a rebuild proportional to database size.
  • Cancellation. Closing the client connection (or shutting the service down) cancels between embedding windows, before anything is written, and the result carries cancelled: true. Once the write phase has started it always finishes and rebuilds, so a cancel never leaves an index dropped.
  • Not recorded in the WAL. Vectors are a local cache recomputed on replay (ADR-0526), so the repair writes in place and adds nothing to the WAL.
  • Out of scope. Renamed entities and changed source text are not detected, and zero-vector rows that are not in the record are not found. Emits MCP progress notifications (phase: embedding, then writing) when called with a progress token.

Cross-group pointers (add_cross_group_edge, rebind_pointers)

Section titled “Cross-group pointers (add_cross_group_edge, rebind_pointers)”

knowledge_add_cross_group_edge creates an edge whose endpoint(s) may live in a group_id other than the edge’s own — the hub/layer-graph topology introduced by issue #369 (see ADR-0369). Every intra-group edge write (knowledge_add_episode, knowledge_process_chunk, and every other existing write path) is completely unaffected: pointers only ever exist on edges created through this tool.

  • Each endpoint is either a bare UUID or a name to resolve. {"uuid": "..."} names an entity already known to live in the edge’s own group_id — no resolution, no pointer. {"source_group_id": "...", "endpoint_name": "..."} names a foreign endpoint: it is resolved by case-insensitive name lookup against that group (the same authority get_entity_by_name_ci_with_scan_fallback uses for extraction-time endpoint resolution, per ADR-0283), and the edge carries a cross_group_pointers.{src,dst} object recording the assertion (source_group_id, endpoint_name, plus an optional endpoint_kind) and the resolution cache (resolved_uuid, bound_at_seq, binding_state). Top-level source_kind / target_kind (issue #615) pin a foreign endpoint to an entity kind: a kind-pinned pointer resolves within that kind only and stays bound when a same-named entity of another kind appears; a kind-less pointer resolves across all kinds and becomes ambiguous (no hop) once a second kind shares the name. A kind on a {uuid} endpoint is rejected. If a pinned kind no longer exists the pointer is unbound.
  • A foreign endpoint that doesn’t currently resolve is unbound, not dropped. Unlike ordinary extraction (which hard-drops an unresolvable endpoint at commit — see ADR-0051), the edge is still created; only the hop to that side is missing until the target group is (re)built — which re-binds it automatically, see knowledge_rebuild_from_wal — or a knowledge_rebind_pointers call resolves it. A binding_state of ambiguous means more than one entity currently matches the name — also retained, also missing that hop, never a silently-guessed winner.
  • A bare-UUID endpoint that turns out to belong to a different group than the edge is rejected before any write happens — this is what keeps a cross-group edge from silently losing its pointer fields the first time a caller passes a UUID instead of a name.
  • knowledge_rebind_pointers ({"source_group_id": "..."}, required) re-resolves every pointer whose source_group_id matches, after that source group’s own hydration, incremental replay, or refresh cycle — including an ordinary knowledge_rebuild_from_wal targeting that one group, not only a full purge-and-rehydrate (issue #378). Since issue #741 every successful knowledge_rebuild_from_wal already runs this pass for the rebuilt group and reports it as cross_group_rebind, so a manual call is only needed after hydrating a group by some other route (e.g. assertion-API writes). A pointer currently bound is skipped once its bound_at_seq is already at or past source_group_id’s own applied WAL position — never any other group’s, even when the edge carrying the pointer lives in a third, different group — this staleness gate is what makes a second call with no intervening change to source_group_id’s stream a true no-op for pointers that are already correct. A pointer currently unbound or ambiguous is always re-resolved regardless of bound_at_seq (issue #392): a known-broken pointer is repaired unconditionally, since the position comparison alone cannot tell “nothing changed” apart from “the source group was purged and then restored to the same position the pointer was originally bound at.” A resolution that would create a self-loop or duplicate an existing directed edge invalidates the edge instead of writing a broken or redundant one, reusing knowledge_merge_entities’s own self-loop/dedup handling rather than a new policy. Returns {checked, bound, unbound, ambiguous, invalidated_self_loop, invalidated_duplicate, staleness_skipped} — staleness_skipped counts pointers skipped by the gate above, distinct from checked (pointers actually re-resolved), so a checked: 0 result is never ambiguous about whether anything was examined.
  • Unbound and ambiguous edges are excluded from normal reads. Every existing two-hop traversal, search, and MCP read path requires both hops to exist — a pointer that hasn’t resolved is invisible the same way any other incomplete edge would be, no special-casing needed. Aggregate counts are visible via knowledge_status’s cross_group_pointers: {bound, unbound, ambiguous} field, so a refresh in progress is observable without a dedicated inspection endpoint.

Ingestion results (process_chunk)

Section titled “Ingestion results (process_chunk)”

Progress (issue #861, feature chunk_progress). With a non-null _progress_token param, knowledge_process_chunk streams {"type":"progress","phase":"embed"|"extract"|"commit"} lines before the terminal result, in that order, each only if the phase runs. embed and extract are emitted together as start-of-phase markers (the service runs them concurrently); commit is sent once the group write lock is held, after which the write cannot be cancelled: a request still waiting for the lock behind another writer has not sent commit and is still cancellable. A request that returns early sends no frame for a phase that never ran: an unchanged resubmission (unchanged_noop) or a validation error sends none, only the terminal response. Without the token nothing changes. These names are the single-chunk vocabulary; knowledge_process_document keeps its own (chunked / extracting / committing). The frames carry no token; correlate by connection (see Connections, concurrency and timeouts). A client that disconnects mid-request cancels it before commit (feature cancel_on_disconnect). While a request that sent a token is otherwise silent (the LLM call between extract and commit), the service writes {"type":"progress","phase":"heartbeat"} about every 10 s, so a client with a per-line idle read timeout (as the attached MCP backend has, 30 s by default) keeps its connection and the ingest alive. Ignore unknown phase values; token-less requests get none.

knowledge_process_chunk reports what it could not write, not only how much. Two additive result fields exist for that, both introduced in 0.13.2.

  • dropped_edges reports the edges behind edges_dropped_unresolvable. An extracted edge whose source or target endpoint resolves to no entity — neither in the current extraction batch nor in the persisted graph — is dropped rather than written (ADR-0051). edges_dropped_unresolvable counts those drops; dropped_edges describes them, with one entry per counted edge, in extraction order:

    unresolved_endpoint is "source", "target", or "both". relation_type may be null, mirroring the fact that it is already optional on an extracted edge before resolution is attempted. The dropped edge’s content is not persisted anywhere, so this result is the only place it appears — a consumer that wants to tell a user which fact was lost must read it here rather than recover it later. dropped_edges is always present, an empty list when nothing was dropped, so it can be iterated unconditionally. edges_dropped_unresolvable’s existing meaning is unchanged, and a caller reading only the count is unaffected (issue #411).

  • entities_dropped_source_id counts extracted entities dropped for being named after the episode’s own source ID or a cited note ID (issue #824). An entity whose normalised name (case, surrounding punctuation / [[ ]], path prefix, one .md/.markdown/.mdx/.txt extension) equals the chunk’s own slug-shaped note ID (no whitespace, containing a -, _ or digit; a note named after its subject, such as Alice.md, has none) — the source_file, doc_id, or the chunk_id before its #<n> suffix — is the model extracting the note itself and is dropped, together with any edge touching it. So is an entity whose name is, verbatim (before normalisation), an all-lowercase, space-free, ID-shaped [[wikilink]] target in the chunk text (a citation such as Sources: [[project-quill-core-1]]) and the source ID of a note already ingested in the same group. [[GPT-4]], [[Quill Core]] and [[machine-learning]] (no such note) are kept. The host-asserted Document/Source entity is the supported way to represent the note. The count is a top-level field, always present (0 when nothing was dropped); the discarded edges are not counted in edges_dropped_unresolvable.

  • edges_dropped_self_loop counts edges dropped because both endpoints resolved to one entity. Two differently named endpoints can resolve to the same entity UUID (through dedup merges or salvage); inserting that edge would create a self-loop, so Phase C drops it. The count is a separate top-level field, always present, and these edges are not in dropped_edges or edges_dropped_unresolvable. (Edges whose endpoint names are identical are filtered earlier and never counted, except under an ontology, where they are stored as literal-object self-loops; see edges_literal_object below.) Separately, an off-list edge endpoint that already exists exactly (same group, case-insensitive) in the stored graph resolves to that entity and is never salvaged onto a similar entity of the current chunk; a name stored under more than one eligible kind is dropped as ambiguous rather than salvaged (ADR-0666).

  • edges_swapped and edges_signature_mismatch report the endpoint direction check (#816). Two additive top-level counters, always present. edges_swapped counts edges stored with their endpoints exchanged because they fit the relation’s declared signature only when reversed; edges_signature_mismatch counts edges stored unchanged but marked "signature_mismatch": true in their attributes because they fit in neither direction. No edge is dropped by this check. Both are 0 for an ontology that declares no signature. Swaps made by an inverse alias (strict mode) are not counted here. See Ontology → Edge direction.

  • edges_literal_object and edges_suspected_misattachment report literal-valued facts (#823). Two additive top-level counters, always present. Under an ontology with an extractable relation type, edges_literal_object counts edges stored as a self-loop on one entity because the model emitted a literal-valued fact about it (“Marlin Core has a monthly budget of $4,200”) with the same name on both ends; each such edge carries "literal_object": true in its attributes. Admission is by name equality alone (the fact is not checked for a value), so this is an upper bound on genuine literal-valued facts. It is always 0 with no ontology, where a self-reference is still dropped. edges_suspected_misattachment counts edges between two different entities, in every mode, stored unchanged but marked "suspected_misattachment": true because their fact states a literal value (a digit or currency symbol) without naming both endpoints. Neither drops an edge. A self-loop’s endpoints have the same UUID in knowledge_get_edges_by_group and the other edge reads. See Ontology → Literal-valued facts and ADR-0823.

  • warning reports oversized input. A chunk_text longer than the advisory threshold (LCG_CHUNK_TEXT_ADVISORY_MAX_CHARS, default 8,000 characters — see Configuration) adds a warning field naming the actual and recommended character counts, and emits a chunk_text_oversized telemetry event. This is visibility only: nothing is truncated, split, or rejected, and the call succeeds exactly as it did before. The warning.message points at knowledge_process_document (issue #862): send a whole document or a long page there and the server chunks it for you (see Document mode). The client is not asked to split it by hand (issue #407, reworded by #862).

  • dedup_paths reports how this chunk’s entities were resolved. An additive object of per-path tallies for the chunk’s Phase B entity resolution (ADR-0650), always present:

    exact_name counts entities merged by the exact case-insensitive name match; embedding_merge counts embedding-path merges where a candidate survived the identifier veto and the dedup adapter confirmed it; vetoed counts entities that had above-threshold embedding candidates, all of which were rejected by the identifier-mismatch veto (names differing by a number or identifier, such as ADR 2018 / ADR 2019, or by a distinct short all-caps code such as ACDS / ACDM), so a new entity was inserted; adapter_rejected counts candidates that survived the veto but were rejected by a non-LLM (custom) dedup adapter; llm_confirmed, llm_rejected and llm_unavailable count candidates judged by the LLM dedup check (LCG_DEDUP_LLM, ADR-0652) as duplicate (merged), distinct (inserted) and unanswerable — error, timeout or malformed answer — (inserted); when the check is off, a surviving candidate merges and counts as embedding_merge; salvage_vetoed counts off-list edge endpoints whose salvage candidates were all vetoed. The tallies are per chunk; sum them across chunks for a run total.

Progress notifications

Section titled “Progress notifications”

Over the socket, knowledge_process_chunk and knowledge_process_document also stream progress when given _progress_token; see Ingestion results. Those two are not bridged to MCP progress notifications.

The seven long-running operations — knowledge_rebuild_from_wal, knowledge_canonicalize_relations, knowledge_backfill_relation_types, knowledge_backfill_summary_embeddings, knowledge_reembed_missing, knowledge_reprocess_relation_types, and knowledge_reprocess_entity_types — bridge to MCP progress notifications when the client attaches a progress token to the tools/call request (_meta.progressToken), in both standalone and attached mode. Without a progress token, these calls simply block until they complete, same as over the socket protocol. In attached mode, each progress notification also re-arms LCG_ATTACHED_CALL_TIMEOUT_MS’s per-read-line idle timer (see DB-access modes above), so a progress-tracked call isn’t falsely reported as timed out just because it runs longer than that timeout in total.
