Retrieval-Quality Evaluation

lcg-eval retrieval answers a question the extraction eval cannot: given a real question, does the read side return the right notes and the right evidence? It scores LCG’s knowledge_search_passages, knowledge_find_entities and knowledge_find_relationships against a checked-in question set, and compares them with qmd — local markdown search (SQLite FTS5 + vectors, LLM query expansion, RRF, LLM reranker) and the strongest local stand-in for “raw top-k retrieval”.

It is a separate mode of the existing lcg-eval binary. The extraction eval (testing-and-evaluation.md) is unchanged.

Status: no numbers published yet. The harness and both fixtures (the 31-note v1 smoke corpus and the 408-note v2 skeleton, whose prose a maintainer still has to render) are in the repository; results appear here only after a maintainer has run the comparison on a real embedder. Until then this page deliberately contains no scores.

Passage ranking never reads an edge’s type, direction or endpoints. To score the extracted graph against a fixture’s skeleton.json, use lcg-eval graph-integrity (graph-integrity-evaluation.md).

What it measures

Section titled “What it measures”
ConfigurationWhat runs
lcg-passagesknowledge_search_passages sending neither mode nor belief_aware: the service’s shipped default (#806), i.e. belief-aware vector, no FTS and no RRF. It tracks the default, so a change to the default shows up here. The harness removes LCG_PASSAGE_SEARCH_MODE and LCG_PASSAGE_BELIEF_AWARE from the spawned service’s environment so an operator’s overrides cannot change what it measures. It is the same request as lcg-passages-belief today.
lcg-passages-rawOpt-in (#806), not in the default run. mode: "vector", belief_aware: false: cosine only, the pre-#806 lcg-passages baseline, so the belief-aware gain stays measurable.
lcg-passages-variantsExtra. lcg-passages (the shipped default, belief-aware vector) plus the question’s variants from query-variants.jsonl passed as queries (#802): one batched embed, one vector probe per query (concurrent), weighted RRF with the primary query weighing 2 and the variants sharing a total of 1. Skipped, not failed, when query-variants.jsonl is absent.
lcg-passages-belief-variantsOpt-in. lcg-passages-belief plus the same variants: every query runs the vector pipeline, belief-aware ranking runs once on the fused list. Read against lcg-passages-belief.
lcg-passages-hybrid-belief-variantsOpt-in. lcg-passages-hybrid-belief plus the same variants: every query runs BM25 + vector (so a variant’s keywords reach BM25), belief-aware ranking runs once on the fused list. Read against lcg-passages-hybrid-belief.
lcg-entities-factsknowledge_find_entities + knowledge_find_relationships (hybrid FTS + vector, RRF), default reads. k is split across the two reads (ceil(k/2) entities + ceil(k/2) facts) and the ranks are interleaved.
qmdqmd query --no-rerank (query expansion on).
qmd-rerankqmd query with its LLM reranker.
lcg-passages-hybridOpt-in (#789), not in the default run. knowledge_search_passages with mode: "hybrid", belief_aware: false: BM25 over episode text + vector, weighted RRF (lexical weight 0.4, vector 1.0).
lcg-passages-hybrid-beliefOpt-in (#789). As above with belief_aware: true (the hybrid default): a derived page ranks below the primary note it cites, and a superseded passage below its successor.
lcg-passages-beliefOpt-in (#789). mode: "vector" with belief_aware: true: the vector ranking plus the same rules. Comparing the lcg-passages* rows shows what weighted fusion and the belief rules each add, per category. Unweighted RRF and the top-rank bonus were measured and dropped (ADR-0789).
lcg-entities-facts-beliefExtra, clearly labelled variant. As lcg-entities-facts, but facts are read with believed_only=true.

Fact reads carry no episodes field: the harness maps each fact to its producing notes through belief.producing_episode_uuids, which the service returns only when a belief parameter is sent. Both LCG fact configurations therefore send believed_only (false for lcg-entities-facts, which annotates without filtering). Only the fact read can express belief (ADR-0705); the entity read of lcg-entities-facts-belief is unfiltered and can still credit a superseded note. During ingest the harness validates every knowledge_supersede_document response and aborts, naming both note ids, if a call ended belief for zero episodes (replays and future-dated supersessions excepted); the report’s ingest block shows “Belief ended for N episode(s) across M document supersession(s)”.

The first four are the headline table. The fifth exists because only edge reads can express belief time (ADR-0705): passages and entities have no belief filter and return superseded text by default, so without it the temporal hypothesis would test the configuration, not the architecture.

Every configuration runs over the same corpus and question set with the same k (--k, default 10). Score floors are set to zero (min_score=0, min_similarity=0) so a floor never truncates a result list below k.

For lcg-entities-facts* the shared k is a retrieval budget split across the entity and fact reads, so the configuration does not get 2k results against the other configurations’ k. One asymmetry remains by design: an entity maps to every note it was extracted from, so a single entity result can credit several notes before the list is cut to k notes.

Metrics

Section titled “Metrics”
  • recall@k, MRR, nDCG@k at note level. The ranked note list is de-duplicated (first occurrence wins) and cut at k. nDCG uses graded gain 2^gain − 1.
  • grounded-recall@k / grounded-MRR for answer questions: a blind LLM judge sees only a key fact and one returned text and says whether the text supports the fact. It never sees which system produced the text, and chunk boundaries do not matter, so neither system’s chunker is favoured. Finding the right note but returning the wrong passage counts as a note hit and a grounded miss.
  • stale>current and stale-in-top-k for temporal questions: whether the best-ranked superseded note outranks the best-ranked current note (or appears in the top k at all). Lower is better. A stale hit with no current hit counts as stale-above-current.
  • false-pos@k for negative questions (no relevant note exists): 1 if anything was returned. Negatives are excluded from recall/MRR/nDCG means. Because every configuration runs with its score floor at 0, a system normally returns results for any query, so this column is usually pinned at 1.0 for all of them; the report says so (“non-discriminating”) rather than marking a winner. It only separates systems that return fewer than k results on their own (e.g. qmd).
  • Hits without evidence text. If a qmd hit carries no snippet there is no passage to judge. It is counted as ungrounded (empty evidence; the judge is not called) and the report lists how many hits had no snippet per configuration, so qmd’s grounded figures are a lower bound rather than quietly equal to its note-level recall. There is deliberately no fallback to the whole note.
  • Latency p50/p95 per query, warm only: indices are built explicitly and one unmeasured pass runs before the timed pass. qmd runs as one process per query, so its latency is per-process (it includes model load) and it gets a single warm-up query rather than a full pass.
  • Query-time model calls. LCG: one embedder call per read (a fallback get_edges_by_uuids lookup, if a fact read omits provenance, is counted separately; it should now be 0). qmd does not expose its expansion/rerank call counts, so they are reported as n/a (not exposed), never as 0.
  • Ingestion cost is reported separately: LCG ingest wall time and number of extraction requests (each is at least one LLM call); qmd index time.

Confidence intervals and noise (#788)

Section titled “Confidence intervals and noise (#788)”

The first live run on the small v1 corpus (#786) showed why point estimates are not enough: with 40 judged questions a single question moves recall by 0.025, so a headline gap of 0.028 nDCG was one to three questions’ worth and could not be told from noise. The report therefore carries:

  • A 95% bootstrap interval on every headline metric (recall@k, MRR, nDCG@k, grounded-recall@k, stale>current, false-pos@k), overall and per category. The method is a percentile bootstrap over questions: resample the scored questions with replacement 10,000 times, take the mean of each resample, and report the 2.5th and 97.5th percentiles. Each metric is resampled over the questions where it is defined (negatives are not part of nDCG; only temporal questions have stale>current), so n differs by metric.
  • Paired comparisons. For every pair of configurations that ran, the difference in per-question nDCG@k (a − b) gets its own bootstrap interval, joined by question id (a configuration with failed queries has fewer rows, so positional pairing would be wrong). If the interval includes zero the row reads “not distinguishable from noise”; a winner is only named when the top configuration’s paired interval is wholly above zero against every other configuration. The JSON carries the same comparison for recall@k. No multiplicity correction is applied across the many pairs shown; treat one isolated “significant” pair among many with suspicion.
  • Hypotheses H1/H2 use the same rule: the best lcg-* and best qmd* configuration (by point estimate) are compared on the category’s nDCG@k, and the reading is YES, NO (the opposite is established), not distinguishable from noise, or cannot be read.
  • Low-n and ceiling labels. A category with fewer than 20 questions is flagged “low n”, and its (visibly wide) interval is printed anyway. When every configuration scores nDCG@k ≥ 0.98 in a scope, the report says it is at the ceiling and does not rank the configurations there. Where fewer than two questions are scored the interval is n/a, never a zero-width interval.
  • Reproducibility. The seed (default 788), resample count and level are printed in the report and in report.json (bootstrap). Each interval is seeded from the base seed XOR an FNV-1a hash of config|category|metric, so adding a configuration changes no other interval, and two runs over the same per-question scores are byte-identical. Change them with --bootstrap-seed and --bootstrap-resamples (e.g. --bootstrap-resamples 1000 for a quick look).

Bold in the tables marks the best point estimate. It is not by itself a finding; read the paired comparison beneath each table.

By origin of returned notes (fixtures that declare origins)

Section titled “By origin of returned notes (fixtures that declare origins)”

Real notebooks contain agent-maintained pages that restate human notes. Origin (ADR-0752) is stamped on each note at ingest, so a derived page cannot corroborate itself. When a fixture declares origins, the report adds a section that shows how each configuration treats those restatements. The definitions are fixed so the numbers are comparable between configurations:

  • A restating note for a question is a derived note whose cites contains one of the question’s relevant primary notes and which is not itself in the question’s relevant_notes.
  • A question is eligible if it is not a negative and has at least one restating note.
  • Restating share@k: the mean, over eligible questions, of the fraction of the returned top-k that are restating notes.
  • Outrank rate: over eligible questions where both a relevant primary note and a restating note were returned, how often the best-ranked restating note sits above the best-ranked primary note (the pair count is shown).
  • Derived-only rate: over eligible questions, how often a restating note was returned and no relevant primary note was.
  • Returned top-k by origin: the share of all returned results that are primary, external, derived, answer or undeclared, over non-negative questions.

Each rate carries a bootstrap interval. v1 declares no origins, so it never prints this section.

Result mapping (identical for every configuration)

Section titled “Result mapping (identical for every configuration)”
  • Passage → note: source_description is "{note}:{chunk}".
  • Entity → notes: every note whose episodes mention the entity (built once at ingest).
  • Fact → notes: the fact’s producing episodes (episodes). ADR-0012’s either-endpoint inference is never used.
  • qmd result → note: the result path’s file stem.

Query variants (lcg-passages-variants)

Section titled “Query variants (lcg-passages-variants)”

A paraphrase question describes a thing instead of naming it, so it shares few words with the answer note. An agent calling knowledge_search_passages can supply its own rewrites as queries (IPC reference). The eval simulates that agent from a fixture, query-variants.jsonl, with up to 5 variants per question id. An LLM writes them seeing only the question text (no corpus, notes or relevance labels) under the prompt committed beside the fixture, query-variants.prompt.md. It is a one-time maintainer step, never run in CI:

The fixture is stamped with the questions hash; the eval refuses a stale one. Leak check: a variant that contains, verbatim, the title (first # heading, whole or without Notes on / Q&A: ) or a key-fact string of any note relevant to its question fails, naming the question and variant. Matching is case-insensitive, needles under 8 characters are skipped, and text the question itself already contains is not a leak. It catches verbatim leaks only, not paraphrased ones. With no query-variants.jsonl, the lcg-passages-variants row is reported as skipped.

The committed v2 fixture (244 questions, 1,194 variants) was written by Sonnet 4.6 from each question’s text alone through this exchange; --check finds no leaks. About one variant in ten is a hypothetical answer with a placeholder ([date], [Name]), which adds a noise token and will not match note text.

That fixture predates the current query-variants.prompt.md, which since added the rules to keep every named entity and to send no placeholders. The fixture does not follow them (about 41% of multi-hop variants omit the anchor entity), and it is not reproducible from the committed prompt, because replies are keyed by a hash of the system prompt. It will be regenerated and re-measured with #797’s composite search.

Every variants config sends the same request as its base config plus queries, so each query runs that pipeline (vector, or BM25 + vector) and the per-query rankings are fused (primary weight 2, the variants sharing a total of 1). The report’s “Query variants vs <base>” section, one per variants config (lcg-passages-variants against lcg-passages, lcg-passages-hybrid-belief-variants against lcg-passages-hybrid-belief), gives per-category paired nDCG@k differences with intervals, p50/p95, and the merge-bar reading: paraphrase interval above zero, no category wholly below zero. Latency is reported, not gated: variants are deliberate agent searches.

First v2 result (vector-only, per-variant weight 1, head a0c7e95f): variants lowered overall nDCG@10 from 0.568 to 0.522 (paraphrase 0.150 to 0.085, multi-hop 0.662 to 0.552, p50 24 ms to 141 ms). That is why variants now run the request’s whole pipeline, share a fixed weight budget and fuse concurrently (ADR-0802).

Second v2 result (head 87c85525, that design): overall +0.011 (vector) and +0.017 (hybrid), within noise; passage +0.117 and +0.112, hybrid paraphrase +0.082 [+0.017, +0.153], and multi-hop -0.062 [-0.107, -0.026] (vector) and -0.059 [-0.097, -0.027] (hybrid). The multi-hop loss is a known regression with the committed fixture, caused mostly by correlated variants voting together for generic distractors; entity-preserving variants are the planned mitigation (ADR-0802).

Caveats the report repeats

Section titled “Caveats the report repeats”
  • LCG and qmd use different embedding (and reranker) models, so this compares systems, not retrieval algorithms.
  • Both corpora are synthetic. v1 is small and hand-built (results are indicative, not general). v2 is larger and synthetic: its structure is generated and its prose is written by an LLM, so it is more uniform than a real notebook’s and direct questions may sit near the ceiling. The report prints the matching caveat, and says explicitly when a category is at the ceiling.
  • LCG ingestion is only deterministic with a replayed extraction cassette; qmd’s expansion and reranking depend on their models. Relevance metrics are exactly reproducible for a fixed LCG graph and embedder.
  • The hypotheses (“LCG beats qmd on temporal/superseded questions”; “qmd beats LCG on paraphrase questions”) are read from the data with the paired-interval rule above (yes, no, not distinguishable from noise, or cannot be read). They are not assumed.
  • Temporal questions about a decision revised by a plain later note (no supersession) measure retrieval-level recency handling only: LCG’s supersession state cannot help there, so those questions can favour systems that rank by text alone. That is the intended signal.

v1 (smoke)

Section titled “v1 (smoke)”

fernhill-notebook-1 is a notebook for a fictional bike-share co-operative with 8 decisions that a later note explicitly replaces. It stays as a fast smoke test: every note fits in one chunk, so it cannot exercise chunking, long-note recall or passage choice, and with 40 judged questions one question is 0.025 of recall. Its content and hashes never change.

v2 (realistic)

Section titled “v2 (realistic)”

meridian-notebook-2 is a fictional cooperative’s notebook shaped like a Liminis workspace:

  • Size mix (target words): 302 notes under 250 words, 22 of 250–500, 78 of 500–2,000 and 6 over 5,000. The long notes are weekly digests and journals with a handful of facts buried in otherwise generic text, so choosing the right passage inside a note is exercised.

  • Origins: human notes (primary), clipped articles (external, some carrying a vendor’s public list price), agent-maintained entity and decision pages (derived, each citing the notes it restates), and filed answers (answer). 56 derived pages restate facts from primary notes, so “the wiki citing itself” is present; some lag and restate a stale decision.

  • Near-duplicates: each entity’s facts are restated by its derived page and, for 16 facts, by a primary standup recap. Ground truth lists the recap at gain 1 beside the source at gain 2; the derived restatements are never relevant (the per-origin report shows how often they outrank the source). The generator completes every non-negative question’s relevant set from the skeleton: any other non-derived, non-stale note that states one of the question’s basis facts (any hop, for multi-hop) is added at gain 1, so a system returning a correct near-duplicate (a recap, a digest, a filed answer) is not scored wrong for it. The check step fails a rendered fixture in which such a note is left out.

  • Time: 26 decisions, each revised 2–4 times (3–5 notes), with explicit knowledge_supersede_document revisions (45 supersessions) and plain later notes that contradict the earlier one without superseding it. Several effective dates differ from the recording date. Explicit supersessions are primary→primary only, because ADR-0752 refuses a derived page superseding a primary note.

  • Questions (target and minimum 30 per category):

    CategoryCountWhat it asks
    direct40A fact stated in one note. 6 are about a clipped article’s figure.
    paraphrase40The same kind of fact, asked without lexical overlap with the source (see below).
    temporal40The current value of a revised decision (20 chains end in an explicit supersession, 20 in an implicit contradiction; 14 are re-asked with different wording).
    answer30A fact with a key-fact evidence entry for grounded judging; the filed answer is a gain-1 relevant note for half of them.
    multi-hop30Needs two notes: a project’s supplier then the supplier’s attribute (15), or compare two projects’ budgets (15).
    passage30One fact buried in a paragraph of a long note, always beyond the note’s first chunk, with the key fact as evidence.
    negative34No note answers. 17 ask about an entity that does not exist but is named like ones that do (Cedar Labs beside Cedar Core); 17 ask a real entity for an attribute its kind never has.

    At 244 questions a single question moves recall by at most 0.0125 in aggregate (v1: 0.025).

Paraphrase rule. The checks count a question’s content words (lowercase, longer than three letters, minus glue words like what and does) and requires at most 25 % of them to appear in the fact sentence and at most 50 % in the whole relevant note. The skeleton builder replaces a candidate whose plain wording fails from a reserve; the same bound is checked again on the rendered wording and the rendered note. Note-side and question-side wordings of every domain, kind and attribute share no content word by construction (billing vs invoicing and payment collection).

Negatives are unanswerable by construction and verified. A fake entity is checked to appear in no note; a real entity asked for an attribute its kind never has is checked never to share a note with that attribute’s marker words. Both are checked against the skeleton when it is built and again against the rendered text. The near-miss distractors (same family name, same attribute) are present in the corpus.

Limitation. An LLM writes the prose, so notes read naturally and paraphrase questions are not template paraphrases, but one model with one prompt still writes everything: the corpus is more uniform than a real notebook, and direct questions may be at the ceiling for both systems. That is reported, with intervals, not hidden. Use the private-notebook run below as a cross-check.

How v2 is built: skeleton, then render, then check

Section titled “How v2 is built: skeleton, then render, then check”

v2 is built in two steps so that structure is reproducible and prose is natural.

  1. Skeleton (deterministic, free). lcg-eval retrieval-gen turns the checked-in scenario.json (seed and quotas) and the fact model in code into skeleton.json: entities and facts, which note carries which facts (and, for long notes, in which section), each note’s origin, reference time, target length and citations, the explicit supersessions with effective dates, and every question’s ground truth (relevant notes, gains, evidence key facts, current/stale). Same scenario and seed give a byte-identical skeleton (hand-rolled SplitMix64, no clock, no network, no model).
  2. Render (explicit, paid, once; a maintainer step). lcg-eval retrieval-render has an LLM write every note in the voice its origin implies (journal, decision record, standup recap, clipped article, agent topic page with citations, filed answer) and every question’s wording, paraphrase questions included. It writes manifest.json (generated from the skeleton), notes/*.md, questions.jsonl, questions.meta.json and render.json (render model, prompt version, skeleton hash). The rendered output is checked in; CI and normal eval runs never call a model, and there is no template fallback for the checked-in fixture. A long note is rendered section by section so each fact lands in the section the skeleton assigned it.
  3. Checks (free, in cargo test and retrieval-gen --check). They verify the checked-in text against the skeleton rather than regenerating it: every skeleton fact appears in its note (entity name and value verbatim); evidence key facts are findable in their notes; a passage fact sits in a later chunk of a multi-chunk note; a note names no entity other than its own; an implicit revision does not mention the earlier value and an explicit one states its effective date; derived and answer pages carry their [[citations]]; questions keep the names they must (and a paraphrase names none); the paraphrase lexical-overlap bound holds on the rendered wording against the sentence carrying the fact and the whole note; and negatives remain unanswerable. manifest.json and the question ground truth must equal what the skeleton generates (only the wording may change), and render.json must name the current skeleton.

--model (default the judge model) is recorded in render.json. A crashed run continues with --resume. Re-rendering changes the corpus: bump corpus_version and questions_version in scenario.json, regenerate the skeleton, then render. A change to the skeleton makes a test fail until skeleton.json is regenerated. The order is: freeze the generator → generate the skeleton → render → review → record the cassette.

Current status. No model key was available when this was implemented, so the checked-in v2 is the skeleton only: it has not been rendered, and lcg-eval retrieval --corpus …/retrieval-v2 stops with a message saying so. Rendering, the question review and the cassette are maintainer steps. The Rust tests exercise the whole pipeline (checks, loader, ingest, report) against a template-prose test double built in a scratch directory; that prose is never checked in, and a test fails if a checked-in render.json names it.

Human review of the questions

Section titled “Human review of the questions”

review.json is a template that lists a seeded, stratified sample (6 questions per category, 42 in all, at least 10 % of the set) with three verdicts per question: ground truth correct, note relevance correct, key fact correct, plus the reviewer, date, error rate and the question-set version and hash. The checked-in record is pending with empty verdicts: no human has reviewed it, and neither the generator nor the renderer ever writes verdicts. After rendering, retrieval-render fills questions_hash and each sampled question’s text (only while the record is pending; a record marked reviewed is never modified) so the reviewer can read the questions in one place. The fixture counts as reviewed only once a maintainer fills every verdict, sets status to reviewed, and records reviewer, reviewed_on and error_rate (the share of sampled questions with any false verdict). If the rate exceeds error_rate_threshold (default 5 %), correct or regenerate the affected categories and re-review. A test checks that the sampled ids exist, every category is covered, the record names the current skeleton and (once rendered) the question set’s hash, that a pending record has no verdicts, and (when reviewed) that every verdict is filled and the error rate agrees with them.

Recording the v2 cassette (free re-runs)

Section titled “Recording the v2 cassette (free re-runs)”

Ingesting v2 means one knowledge_process_chunk call per chunk (several hundred once rendered; the dry run prints the exact number), each at least one extraction-LLM call. Record them once and replay forever (cassettes: ADR-0044):

After that, 07-retrieval-eval.sh --corpus crates/eval/fixtures/retrieval-v2 replays <corpus>/cassette.jsonl automatically (or set LCG_EVAL_REPLAY_CASSETTE) and makes zero extraction requests. The cassette is keyed by extraction input, not by corpus hash, so if the corpus changes, the changed chunks fail loudly with a cassette miss that names the note and chunk and the run stops; nothing falls back to a live model. The cassette is recorded against the corpus hash the report prints (hash in the report header, after rendering); write that hash next to the file when committing it. Expect a few MB; if it is too large for the repository, keep it in external storage and set LCG_EVAL_REPLAY_CASSETTE instead of using the sidecar path. Section titled “Question format”
FieldRules

Paraphrase questions deliberately share little vocabulary with the relevant text.

Ingest concurrency

Section titled “Ingest concurrency”

A live extraction of the v2 corpus takes hours because the harness used to send one knowledge_process_chunk at a time, while the extractor endpoint sat mostly idle. --ingest-concurrency N (also accepted by retrieval-score-probe) keeps up to N calls in flight, each on its own connection to the service (it serves one request at a time per connection). A re-extraction takes roughly 1/N of the time, bounded by the endpoint’s capacity; through --extractor-uds / --embedder-uds the service’s own sidecar pools hold 4 connections, so N above 4 gains nothing there. Results do not depend on completion order: per-chunk results are folded in manifest order, a failed chunk still fails the run with its note id and chunk index (the earliest one in manifest order if several fail), and supersessions, the index build and the entity-link pass run only after every chunk has finished. At N = 1 the run is unchanged: same call order, same metrics, same digests (report.json meta only gains the ingest_concurrency key). The value used is in report.md (Reproduction) and in report.json meta.ingest_concurrency; it is not part of the inputs digests. A pool’s per-call timeout is 900 s times ceil(N / 4), because a call’s clock also counts time queued inside the service. If a chunk fails, calls still in flight are abandoned: the service cancels those not yet committing and finishes any commit already started, and lcg-eval stops it with knowledge_close before exiting. With --keep-workspace, the manifest records ingest_concurrency when it was above 1 (and graph-qa notes it), so a workspace built concurrently is not compared as like for like.

Caveats at N > 1:

  • Live graphs can differ from run to run, and from N = 1. Entity summaries are consolidated against whatever the graph holds when a chunk is processed, and the service resolves entities without a lock between chunks, so two chunks that mention the same new entity can each insert it (ADR-0029). Expect order-dependent summaries and the occasional extra duplicate entity. Do not compare an N > 1 run against an N = 1 baseline as like for like.
  • A cassette recorded at N > 1 is order-dependent. --record-cassette still works, warns, and marks the sidecar C.meta.json with ingest_concurrency and order_dependent: true. The extract and classify_* entries replay exactly, but the consolidate_summary and judge_duplicates keys hash graph state that depended on commit order. Measured offline (ADR-0900: four chunks sharing one entity, recorded with all in flight, replayed one at a time): 0 extract misses, 0 classify_* misses, 3 of 3 consolidate_summary misses. The service swallows those misses (bounded fallback, an stderr line), so such a replay finishes with exit 0 and a possibly different graph; the eval has no miss counter. Record at the default N = 1 when you need a cassette that replays exactly.
  • Replay always runs at N = 1. With --replay-cassette, --ingest-concurrency is overridden with a warning, and the report states the value actually used (meta.ingest_concurrency) next to what you asked for (meta.ingest_concurrency_requested). Replaying an order_dependent cassette also warns.

Comparing two runs

Section titled “Comparing two runs”

--compare reads the earlier report before anything is started or spent, runs the new evaluation, writes this run’s report.md / report.json, and then judges comparability (so a refusal never discards a finished run). It prints per-config and per-category nDCG@k deltas, and writes them to compare.md beside the report when --out is set.

KindInputsWhen they differ
Hardinputs.corpus, inputs.questions, kExit 2 naming every differing hard input. No deltas are printed and no compare.md is written.
Softvariants, cassette, embedder_model, extractor, service_binary, service_env, meta.lcg_build (the service build), meta.ontology_hashThe deltas are printed under a banner listing each changed input. With --strict, exit 2 instead.

Per-question ranked lists

Section titled “Per-question ranked lists”

--record-ranked writes ranked.jsonl beside the report: one line per config and scored question,

hits are the service’s passages in response order, before the note de-duplication the metrics use. score is the config’s own ranking score, similarity is present only in hybrid mode (absent for a lexical-only hit), and legs (dense, lexical or both) is present when the service supplies it (hybrid mode, service build with #871 or later); a field the service did not supply is omitted, never null. Comparing embedding profiles

Section titled “Comparing embedding profiles”

Asymmetric embedders (BGE, nomic, e5) are trained with role prefixes. --embedding-profile runs the LCG configurations under each named profile so the report shows the difference side by side:

With more than one profile, each LCG configuration appears once per profile as <id>@<profile> (for example lcg-passages@none and lcg-passages@bge-v1.5), and every profile runs in its own fresh workspace with a fresh ingest — a document-prefix change means a re-embed, so vectors are never reused across profiles. Comparing the passage stages (rerank and query expansion)

Section titled “Comparing the passage stages (rerank and query expansion)”

Four opt-in configurations measure the optional stages of knowledge_search_passages (ADR-0796); each is switchable and measured on its own:

ConfigStages
lcg-passages-rerankrerank only
lcg-passages-expandquery expansion only
lcg-passages-belief-rerankrerank over a belief-aware first stage (belief_aware: true with rerank: true)
lcg-passages-expand-rerankexpansion, RRF fusion, then rerank

Since #806 lcg-passages is the shipped belief-aware default, while lcg-passages-rerank, -expand and -expand-rerank pin a raw cosine first stage (belief_aware: false); lcg-passages-raw is the matching un-staged baseline and lcg-passages-belief-rerank is the stage over the belief-aware first stage. The report’s Passage stages section pairs each stage with the baseline that has the same first stage (lcg-passages-raw, or lcg-passages-belief for lcg-passages-belief-rerank) when that baseline ran, and falls back to lcg-passages otherwise, so include lcg-passages-raw (and lcg-passages-belief) in --configs for an isolated stage delta. All baselines send rerank: false, expand: false.

They are not in the default configuration list: they need a reranker (and for expansion an LLM) reachable from the spawned service, which is normally the CoreML sidecar started with a rerank model (see native/local-inference/README.md).

A stage that was requested but did not apply (sidecar down, model absent) is reported as a failed query, never scored as if it had run — the service degrades to first-stage results, and scoring those under the stage’s name would silently report lcg-passages numbers. The report’s Passage stages section gives, for each stage, the paired nDCG@k difference against the matching un-staged baseline (lcg-passages-raw / lcg-passages-belief, else lcg-passages) per category with a 95% bootstrap interval (and expansion on top of lcg-passages-rerank), plus the four rerank acceptance checks: paraphrase gain with an interval above zero, overall not lower, temporal interval including or exceeding zero, and p50 ≤ 150 ms. Take acceptance numbers only after #790 (embedding roles) is in the build under test, and hybrid BM25 + vector (#789) has landed, but the eval has no configuration for rerank or expansion on top of hybrid yet, so that half of the comparison is still to be done.

When to use each stage

Section titled “When to use each stage”

Rerank is measured; expansion is not yet. The maintainer’s v2 and v1 numbers (Apple silicon, mxbai Core ML model) are in ADR-0796: lcg-passages-belief-rerank scores 0.759 nDCG@10 on v2 against 0.653 for lcg-passages-belief (+0.106 [+0.073, +0.142]) and 0.935 against 0.894 on the v1 holdout, at about 1.9 s p50 (not the 150 ms budget).

  • Rerank is aimed at paraphrase questions (a role or description instead of a name). Its blend keeps superseded notes below their replacements, so it is designed not to repeat qmd’s temporal collapse (qmd-rerank 0.293 vs lcg-passages 0.628). Measured on v2 with the belief-aware first stage, temporal is 0.800 against 0.745 for lcg-passages-belief (the 0.85 target was not reached; accepted as a follow-up), so it does not collapse. Use it for deliberate searches by role or description, not search-as-you-type (about 1.9 s p50 at the default 50 candidates).
  • Query expansion is expected to cost on the order of a second (unmeasured). It is recommended only if the measurements show it improving some category with a paired interval above zero beyond what rerank already gives; if no category justifies it, the ADR says so and it should not be used. Either way it is for deliberate agent searches, never search-as-you-type.

Reading the report

Section titled “Reading the report”
  • Overall and per-category tables: every configuration’s metrics as point [lo, hi], with the best point estimate per column in bold and the number of questions behind each mean. Under each table, a paired nDCG@k comparison, and a line that names a winner only if it is distinguishable from every other configuration, else says “not distinguishable from noise”. Low-n and at-the-ceiling categories are labelled.
  • By origin of returned notes (fixtures that declare origins): how often derived restatements are returned and outrank the primary source.
  • Hypotheses: YES, NO, not distinguishable from noise or cannot be read (a side was skipped) for “LCG beats qmd on temporal/superseded” and “qmd beats LCG on paraphrase”.
  • Cost, Reproduction (corpus/question versions and hashes, LCG build, qmd version and models, embedder, extractor, judge model, k, latency convention).

Running on a private real notebook

Section titled “Running on a private real notebook”

Synthetic corpora approximate a real notebook. To sanity-check on yours, run the same harness over your own notes with a question set you write locally, and report results only: nothing from the notebook or the questions is checked in or written into the report.

  1. Make a fixture directory outside the repository (for example ~/eval-private/mynotebook) in the same format: notes/<id>.md (copy or symlink your markdown files; ids are lowercase slugs), a manifest.json listing the notes in the order to ingest them, and a questions.jsonl in the format above. A minimal manifest needs only {"corpus_version": "private-1", "notes": [{"id": "..."}, ...]}; add reference_time and, if you want the origin analysis, origin/cites. Write the questions yourself, including a few negatives.

  2. Run with --private and with the output and judge cache outside any git tree:

    or lcg-eval retrieval --private --corpus ... --out ... --judge-cache ... (use --no-grounded to skip the judge and its cache).

  3. What --private does. It requires an explicit --out (and --judge-cache unless --no-grounded) and refuses any such path, and any --record-cassette or --keep-workspace path, that is inside a git working tree (it looks for a .git above the path), so private text cannot land in a commit. The report’s disclaimer says the corpus is a private notebook, not a synthetic one. The report contains aggregate metrics, counts, versions and hashes only: it never prints note or question text, and the detail of a failed query is withheld (id: error (detail withheld)) because a service error can echo the query. The judge cache does hold key facts and returned note text, which is why it must live outside the repository, and why running without --private from the repository root would write it there by default (retrieval_evidence_cache.jsonl in the working directory).

  4. qmd keeps its own index of your notes under its usual location; remove it afterwards (qmd --index <name> collection remove <name>) if you do not want it to persist. Nothing in the repository is created or modified by a private run.

The same statistics apply: with a few dozen of your own questions the intervals will be wide, and the report will say so.

Ingesting under an ontology and keeping the workspace (#821)

Section titled “Ingesting under an ontology and keeping the workspace (#821)”

Graph-shaped questions are answered from a graph extracted under an ontology, and graph-quality tools (graph-integrity, graph-qa) read an ingested workspace. lcg-eval retrieval does both:

FlagMeaning
--ontology <FILE>Every extraction call is constrained by this ontology. It is written into the workspace as .lcg/ontology.yaml, which is where the service reads it.
--ontology-mode open|strictThe mode applied to the ontology (default strict, as in the extraction eval). It needs --ontology. The mode is part of the ontology hash.
--keep-workspace <DIR>After the run, the service is shut down gracefully (knowledge_close) and the ingested workspace (DB, WAL, ontology) is moved to DIR, with an lcg-eval-workspace.json manifest. DIR must not exist or must be empty. It takes one --embedding-profile at most, and needs at least one lcg-* config in --configs (a qmd-only run ingests nothing into LCG). Without the flag the temporary workspace is removed, as before.

The ontology hash. The report records the ontology’s hash and mode in its Reproduction block and in meta.ontology_hash / meta.ontology_mode. It is lcg_core::ontology::content_hash, the hash LCG already computes; a run without an ontology records none. The value is the one the service reports (knowledge_get_ontology.ontology_hash for the eval group), not the staged file’s: the spawned service is always given the eval workspace through LIMINIS_WORKSPACE_ROOT (overriding any value in your shell), and right after startup lcg-eval checks that the service loaded the staged ontology. If the service has no ontology, a different one, or is an older build that reports no hash, the run exits non-zero before any ingest with an error naming both hashes (#881). graph-qa applies the same check when its workspace has an ontology (the eval group’s .lcg/ontology/retrieval-eval.yaml, else .lcg/ontology.yaml). The cassette sidecar and the kept-workspace manifest also record the service-reported hash.

The cassette check. A cassette’s records carry no ontology, so --record-cassette C also writes C.meta.json with the hash it was recorded under (none without an ontology). Replaying C under a different hash (another ontology, another mode, or no ontology at all) fails before the service starts. The error names both hashes, and no extraction call is made: without the check every call would miss. A cassette recorded before this change has no sidecar. Replaying it with --ontology prints a warning that the hash cannot be verified and carries on.

The manifest. lcg-eval-workspace.json records how the workspace was built: group, corpus version and hash, ontology hash and mode, embedder (any userinfo, query or fragment stripped from its URL, so no credential is written to disk), embedding profile, extractor, cassette and LCG build. graph-qa refuses a workspace whose embedder differs from the one it is given (exit 3). The addresses are compared after normalising loopback aliases (localhost, 127.0.0.1, [::1]), case and a trailing slash; --allow-embedder-mismatch downgrades a remaining mismatch to a warning, for the same embedding model reached at a new address (a relocated socket, say). A genuinely different embedder would make the stored vectors incomparable and the numbers silently meaningless.

Graph question answering (graph-qa, #821)

Section titled “Graph question answering (graph-qa, #821)”

lcg-eval graph-qa answers the retrieval-v2 graph question set over a kept workspace and compares how each retrieval route serves a reader. It is the reproducible form of experiment E13 (#815) and the regression check for knowledge_walk (#820).

The graph question set

Section titled “The graph question set”

crates/eval/fixtures/retrieval-v2/graph-questions.jsonl is generated from the skeleton by retrieval-gen, and retrieval-gen --check reports any drift. It has 144 questions. The gold is the skeleton’s facts plus the prose-introduced facts in prose-facts.json (see below):

  • E13 (set: "e13", ids g000–g128): 129 questions, the same as the E13 reference question for question. By shape: chain-2 48, chain-3 24, list 31, join 14, history 12. They fall into 13 finer families, such as supplier-contact, owner-manager-location and change-history.
  • Inverse (set: "inverse", shape: "inverse", ids i000–i014): 15 new questions that ask for the source side of a relation given its target, so the answer depends on edge direction:
    • reports-to-single: “Who reports to X?”, for managers with one report;
    • account-manager-of: “Which suppliers is X the account manager for?”;
    • projects-of-reports: “Which projects are owned by someone who reports to X?”.

Each line carries id, set, family, cq, shape, text, answers (ordered for history), scoring (single, set or ordered), split (dev or test), hops (the facts a complete answer rests on, with every primary note stating each value), path (the expected relation types and directions, for later path-level analysis) and, only where the prose is ambiguous, optional_answers.

Prose-introduced facts (#907). The v2 prose was rendered by an LLM from the skeleton, and it introduced two project owners the skeleton does not contain, both in notes/journal-04.md. A system that reads the corpus correctly returns them, and gold derived from the skeleton alone would score that as a precision loss. crates/eval/fixtures/retrieval-v2/prose-facts.json records such facts (entity, attribute, value, notes, status) and retrieval-gen reads it:

statusMeaningEffect
statedThe prose states it unambiguously.Treated as a skeleton fact when deriving answers for the list (owned-by), join (projects-by-owner-city) and inverse (projects-of-reports) questions.
ambiguousThe wording supports it but does not settle it.Added to the question’s optional_answers, not answers.

The initial entries are Telemetry clean-up (Owner: Marcus Haddad, stated: “will continue with Marcus Haddad as owner”) and Routing handover (Owner: Priya Varga, ambiguous: “led by”). They change answers on g072, g109 and i014 and optional_answers on i013, and nothing else. hops stay skeleton-derived, the overlay never adds or reselects a question, and generation fails for an entry with an unknown status, an unsupported attribute, an unknown owner, an unknown note, a cited note whose rendered text does not name both the entity and the value, a repeated (entity, attribute), or an entity that already has a skeleton Owner or that equals a skeleton entity only after normalising case and punctuation (a typo). Names compare through the scorer’s norm. The gold depends on the file, so questions.meta.json records its prose_facts_hash and retrieval-gen --check fails when the file changes without that hash: bump questions_version, regenerate and record the new hash together.

Scoring optional answers. For set questions, a returned answer that equals an optional answer after normalising case, punctuation and spacing (and matches no gold answer) is dropped before precision, and recall is over answers alone. So an optional answer neither raises nor lowers the score, whether the run returns it, omits it or repeats it. Optional answers match by equality, not containment: a fragment of one (“Routing”) or a longer string containing it is a wrong answer and counts against precision. single and ordered scoring ignore optional_answers. The per-question graph-qa report rows carry optional_answers where there are some, so an extra answer that cost nothing can be explained. The set was meridian-questions-3 before this change and is meridian-questions-4 after it: graph-qa scores from the two are not comparable for g072, g109, i013 and i014 (the report itself records no question-set version).

Dev/test split. The split is fixed, with seed 815. For each family, in order of first appearance, its ids are shuffled with one shared random.Random(815), and the first half (rounded up) is dev. The E13 part gives the reference 67 dev / 62 test. The inverse family is split the same way, from its own Random(815). Questions are chosen with Python-compatible RNGs (a Rust MT19937) so the E13 set matches the probe exactly.

Running it

Section titled “Running it”

The workspace is copied to a temporary directory and the service runs on the copy. The workspace itself, including its WAL, is never modified.

--corpus <DIR>crates/eval/fixtures/retrieval-v2The fixture; qmd reads its notes.

Exit codes:

  • 0: the run succeeded.
  • 1: the run failed (service, model provider or I/O), or a runner’s reader replies failed to parse more than 10% of the time. Unparseable replies score 0, so a reader that answers in prose (a provider or bridge that ignores output_config.format) would otherwise yield an all-zero report that looks like a measurement. The report is still written; its Overall section and stderr give the parse-error count per runner. --allow-reader-errors turns this failure into a warning.
  • 2: usage error.
  • 3: unusable workspace (missing, not ingested, or an embedder mismatch).
  • 4: questions without a plan, and no planner may be called. With no model provider configured, a planner response already in --llm-cache still counts as a plan, so a fully cached rerun works offline; only questions with no recorded or cached plan are uncovered.

Runners

Section titled “Runners”
RunnerContext given to the reader
passagesThe shipped default knowledge_search_passages, top k, as Passages from the notes: followed by [note, date] blocks.
passages-belief-rerankThe same, reranked over a belief-aware first stage. It needs a reranker, and a stage that did not apply fails the run rather than being scored as first-stage results.
qmdThe whole note for each qmd hit (E13 step 3). It is skipped with a notice when qmd cannot run, as retrieval does.
walkAn LLM planner sees only the question and the workspace’s knowledge_get_ontology menu (no family, no gold). It returns {route, start, hops: [{types, phrase, direction}], list, history, answer_type}. The plan runs through knowledge_walk, mapped as follows: types → relation_types, mode history / list / single, direction_mode: soft, and query set to the question. The reader gets Facts from the knowledge graph: followed by the walk’s facts_text, or (none found).
routeThe planner’s route for each question: passages context when it routes to passages, otherwise the walk’s context. This is E13’s “route v5”.

One plan per question serves both walk and route. A plan is a plan error in these cases:

  • it does not parse;
  • it names an unknown route or direction;
  • a hop’s relation type is not in the ontology;
  • its answer_type is neither an ontology entity type nor value;
  • a graph route has no hops.

The question is then answered from an empty walk and counted; it is never re-planned. A start entity that matches no node is counted as unresolved, and the question scores 0.

The reader and scoring

Section titled “The reader and scoring”

Every runner’s context goes to one reader prompt, ported word for word from the probe (e13-read-v1); the user turn is <context>\n\nQuestion: <text>. The planner prompt is the probe’s v5 (e13-plan-v5). Both versions are recorded in the report. Identical prompts are sent once, so the same context always gets the same answer.

Scoring is the probe’s score(). Answers are normalised first: lowercased, runs of characters other than letters, digits, %, $ and . become a space, and spaces and dots are stripped from the ends. An answer matches a gold value when it contains it, or when the answer has 3 or more characters and the gold contains the answer.

  • single: 1 when the first answer matches, else 0.
  • set (lists, joins, many-valued inverses): set F1.
  • ordered (history): 1 only for the same number of values, each matching in order.

Plans files and caching

Section titled “Plans files and caching”

A plans file has the probe’s v5-plans.json format:

  • top-level model, ontology and planner_prompt;
  • plans, keyed by question id;
  • optional route_planned5_scores, which the report shows as a reference.

Plan ids that name no question are ignored and listed as warnings. Questions the file does not cover (the inverse family, for e13-v5-plans.json) go to the planner, unless --plans-only is set.

Planner and reader responses are cached in --llm-cache. Each entry is keyed by sha256 of the model, system prompt, user prompt and schema, and is written as it arrives. Any change to a prompt byte or the model is a cache miss. A fully cached run makes no model call and gives byte-identical scores. A provider failure aborts the run rather than scoring the remaining questions as wrong, and a rerun resumes from the cache.

The report

Section titled “The report”

graph-qa.md and graph-qa.json contain:

  • Overall: the mean score per runner on E13, its dev and test halves, and all questions (E13 plus inverse) with their halves. The E13 numbers stay comparable with E13.
  • By shape: chain-2, chain-3, list, join, history and inverse, for all questions and for each half.
  • By family: a secondary table.
  • Paired differences: for every pair of runners, the mean difference with a 95% paired bootstrap interval, over E13, all, each half and each shape.
  • Diagnostics: routes by shape, plan sources (file or planner), plan errors and unresolved starts by shape, reader responses that did not parse, plans-file warnings and the plans file’s reference scores.
  • Per question: route, plan and its source, whether the start resolved, answers, gold and score.
  • Reproduction: the workspace’s ontology hash and manifest, the models, prompt versions and cache counts.

In graph-qa.json, everything the questions, plans and responses determine is under scores. Run facts such as cache counts are under meta.

Graph-QA numbers (E13 and later) are produced this way, and only this way:

  1. Ingest v2 under ontology v3.1 and keep the workspace, with the BGE embedder the passage numbers use:

    Replaying that cassette later reproduces the same graph without extraction calls.

  2. Run graph-qa with the recorded E13 v5 plans:

Out of scope

Section titled “Out of scope”

This eval measures retrieval; it does not change it. Query expansion, position-aware reranker blending and an explain trace are follow-up work that plugs in as new configurations. Context assembly baselines (#734), document mode (#733) and retrieval restricted to primary sources (#752) are separate. Design record: ADR-0754.
