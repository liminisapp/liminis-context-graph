Graph-Integrity Evaluation

lcg-eval graph-integrity is a deterministic report on the graph an ingest produced. It reads the nodes and edges of an ingested workspace and scores them against a fixture’s skeleton.json, the ground truth the fixture was generated from. No LLM, no judge, no network and no extraction provider is involved, and the workspace is never written.

Why it exists

Section titled “Why it exists”

The retrieval evaluation (retrieval-quality-evaluation.md) scores passage ranking (nDCG over notes). That path never reads an edge’s type, direction or endpoints, so a badly wrong graph can score well. It happened: about a third of typed edges on known-true links pointed the wrong way (#816) and no test or eval had flagged it. This command makes typing, links, direction and value-fact attachment into numbers, so a fix can be shown to move them.

It measures. It does not repair anything.

Running it

Section titled “Running it”

The input is a workspace directory that a service has ingested into. The usual source is lcg-eval retrieval --keep-workspace <DIR> (#821), which keeps the ingested workspace (with --ontology <file>, one built under that ontology) instead of removing its temporary workspace; see Ingesting under an ontology and keeping the workspace. The command accepts any workspace whose DB a service could open.

Workspace ontology default. The group’s own .lcg/ontology/<group>.yaml wins, then the workspace-wide .lcg/ontology.yaml (the order the service resolves it); with neither, the graph is treated as free-form and the fit section is not applicable. The report states which one was used.

Exit codes.

CodeMeaning
0Success.
1Runtime error: unreadable skeleton or mapping, an invalid --compare file (the message names it), an unloadable --ontology, an unwritable --out.
2Usage error, or --compare against a report produced with a different skeleton or mapping. (lcg-eval retrieval --compare follows the same shape with its own hard/soft input policy; see retrieval-quality-evaluation.md.)
3The workspace is unusable: missing, not an ingested workspace, its DB cannot be opened or queried (degraded or corrupt; nothing is repaired), or it holds no nodes in the group. An all-zero report is never produced.

How it reads without writing

Section titled “How it reads without writing”

Opening a lbug database can replay and checkpoint its WAL, and starting the service migrates, binds a socket and heals indexes. So the original is never opened: the DB file and its sidecars (liminis.db.*) are copied into a temporary directory and the copy is opened in-process (lcg_core::db::Db, then the same read queries knowledge_get_nodes_by_group and knowledge_get_edges_by_group use). The workspace itself is only read, including the ontology files, so a run (successful or failed) leaves it byte-identical. No service process or embedder is started. See ADR-0819.

The vector/FTS extensions that opening needs are loaded the way the service loads them (a staged bundle, or lbug’s own install into your home directory). They are never written into the workspace.

The mapping file

Section titled “The mapping file”

The mapping is data, kept next to the fixture (crates/eval/fixtures/retrieval-v2/graph-mapping.json), so a second corpus or a different relation vocabulary needs no code change.

  • kinds: skeleton entity kind → the node type labels accepted for it.
  • links: skeleton fact attribute → the accepted relation types. direction is stated relative to the skeleton fact’s subject (the fact’s entity): subject_to_object means the edge source is the subject and the target is the value entity; object_to_subject is the reverse. Direction is declared per accepted relation type and is never inferred. Accepting a free-form name (MANAGES) is how the same format covers graphs built without an ontology.
  • junk.prefixes: first slug segments that mark a note ID (see Junk).
  • A kind in the skeleton with no kinds entry, or a link-shaped attribute with no links entry, is listed in the report as unmapped and excluded from the relevant denominators; it is not counted as a failure.

The report records the SHA-256 of the skeleton and the mapping. --compare refuses two reports whose hashes differ.

Matching rules

Section titled “Matching rules”

Each rule is defined once, in crates/eval/src/graph_integrity/rules.rs.

  • Normalisation. Lowercase; _, - and any whitespace read as one space; ends trimmed. So Cedar_Core, CEDAR-CORE and cedar core are the same name, and OWNED_BY equals owned by.
  • Name match. Equality of normalised names. Never a substring, never an alias, never fuzzy: Cedar Core does not match Cedar Supply or Cedar.
  • Node of an entity. Every node whose normalised name equals the entity’s. Several nodes means the entity is split; edges on any of them count as incident to the entity.
  • Type match. Some entry of the node’s labels (the type plus its ancestors) equals, case-insensitively, one of the mapping’s node_types for the kind. The implicit Entity label never counts. labels is used rather than kind, which is an identity field that is Entity unless the ontology marks the type identity-bearing.
  • Edge type. The stored relation_type when non-empty, else the edge name, compared through normalisation against the mapping’s names.
  • Value text. The normalised value must occur in the normalised edge fact at alphanumeric word boundaries (so 6 does not match inside 96). This is an exact-string rule: a fact restated as 4200 for $4,200 is “not stated” although the value is present. “Not stated” therefore over-counts the true misses (it is an upper bound on them) and “stated” under-counts, so “stated” is a lower bound. The word-boundary containment can push the other way only in rare cases (a short value such as 9 found in an unrelated mention on an incident edge), so neither figure is exact.

Metrics

Section titled “Metrics”

All counts are reported as numerator/denominator where a denominator is meaningful, identically in report.md and report.json.

Typing

Section titled “Typing”
  • Found: skeleton entities with at least one matching node, of all skeleton entities.
  • Split: entities matched by two or more nodes (a count).
  • Typed: entities, among those whose kind is mapped, with at least one matching node carrying an accepted type. An absent entity is not typed. The denominator is the number of mapped entities.

Links, per attribute and in total

Section titled “Links, per attribute and in total”

A true link is a skeleton fact whose value is itself a skeleton entity and whose attribute has a links entry, de-duplicated by (subject, attribute, value entity). Per link:

  • Present: any edge, of any type and in either direction, between a node of the subject and a node of the value entity.
  • Expected relation type: among those edges, at least one whose type is accepted for the attribute.
  • Direction correct: among links with the expected type, at least one expected-type edge whose orientation matches that relation type’s declared direction. Judged only among edges of the expected type; a link with both a forward and a reversed edge counts as correct. The denominator is the number of links with the expected type, so 56/71 reads “56 of the 71 typed links point the right way”.

Value facts

Section titled “Value facts”

A value fact is a skeleton fact whose attribute is not a mapped link and whose value is not a skeleton entity, de-duplicated by (entity, attribute, value). The denominator is all of them.

  • Stated: some edge incident to a node of the entity has the value in its fact text.
  • Misattached: some such edge that states the value has, as its other endpoint, a node that is a different skeleton entity, and its fact text does not name that entity. For example “Marlin Core has a monthly budget of $4,200” stored as Marlin Core HAS_MEASURE Tomas Kowalski. An edge whose text does name the other entity (a person set the budget) is a legitimate relation, not misattached. The two flags are independent: that Marlin Core edge is both stated and misattached; each fact is counted once per flag.

A self-loop on the entity (the representation of a literal-valued fact under an ontology since #823, see ontology.md) that states the value counts as stated and is never misattached, since its other end is the entity itself.

Why a fact is not stated (--unstated-breakdown, #823). “Stated” reads only edge fact text, so a value can be in the graph and still count as not stated. With the flag, each not-stated value fact is put in the first of these that holds:

  1. Only in the entity’s node summary: the value (exact bounded match, as for “stated”) is in a summary of one of the entity’s own nodes.
  2. On another entity: the value is on an edge not incident to the entity, or in another node’s name or summary. For example “The offsite will take place in Aarhus” on an offsite node’s edge.
  3. Present in another surface form: an incident edge or the entity’s own summary states it in a form the exact match misses. A [day] Month YYYY value matches its ISO (2027-03, 2026-11-02) and abbreviated (Mar 2027) spellings; any other value with digits matches when all its number tokens appear, separators removed ($4,200 ≈ 4200 USD, 98.5% ≈ 98.5 percent). This is loose, since a small number can match an unrelated figure, so this group is an upper bound.
  4. Absent: none of the above.

The breakdown is diagnostic and does not change the stated or misattached definitions.

Junk

Section titled “Junk”

Nodes named like a note ID. A node is junk when it is not a skeleton entity and either its normalised name equals a normalised note ID from the skeleton (project-cedar-core-1), or its raw name is lowercase slug-shaped ([a-z0-9]+(-[a-z0-9]+)+), starts with one of junk.prefixes and has an all-digit segment (recap-01-aiko-osei, digest-047). A node that merely looks unusual is not junk. This is measured here and fixed elsewhere.

Signature

Section titled “Signature”
  • Marks: the number of edges carrying a stored signature_mismatch mark (#816), per edge type, read from the edge attributes JSON key signature_mismatch (null or false do not count; the key name is the constant SIGNATURE_MARK_KEY). When no edge carries the key, the report says marks are absent (a graph or build without #816) so that zero is not read as “clean”.
  • Fit / reversed / neither, per edge type, against the ontology’s declared signature (source_type → target_type, each a name or a list since #816): fit when the source node’s labels include any of the source types and the target’s include any of the target types (labels already include ancestors); reversed when they satisfy it swapped and do not fit; neither otherwise. The declared types are resolved as #816’s ingest check resolves them (names the ontology does not declare are ignored). An empty side matches anything; a relation with no endpoint types, and a symmetric relation, is counted as unconstrained. Edge types in the graph that the ontology does not declare are listed separately. With no ontology, or an ontology with no signatures, the section is reported as not applicable.

Comparing two graphs

Section titled “Comparing two graphs”

--compare <report.json> prints, for every metric, the earlier value, this run’s value, the signed delta (this − earlier) and whether it is an improvement (higher is better for found, typed, links and stated; lower is better for split, misattached, junk, marks, reversed and neither). run_meta (workspace path, version, timestamp) is ignored. For ratio metrics the verdict is judged by the rate (num/den), not the numerator, because the denominator can differ between graphs (for example direction-correct is 35/35 on a free-form graph and 56/71 under an ontology: the delta is +21 but the verdict is “worse rate”); such rows are marked “(denominators differ)”. A different skeleton or mapping hash exits 2, but report.md and report.json are still written to --out first; a file that is not a valid report exits 1 naming the file.

Determinism

Section titled “Determinism”

The same workspace, skeleton, mapping and ontology give identical JSON. The only run-dependent data (workspace path, tool version, timestamp) is in a separate run_meta block.

Reconciliation with the E13 baseline

Section titled “Reconciliation with the E13 baseline”

The E13 table in #819 came from a one-off script outside LCG that is not in this repository.

Provenance of the figures below. The numbers in this section are maintainer-reported: the maintainer ran the command on three kept v2 workspaces (free-form, ontology v3.1, v3.1 after the #816 repair) and reported the results on PR #822, including that the workspaces were byte-identical afterwards and that a run takes about 0.14 s. The kept workspaces and the E13 script are not in this repository, so these figures cannot be reproduced from the repo alone, and SC-001 is not verified by anything committed here. The repo’s own checks are the unit tests (including the hand-built graph and the shipped-mapping coverage test).

Denominators. The command finds 60 true links (five attributes × 12 pairs) and 440 literal value facts; E13 used 72 and 428 (the same sum of 500). The difference is the 12 Location links: E13 scored them as links because the value resolves to a graph node, while here a skeleton fact is a link only when its value is a skeleton entity, so Location counts as a value fact. Excluding Location from E13’s figures gives this command’s link rows:

expected relation typedirection correct
ontology v3.159/6044/59 (Account manager 6/12, Exception approver 5/12)
v3.1 after #816 repair59/6059/59
free-form53/6053/53

As reported, these equal E13’s 56/71 → 44/59 and 71/71 → 59/59 once its 12 Location links are removed. Scoring Location as a link (LOCATED_IN, subject to object, when its value resolves to a graph node, as E13 did) is a possible later extension of the mapping and the scoring rule.

Other rows (maintainer-reported). Typing is 47/48 on the ontology graphs with all 48 entities found; junk nodes are 13 on the ontology graphs (the same list as E13); value facts are 293/440 stated with 27 misattached, against E13’s 290/428 and 29 under its looser matching; all 975 signature_mismatch marks written by the #816 repair are read on the repaired workspace.

The mapping must name the ontology’s relation types. A link attribute whose mapping lists only free-form names scores 0/12 expected type and 0/0 direction on an ontology graph, which hides the defect the report exists to catch. This happened for Account manager (CONTACT_FOR) and Exception approver (APPROVES) until they were added. The unit test shipped_v2_mapping_covers_the_ontology_relation_types requires every v2 ontology relation type (OWNS, SUPPLIED_BY, CONTACT_FOR, APPROVES, REPORTS_TO) to be in the mapping with the expected direction. A mapping for another corpus needs the same check against its ontology.

Remaining residuals come from the string rules above: the junk count depends on the note-ID rule (an exact ID or a prefixed slug with a digit segment), and free-form typing depends on the node_types list in the mapping, which is the tuning point for a free-form graph’s labels.

Value-fact misattachment (#823)

Section titled “Value-fact misattachment (#823)”

Under an ontology, value facts were pinned to unrelated entities (27 of 440 misattached on the ontology v3.1 graph above, against 2 free-form). #823 stores a literal-valued fact as a self-loop on the entity it describes (ADR-0823). The acceptance targets: misattached at most 3 under ontology v3.1, stated not lower than the baseline, and the other metrics within ±1 of a baseline from the same commit (direction-correct compared as a rate when the denominators differ), with free-form unchanged within ±1.

Why value facts are not stated: free-form proxy

Section titled “Why value facts are not stated: free-form proxy”

Provenance. Research for #823 analysed the checked-in free-form v2 cassette (crates/eval/fixtures/retrieval-v2/cassette.jsonl, recorded 2026-11-18 with Haiku 4.5, from prompts that predate #816 and #824) with a script kept outside the repository. It counts the union of extractions across the cassette’s 1,006 calls, not a stored graph, so its figures approximate the command’s rather than reproduce them (252/440 stated, against E13’s free-form 259/428; 2 misattached, matching E13). The ontology v3.1 graph is not in the repository; its breakdown comes from --unstated-breakdown on the maintainer’s kept workspace (below).

Of the 440 value facts, 201 were not stated on any edge of their entity in the stating note:

CauseFacts
Only in the entity’s node summary138
On another entity: an edge not incident to it23

Most of the gap is not missing data: two thirds of it sits in the entity’s summary, which “stated” does not read. Only about 24 facts (5%) look genuinely absent, so a follow-up fix for the gap is warranted only if the ontology graph’s breakdown differs materially. 335 of the 1,006 chunks had fewer than two entities, which the free-form prompt gives no way to carry an edge for.
